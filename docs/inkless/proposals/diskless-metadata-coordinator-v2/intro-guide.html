Inkless · Diskless topics · A guide for newcomers

The diskless metadata coordinator, from the ground up

Diskless topics keep Kafka data in object storage instead of on broker disks. Something still has to decide the order of that data and remember where every batch lives. This guide builds that component one piece at a time. It starts with the problem and builds on the parts Kafka already has. Then it tackles the hardest question, when an object in storage may be deleted, and shows how the design answers it without trusting clocks.

Part 1

Why a diskless topic needs a coordinator

Before you can understand a redesign, you need to know what the thing does and why it exists. This part starts with classic Kafka and removes one piece at a time until the coordinator's job is the only thing left.

1Classic Kafka in one picture

Why this exists

Diskless topics exist to remove a cost that classic topics can't avoid. To see that cost, you first need to see how a classic topic stores data.

KIP-1150: Diskless TopicsKIP-1163: motivation

A Kafka topic is split into partitions. Each partition is an append-only log: a list of records where every record gets the next number, called its offset. Offsets are how consumers keep their place: "I've read up to offset 1,400."

In a classic topic, each partition has one leader broker and a few followers. The producer sends its records to the leader. The leader writes them to its local disk, gives them offsets, and the followers copy them. With three copies in three availability zones, the data survives the loss of a whole zone.

That safety has a price. Cloud providers charge for every byte that crosses from one zone to another. The producer's zone matches the leader's zone only one time in three, and the two follower copies always cross a zone. The leader also needs a disk big enough for all the data it keeps.

2Diskless topics: let object storage keep the copies

Why this exists

Object storage, such as Amazon S3, Google Cloud Storage, or Azure Blob Storage, already stores data durably across zones, and writing to it from inside a zone doesn't add a cross-zone charge. KIP-1163 proposes that Kafka hand replication to object storage instead of doing it itself.

KIP-1163: "Kafka delegates replication of diskless topics to object storage"

In a diskless topic, the producer sends its records to any broker, usually one in its own zone. The broker doesn't write them to disk. It collects produce requests in a buffer for a short time, about 250 milliseconds or a few megabytes, and then uploads the whole buffer to object storage as one object.

That object is called a WAL segment or WAL object (WAL stands for write-ahead log). Because the broker accepts produce requests for every partition, one WAL object holds batches for many partitions, often from many topics.

Why mix partitions in one object? Object storage charges per request. If each broker uploaded one object per partition every 250 milliseconds, a cluster with thousands of partitions would make thousands of uploads per second. Mixing keeps the number of uploads tied to the number of brokers, not to the number of partitions. KIP-1163 says it directly: mixing "is necessary to keep the object storage write operation costs reasonable."

What this leaves open

3Data without order: what the coordinator does

Why this exists

In a classic topic, the leader orders the data because it's the only writer. A diskless partition has many writers, so ordering has to move somewhere else. KIP-1163 separates the data, which goes to object storage, from the metadata about the data, which needs strong consistency. The component that owns that metadata is the diskless coordinator.

KIP-1163: "decouple the handling of batch data and batch metadata"KIP-1164: role of the coordinator

Think of a warehouse. Brokers drop boxes into it (the WAL objects). Each box holds pages from many different books (the partitions). Nobody numbers the pages when the box is packed. The coordinator is the catalog at the front desk. When a box arrives, the broker tells the catalog what's inside, and the catalog writes down: "pages 100 to 149 of the book orders-0 are in box X, starting at byte 4,096."

That catalog entry is called a batch coordinate. The coordinator does three kinds of work with coordinates:

  • Commit. After an upload, the broker sends the coordinator a list of the batches in the object. The coordinator checks them (for example, it rejects a duplicate from an idempotent producer), gives each batch its offsets, and stores the coordinates. Only then does the producer get its answer. In the code, this is commitFile.
  • Find. When a consumer asks for offset 1,400 of orders-0 and the broker doesn't have it cached, the broker asks the coordinator where those batches are. In the code, this is findBatches. Related lookups, such as "what is the latest offset," go through listOffsets.
  • Housekeeping. Retention, DeleteRecords, and topic deletion remove coordinates. Once no coordinate points into an object, the object can be deleted from storage.

4Where the coordinator lives today, and why that changes

Why this exists

Inkless runs the coordinator on PostgreSQL. KIP-1164 rejects an external system "to keep Kafka self-sufficient," and proposes storing the coordinator's state inside Kafka. The design in this guide implements a subset of that proposal.

KIP-1164: Rejected alternativesScale and availability

In Inkless today, the coordinator is a PostgreSQL database. Brokers talk to it through a Java interface called ControlPlane. A commit is a SQL transaction that inserts the batch rows, and a lookup is a SQL query. This works and ships, but it has costs:

  • Another system to run. Every Kafka cluster with diskless topics also needs a highly available PostgreSQL deployment, with its own backups, upgrades, and on-call.
  • One database for the whole cluster. Every commit and every cache-miss lookup from every broker goes to the same primary, which limits both scale and availability.
  • Upstream Kafka can't depend on it. Apache Kafka can't require users to bring a specific database.

KIP-1164 proposes building the coordinator the way Kafka already builds its other coordinators. The group coordinator keeps consumer group state in the internal topic __consumer_offsets. The diskless coordinator keeps its state in a new internal topic, __diskless_metadata. The KIP also rejects two other places to put the state:

OptionWhy KIP-1164 rejects it
An external system, such as PostgreSQLKafka should be self-sufficient.
The cluster's own KRaft metadata quorumIt would mix slow, low-volume cluster metadata with fast, high-volume batch metadata, and could slow down critical work such as leader elections.
A separate KRaft quorumIt offers no real benefit over a normal Kafka topic.

The design adds this topic-based coordinator as a third ControlPlane implementation, DisklessMetadataControlPlane, next to PostgreSQL and an in-memory one used in tests. An operator selects it with inkless.control.plane.class.

The two rules every decision must pass

The design holds every decision to two bars. You'll see them cited again and again in later chapters, because they decide which ideas survive:

Data-loss bar: Kafka parity

The coordinator must survive every failure that a classic topic survives. If a classic topic would also lose data in some failure, the design may accept that loss as a risk, but never more.

Performance bar: no worse than PostgreSQL

No extra waiting on the produce, commit, or read path compared with the PostgreSQL backend, and no change that adds a high cost to each operation.

Takeaway

The goal is a coordinator built from Kafka's own parts: an internal topic as storage and partition leaders as coordinators. It must be as safe as a classic topic and as fast as PostgreSQL.

What this leaves open

A database gives you transactions, indexes, and durability for free. How do you get the same from a Kafka topic?

Part 2

Building a coordinator out of Kafka parts

This part explains how a Kafka topic, a local SQLite database, and a few rules together replace a PostgreSQL server. These pieces are the foundation for everything after it, including the deletion model in Parts 3 and 4.

5The log is the truth

Why this exists

A database guarantees that a committed change survives and that everyone sees changes in the same order. A replicated Kafka log gives the same two guarantees, so KIP-1164 makes the log of __diskless_metadata the coordinator's source of truth.

KIP-1164: "The source of truth for the coordinator will be the __diskless_metadata topic"

Every decision the coordinator makes becomes a record in the log. "Object X was committed, and its batch for orders-0 got offsets 100 to 149" is a record. "Retention removed every batch of orders-0 below offset 500" is a record. "Topic clicks was deleted" is a record.

The leader of the coordinator partition is the only writer. It runs every request through the same four steps that KIP-1164 describes, which also match how the KRaft controller works:

  1. Check the request against the current state. For example: is this a duplicate, and what's the next free offset?
  2. Append one record that describes the outcome, including the values it chose, such as the offsets.
  3. Wait until the followers have copied the record. Kafka tracks this with the high watermark: the offset below which every in-sync replica has the record.
  4. Reply to the broker that asked.

One rule makes this work: applying a record never reads anything outside the log. It never reads a clock, and it never reads the broker's own view of cluster metadata. The record carries every value it needs. If one replica applied "delete topic clicks" when its own copy of the cluster metadata said so, and another replica did it a moment later, they would delete at different positions in the log and end up with different state. Because every replica reads the same records in the same order, every replica ends up with the same state.

Analogy

A bank keeps a journal of transactions. The balance of every account can be recomputed from the journal at any time. If a clerk wrote "the balance is whatever my watch says it should be," two branches would disagree. The coordinator's log is the journal, and every value goes into the journal.

Takeaway

The coordinator writes its decisions as records to a replicated topic. The leader decides, the followers copy, and every replica rebuilds the same state from the same records.

What this leaves open

A log is good for writing, but a consumer's question, "where is offset 1,400 of orders-0?", needs an index. Replaying the whole log for every lookup is far too slow.

6SQLite: a copy you can always rebuild

Why this exists

Kafka's other coordinators keep their whole state in memory. KIP-1164 notes that the diskless coordinator's state is much larger, "up to hundreds of megabytes or even gigabytes," so it proposes SQLite, an embedded database, to hold the state on disk with indexes.

KIP-1164: Local state machine

Every replica of a coordinator partition keeps its own SQLite database. SQLite runs inside the broker process, so a query has no network hop. The tables hold the same things PostgreSQL holds today: logs, files, batches, and producer state.

Each replica applies records from the log to its SQLite database, in log order, and only up to the high watermark. With each apply, it stores the offset it applied in the same SQLite transaction. After a restart, it reads that offset and continues from the next record.

Why only up to the high watermark? A record above the high watermark isn't safe yet. If the leader fails, the new leader may not have that record, and the log is truncated to match the new leader. If SQLite had already applied the record, it would need to undo it, and undo is where bugs hide. By waiting, SQLite only ever moves forward.

The database is a cache, not a source of truth. If it's lost or corrupt, the replica deletes it and rebuilds from the log.

Takeaway

Each replica turns the log into an indexed SQLite database. It applies only what the high watermark covers, so it never has to undo anything, and it can always rebuild from the log.

What this leaves open

If the leader may only apply a commit after replication, does every commit have to wait for the previous one to replicate before it can even be checked?

7Speculative state: checking ahead of replication

Why this exists

KIP-1164 names two requirements that pull against each other. Commits should be pipelined, so the next one can start while the current one replicates. But the local state should only change after replication. The coordinator meets both with an in-memory overlay of pending records.

KIP-1164: How operations are performedPerformance bar

Picture two commits for orders-0, a few milliseconds apart. The first one gets offsets 100 to 149. Its record is on its way to the followers, so SQLite doesn't have it yet. If the leader checked the second commit against SQLite alone, it would also hand out offset 100.

The fix is the overlay: a list, in the leader's memory, of records it has appended but not yet applied. The leader checks each new commit against SQLite plus every overlay entry. The second commit sees the first in the overlay and gets offsets 150 to 199.

  • Batching. The leader collects commits for a short linger interval and appends them as one log batch. One replication round trip and one disk sync then cover many commits.
  • Apply on the high watermark. When the high watermark passes an entry, the leader applies it to SQLite, removes it from the overlay, and replies.
  • Failure. If an append fails, the leader drops that entry and every entry after it, and those requests get a retriable error. Later entries took their offsets from the failed one, so they're wrong too.
  • Only the leader. Followers keep no overlay. A new leader starts with an empty one.

This loop isn't new code. It runs on CoordinatorRuntime, the same runtime the group coordinator and share coordinator use. The runtime already provides the single writer thread, the linger, the revert after a failed append, and the parked replies. The overlay is kept in the runtime's in-memory timeline structures, while committed state stays in SQLite.

Analogy

A restaurant host writes reservations in pencil while waiting for the manager to confirm them in ink. New guests are seated around the pencil marks, so no table is booked twice. If the manager rejects one reservation, every pencil mark written after it is erased, because those were planned around it.

8Durability: every batch reaches the disk

Why this exists

The data-loss bar demands Kafka parity. A coordinator partition holds the index of many user partitions at once, so losing its tail loses more than a classic topic would in the same failure. The design therefore makes flushing every batch mandatory, with no weaker mode.

Data-loss barCorrelated power loss

The coordinator writes to __diskless_metadata the way the safest classic producer does:

  • acks=-1: an append counts only when every in-sync replica has it.
  • Replication factor 3 with min.insync.replicas=2: if fewer than two replicas are in sync, appends fail at once with NOT_ENOUGH_REPLICAS instead of hanging. The upstream coordinators append with acks=1, so Inkless brings its own writer for this topic.
  • No unclean leader election: a replica that's missing acknowledged records never becomes leader.

Classic Kafka usually doesn't force each batch to disk with fsync. It relies on copies in different zones: if one broker loses power, the others still have the data. But if every replica loses power at once, which is a correlated power loss, each one loses what was still in memory. On a classic topic that loses the unflushed tail of that one partition.

On the coordinator, the damage spreads, because object storage doesn't lose power along with the brokers:

  • Reused offsets. A lost commit record frees its offsets. The next commit takes them for different data. Brokers that cached the old coordinates now serve different records for the same offset. One coordinator partition holds this for its share of every diskless partition in the cluster.
  • Deleted objects that come back to life in the index. A record that releases an object can survive on one partition while the record that removed the batches is lost on another. The object is then deleted while batch rows still point at it.

So __diskless_metadata requires flush.messages=1: every replica syncs every batch to disk before it counts as appended. Thanks to the linger, that's one sync per batch of commits, not one per commit. The leader's sync matches what PostgreSQL does on every commit. The followers' sync is the price of Kafka parity, and the KRaft metadata log pays the same price for the same reason.

The log now grows forever, because nothing ever deletes old records. A replica that rebuilds from offset 0 after a year would replay a year of commits.

9Snapshots: keep the log short

Why this exists

KIP-1164 proposes to "take snapshots of the local state" and prune the log behind them, the way KRaft does under KIP-630. Without that, the log and the rebuild time grow without limit.

KIP-1164: Metadata log size management

A snapshot is a copy of a replica's SQLite file at a known log offset. Once enough replicas hold a snapshot at offset X, nobody needs the records below X: a replica that loses its database can load the snapshot and replay from X. The leader can then move the log's start forward, and Kafka deletes the old segments.

  • Every replica snapshots itself. Each one copies its own SQLite every hour or every 1 GiB of applied log, whichever comes first, and keeps exactly two snapshots: the newest and one older.
  • The leader moves the log start carefully. It only advances to an offset that at least min.insync.replicas in-sync replicas, the leader included, hold a covering snapshot for. It uses its older snapshot, so the one it keeps after its next rotation still covers the log start.
  • Followers report their snapshots to the leader on a private request. A report counts only while the replica is in sync. If a replica drops out, its report is ignored, because it may have lost its files meanwhile.
  • A replica that needs records below the log start, for example a brand-new replica, fetches a snapshot from an in-sync follower in chunks. It uses the leader only when no follower has one, because the leader is already the busiest broker.

One detail shows how careful the design is about positions. The snapshot's offset is read from the applied-offset row inside the finished copy, never from the live database. A tag read before the copy could be too low. A tag read after could be too high, which would let the leader delete records the copy doesn't contain.

What this leaves open

So far there's one coordinator for the whole cluster. Its leader handles every commit and every cache miss from every broker. Is one leader enough?

10Many coordinators: splitting the work by hash

Why this exists

KIP-1164 gives __diskless_metadata multiple partitions, "effectively creating multiple coordinators and sharding the space of user partitions for scalability." It also limits the damage of a stall: one stuck leader then affects only its share of the cluster.

KIP-1164: Partitioning of __diskless_metadata

The topic has N partitions, 8 by default (the default is provisional). Each one is a complete, independent coordinator, with its own log, SQLite databases, snapshots, overlay, and leader. Kafka spreads the leaders across brokers as it does for any topic. This guide calls them coordinator partitions and writes them as cp0, cp1, and so on. A partition of a normal topic, such as orders-0, is a user partition.

Every user partition belongs to exactly one coordinator partition, so it keeps exactly one place that hands out its offsets. The mapping is a hash, so no broker needs to store a table:

  1. Build the log key: the 16 bytes of the topic ID followed by the partition index as 4 bytes.
  2. Hash it with Kafka's murmur2 and take the result modulo 4096. That's the slot. The 4096 is a fixed protocol constant.
  3. The coordinator partition is slot % N.

Why the extra step through 4096 slots? It keeps a door open. N must be a power of two. If the cluster later doubles N, every slot either stays where it is or moves from p to p + N, so exactly half of each partition's work moves and nothing else changes. Today N is fixed after creation, and the controller refuses CreatePartitions on the topic, but the slot layer costs nothing at runtime: with a power-of-two N, it gives the same answer as murmur2 % N.

KIP-1164 proposed storing each user partition's coordinator in the partition metadata. The hash avoids that stored state. Each leader also recomputes the mapping for every request it receives and rejects a mismatch with INVALID_REQUEST, because a broker that mapped differently would create a second writer for a user partition.

11One file, many coordinators: commit parts

Why this exists

KIP-1163 lets any broker write any partition, so a WAL object usually spans many coordinators. KIP-1164 calls this "undesirable" because it adds network calls, partial failures, and tail latency, and it proposes produce gateways to reduce it. This design leaves gateways out of scope and makes the split commit work safely instead.

KIP-1164: Reducing multi-DC commit operationsPerformance bar

The coordinator partitions that an object's batches map to are its participants. When a broker commits an object, it splits the commit into one part per participant and sends the parts in parallel. Each part carries only that coordinator partition's batches. Each part succeeds or fails on its own.

Wouldn't it be safer to make the parts all-or-nothing with a two-phase commit? It would cost an extra round trip on every commit, and it would protect a guarantee Kafka doesn't offer: a non-transactional produce to two partitions isn't atomic in classic Kafka either. The existing commitFile already returns a separate result for each batch. So if one part fails, the producers of those partitions get a retriable error and retry only those partitions, as they would for any partial produce failure.

Commit queues

Today the broker's FileCommitter commits files on one thread, one file after the other. That keeps a broker's commits in order. With many coordinators, that thread becomes a trap: most files have batches for most coordinator partitions, so if one coordinator partition is slow or offline, every later file waits behind it, on every broker.

The order that matters is the order within a user partition, which here means within a coordinator partition. So FileCommitter keeps one ordered queue per coordinator partition. A file's part on cp2 waits only for the same broker's previous part on cp2. Every part shares its file's commit deadline, so a stuck queue delays each waiting part by at most one deadline. PostgreSQL and the in-memory backend map everything to one queue, which keeps today's behavior.

Try it: one coordinator partition goes bad
Interactive

Two other ideas were considered and rejected. Uploading one object per coordinator partition would remove the split entirely, but it multiplies object-storage writes by up to N. Routing every produce so each broker only writes for one coordinator partition would mean clients could no longer produce to any broker, and every zone would need a broker for each coordinator partition.

Takeaway

A commit fans out into independent parts. A slow coordinator partition hurts only its own user partitions and never stalls the rest.

What this leaves open

Each coordinator partition knows its own batches. But only one thing spans all of them: the object itself. Who decides when it's safe to delete it?

Part 3

The hard problem: deleting objects safely

This part covers the hardest problem the coordinator has: deciding when an object in storage can be deleted. It explains why the problem is hard and what KIP-1164 proposed. Then it walks through a natural first approach, an owner and an intent for every object, and shows why that approach fails both bars.

12Three ways an object gets left behind

Why this exists

Objects cost money for as long as they exist, so every object must eventually be deleted. Deleting one too early loses data. KIP-1163 lists the failure that leaves "garbage objects" behind, and KIP-1164 adds that an object spread across coordinators has "no one owner that controls the file lifetime."

KIP-1163: Error handling and segment object garbage collectionKIP-1164: WAL file management

Deleting an object is safe only when two things are true: no committed batch points into it, and no commit can point into it later. The second condition is the tricky one. Here are the three situations the design must handle:

  • The orphan. The broker uploaded the object and crashed before any commit. The object sits in storage, and no coordinator knows it exists.
  • The shared object. The object's batches are committed on cp0, cp1, and cp3. Retention removes the cp0 batches after one day, but the cp3 batches live for a week. cp0 knows it's done with the object. It doesn't know about cp3.
  • The unknown outcome. A commit part timed out. The broker gave up and told the producer it failed. But the request may still be sitting in the leader's queue, and it may commit later. Until something rules that out, nobody can say the object is unreferenced.

Interactive

Takeaway

An object can be unknown to everyone, known to only some coordinator partitions, or the target of a commit that may still arrive. A safe deletion design must handle all three.

What this leaves open

There are two broad ways to find deletable objects: look at storage, or keep records. Which one is safer?

13Scan the bucket, or keep the books?

Why this exists

KIP-1164 proposes an owner list with hand-overs for shared objects, plus a background scanner that deletes objects no coordinator knows. The design compares that scanner with deletion driven only by the coordinator's own records, and chooses the records.

KIP-1164: WAL file management and Orphan filesData-loss bar

KIP-1164 sketches this approach: the broker lists the participating coordinators in random order in its commit. The first one is the owner. When it holds no more batches of the object, it hands the object to the next one, and the last one deletes it. For orphans, a background worker lists the bucket, asks every coordinator whether it knows each old object, and deletes the ones nobody knows.

The alternative is to keep the books: the coordinator records every object before or when it's created, tracks who still references it, and deletes only objects its own records name.

The deciding difference is the direction of failure. Every system has bugs and bad days. The question is what happens on a bad day:

  • A scanner deletes what nobody knows. If a coordinator wrongly answers "unknown," live data is deleted. That's data loss.
  • Bookkeeping deletes only what it recorded and resolved. If a record is lost or a bug skips a step, an object stays in storage. That's a leak: it costs money, and nothing is lost.

Takeaway

A leak costs storage. Deleting live data loses records forever. So the coordinator deletes only objects its own records name, and the KIP's deleting scanner is out. A scanner that only reports suspected orphans stays possible as future work.

What this leaves open

Bookkeeping has to learn about an object before anyone can lose track of it, including the orphan from a crash right after upload. How?

14A first try: an owner and an intent for every object

Why this exists

To keep books on orphans, the coordinator must hear about an object before it's uploaded. To keep books on shared objects, one place must collect what every participant knows. The most direct way to get both is an intent recorded before every upload, at an owner chosen among the participants. This chapter calls that the owner approach. The design considered it in detail and rejected it, and seeing why explains most of what the final design does.

KIP-1164: WAL file managementRejected alternative

The owner approach keeps KIP-1164's idea of an owner, but instead of handing the object from owner to owner, one owner collects everything. Here's the life of an object under it:

  1. Pick the owner. The broker closes a file, works out its participants, and generates a random object key. It hashes the key to pick one participant as the preferred owner. If that one can't answer, it tries the next participant.
  2. Store the intent. Before uploading anything, the broker sends an intent to the owner: the key, the participants, and the owner. The owner appends it to its log and waits for replication and the disk sync. If no participant stores the intent, the broker uploads nothing and the produce fails.
  3. Upload and commit. The broker uploads the object, then sends the commit parts. Each part carries its first-send time, the broker's clock reading when it first sent the part.
  4. Releases. When a participant holds no more batches of the object, it reports a release to the owner.
  5. Fences. A participant the owner never heard from is silent: it may hold batches, or its part may never have arrived. Once the maximum commit age (5 minutes) has passed, the owner fences each silent participant. The fence is final: the participant answers "I hold batches," or it marks the key as fenced, rejects any later commit for it, and counts as released.
  6. Delete. When every participant is released and the intent is older than the maximum commit age, the owner marks the object, and after a grace period it deletes it.

Clocks enter in three places. A leader rejects a commit part whose first-send time is older than the maximum commit age, measured on the leader's clock. The owner waits that long before it fences. And after a release, a participant keeps a tombstone for the key so that a delayed retry can't add the batches back. Tombstones and fences expire after twice the maximum commit age through a keys-expired record, so SQLite doesn't grow forever.

One more mechanism handles order. If a part to cp1 times out and the broker's next file also has a part for cp1, the late request could commit after the newer one and break the order of cp1's partitions. So the next part carries the old key as a predecessor key, and cp1 fences it first.

15Why the owner approach fails

Why this exists

Checked against the two bars, the owner approach has three gaps in its ownership model. They're why the design uses a different model, which Part 4 builds. A few other risks apply to any deletion model, and Part 5 covers them.

Data-loss barPerformance bar

Gap 1: the intent sits on the produce path

Every upload waits for the intent: a replicated append with a disk sync on every replica, before the upload can even start. At the median that's about as long as a commit. Under load, its tail latency adds directly to every produce, and when an owner is slow, every object it would own is slow. The PostgreSQL backend has no step before the upload, so the intent fails the performance bar.

Gap 2: safety depends on broker clocks

Tombstones and fences expire after twice the maximum commit age. The age check compares the uploader's clock with the leader's clock. If the two clocks differ by more than the maximum commit age, a very late part can pass the age check after its tombstone expired. It then commits batches that point into an object that's already deleted. A consumer that reads those offsets gets an error, and the records are gone. That fails the data-loss bar: a classic topic doesn't lose acknowledged data because two brokers' clocks disagree.

Gap 3: a lot of machinery

To keep the books without a better tool, the owner approach needs intent records, the preferred-owner hash, owner fallback, handling for a stale owner whose intent reply was lost, predecessor fences, per-key tombstones and fences, keys-expired records, and the maximum commit age. Each one is a source of bugs and tests.

Risks that any deletion model must close

Some risks have nothing to do with who owns an object, so a better ownership model alone doesn't fix them. The design closes each one separately:

  • A broker that deletes an object directly after a partial send bypasses the coordinator's books. Chapter 22.
  • A weaker flush policy loses acknowledged records in a correlated power loss. Chapter 8.
  • Admins and clients could delete or alter __diskless_metadata. Chapter 24.
  • A deposed leader could tell a consumer that an offset doesn't exist. Chapter 23.
  • A replica running an older binary could skip a record it doesn't understand. Chapter 26.
  • After every replica crashes, Kafka could elect a replica whose disk was wiped. Chapter 25.
The idea that replaces it

Treat each uploading broker like Kafka's idempotent producer, with an ordered sequence number per file, and most of this machinery disappears. With many coordinator partitions, the idea needs two more pieces: sequence leases and a tracking partition. Part 4 builds all three.

Takeaway

The owner approach is safe only while broker clocks agree within five minutes, and it adds a blocking step to every produce. The design needs a model where order, not time, decides what's safe.

What this leaves open

Kafka already has a tool that uses order to reject stale and duplicate writes without any clock. Can the coordinator use it for brokers?

Part 4

Safe deletion, step by step

This part builds the deletion model the design uses, on top of everything from Part 2. Each chapter adds one idea and says which piece of the owner approach it makes unnecessary: the owner, the intent, tombstones, or the maximum commit age. By the end of chapter 20, you can follow any object from upload to deletion.

16The broker as an idempotent producer

Why this exists

The owner approach remembers each object key separately and needs time limits to forget them. An ordered number per broker lets a coordinator partition remember one value per broker and still reject every late or duplicate commit. It makes per-key tombstones, per-key fences, keys-expired records, predecessor keys, and the maximum commit age unnecessary.

Kafka's idempotent producer (KIP-98)Data-loss bar

Kafka's idempotent producer works like this. Each producer has an ID, an epoch, and a sequence number that goes up by one with every batch. The partition leader remembers the last sequence it accepted from each producer. A batch with the same sequence is a retry, so the leader answers "already done." A lower sequence is stale, so the leader rejects it. No clock is involved: order alone decides.

The design treats each uploading broker the same way:

  • The broker's epoch comes from KRaft. Every time a broker registers, for example after a restart, it gets a new, higher epoch. So nothing needs to be saved across restarts: the new epoch is higher than everything from before.
  • When FileCommitter closes a file, it gives the file the current broker epoch and the next sequence number. Every commit part of that file carries the pair (epoch, sequence). Pairs compare epoch first, then sequence.
  • Every coordinator partition keeps one broker row per uploading broker: the last pair that committed there, and the complete per-batch result of that commit.
  • Gaps are fine. A file that failed to upload uses a sequence and never commits it. Nothing requires last + 1.

Why a number and not a random ID such as a UUID? Because order lets a partition keep one value per broker instead of a growing set of keys, spot a sequence that's missing, and decide all of it without a clock.

Analogy

A bank doesn't remember every check you ever wrote. It remembers the highest check number it cashed from your account. A check with that number again is a duplicate. A check with a lower number is stale. A new checkbook (a new epoch) voids every check from the old one.

What this leaves open

17Object names you can predict

Why this exists

If the object key is random, only the broker knows it, so the coordinator needs a message per object to learn it. If the key is built from the broker's (epoch, sequence), the coordinator can compute every key a broker could have uploaded, with no message at all.

Deterministic object keysPerformance bar

In this design, every object name has this form:

<clusterId>.<brokerId>.<brokerEpoch>.<sequence>

  • Known in advance. If the coordinator knows broker 3 may use sequences 0 to 1023 in epoch 7, it knows the exact names of up to 1,024 objects, whether they were uploaded or not.
  • The cluster ID keeps two clusters that share a bucket and prefix from overwriting or deleting each other's objects. KRaft never reuses a broker epoch inside one cluster, so the name is unique.
  • Upload retries are harmless. Every attempt for one file uses the same name, and every supported object store overwrites the key.
  • Every backend uses it. PostgreSQL stores keys as opaque strings, so existing random keys keep working.

18Leases: a checkbook of numbers, handed out ahead of time

Why this exists

The owner approach's intent is a round trip before every upload. A lease moves that round trip off the produce path: the broker reserves a whole range of sequence numbers in advance, in the background. Every key the broker may upload is then on record before the upload, with no per-object message. This closes the performance gap.

Performance bar

Each broker has one tracking partition, a coordinator partition chosen by hashing the broker ID: murmur2(brokerId) % N. Chapter 20 explains everything it does. Its first job is handing out leases:

  • Ask for a range. The broker asks its tracking partition for a range [a, b] of sequences for its current epoch. The tracking partition appends a sequences-leased record and replies once it's replicated. A range holds at most K = 1024 sequences.
  • Use it. At file close, the broker takes the next leased sequence. No request is needed.
  • Renew early. When fewer than half the range is left, the broker asks for the next range in the background.
  • Nothing leased, no upload. If the broker has no leased sequence, the file fails at once with a retriable error and isn't uploaded. Nothing unrecorded ever reaches storage.
  • Fallback. If the tracking partition t doesn't answer, the broker asks t + 1, then t + 2, and so on. Without this, one unavailable coordinator partition would stop all diskless produce on about one in N brokers once their leases ran out.

Why 1024? With one file every 250 ms, a range lasts about four minutes, and about 85 seconds when a broker closes files as fast as it can. When a lease ends early, the unused numbers become deletes of keys that were never written. Those are cheap: deletes are free on S3, Google Cloud Storage, and Azure.

A lease ends in three ways: the broker's epoch is retired, the broker asks for a lease at a newer epoch, or the broker sends nothing to the tracking partition for 15 minutes, the idle timeout. Then the unused sequences become leftovers, which the tracking partition cleans up, as chapter 20 shows.

19Floors and fences: closing the door without a clock

Why this exists

Before an object can be deleted, every late commit that could still reference it must become impossible. The owner approach uses time: after the maximum commit age, a late part is rejected. This design uses order: it raises a floor, and every pair at or below the floor is rejected forever.

Data-loss barNo clock decides safety

Each broker row has two marks: the last commit, and a fenced-through mark. The floor is the higher of the two. A new commit needs a pair above the floor. The floor only rises, in two ways:

  • The broker commits a newer file at that partition. This happens all the time on a busy broker.
  • A fence. Another coordinator partition asks: "Which of broker 3's sequences between a and b in epoch 7 do you hold?" The asked partition appends a sequences-fenced record that raises its fenced-through mark to (7, b), and answers with the sequences it holds batches for. Every other sequence in the range is now released: it never committed or its batches are gone, and it can never commit again.

A fence needs no clock and no waiting. What about a part that's in flight at the same moment as the fence? The leader handles them one at a time in its overlay, so there are only two possible orders, and both are safe. Try it:

Unknown outcomes, closed by order

Remember the part that timed out in chapter 12. Its producer got KAFKA_STORAGE_ERROR and retries. The late request can still commit, but only until one of these raises the floor at that partition: the broker's next commit there, a fence, the broker's epoch being retired, or its lease ending. On a busy broker, that's about one commit round trip. After that, the late part is stale. An idempotent producer never sees a duplicate, because Kafka's producer checks catch it. A non-idempotent producer has the same small duplicate window it has with an acks=all timeout on a classic topic, or with PostgreSQL today.

Takeaway

A fence asks a partition what it holds and makes everything else in the range impossible, in one step. Late parts can't sneak in afterward, however late they are and whatever the clocks say.

20The tracking partition: one bookkeeper per broker

Why this exists

The owner approach picks an owner per object, among its participants, and that choice needs a round trip before the upload. This design picks one bookkeeper per broker, fixed before any upload: the tracking partition that issued its lease. Because it issued the lease, it already knows every key the broker may upload.

KIP-1164: WAL file managementPerformance bar

The tracking partition has three jobs for the brokers it serves:

  • Leases: the ranges from chapter 18.
  • Tracking entries: for each committed object, which participants still reference it. Every file sends a part to its tracking partition, even when the tracking partition holds none of the file's batches. That part carries the participant set.
  • The deletion queue: keys that are safe to delete, each with the time it was marked.

Releases

When an apply removes batches, through retention, DeleteRecords, topic purge, or consolidation pruning, the participant checks each touched object: does any batch still point into it? An index on batches(file_id) makes the check cheap, and it runs in the same SQLite transaction. If the answer is no, the participant reports a release to the object's tracking partition. The tracking partition records it, and the participant then writes down that the release was accepted, so a new leader knows which reports to resend.

Why not keep a count of live batches per object instead? A count fails toward data loss: one code path that adds a batch without raising the count, and the count reaches zero while batches remain. The query reads the batch rows themselves, so it can't drift.

Fences, in three situations

  • Silent participants. Once the tracking partition itself and every participant it heard from are released, it fences each participant it never heard from. Each one answers "I hold it" (wait for its release) or "released."
  • Missed sequences. If the tracking partition recorded sequence 1 but never sequence 0, its part for sequence 0 failed while other parts may have committed. It doesn't know sequence 0's participants, so it fences sequence 0 at all N partitions and builds the participant set from the answers.
  • Lease ends. When a lease ends, the tracking partition raises its own floor and fences the unused part of the range at every partition. Keys that nobody holds go to the deletion queue.

Deletion

The existing FileCleaner runs on every broker. On this backend it only gets rows on brokers that lead a tracking partition. It waits the existing one-minute grace period, so readers that cached coordinates can finish, deletes the keys from storage, and records a files-deleted record. Deleting a key that doesn't exist counts as success, which covers leftovers that were never uploaded.

Object storage

The design walks through every orphan case and finds that this model covers all of them without a new mechanism. A broker that stops before or after the upload: its lease end fences and queues the key. A broker that stops after some parts: the silent participants are fenced. A part with an unknown outcome: the next commit raises the floor. A leader change halfway through a delete: the queue is in SQLite on every replica, so the new leader deletes the key again, which is harmless.

Takeaway

Each broker's tracking partition leases its numbers, tracks who still references each of its objects, and deletes an object only after every participant has released it or been fenced. Nothing is deleted that a record didn't make impossible to reference.

What this leaves open

The owner approach's big problem was clocks. This design still has timers: the idle timeout and the grace period. Do they matter for safety?

22The one leak left, and why the broker no longer deletes

Why this exists

A design that only deletes what its books name can still leak, and a broker that deletes on its own can still bypass the books. The design checks both. It accepts one leak and switches off the broker's own delete for this backend.

Data-loss barPartial sends

The accepted leak

Object storage can finish a write after the tracking partition deleted that key. For example, an upload request is stuck in the network, the broker gives up, the lease ends, the key is fenced and deleted, and then storage completes the old write. Nothing will ever delete that object again, because no batch row points to it.

The leak is bounded and costs storage, not data. One upload attempt leaks at most one object. A broker cut off from the cluster can upload at most the rest of its lease, at most K files. The one-minute grace period also covers uploads that land within a minute. PostgreSQL today leaks more: when a commit fails, the broker deletes the object only if isSafeToDeleteFile allows it, and nothing collects the rest. A future scanner that only reports suspected orphans would make the leak visible.

The broker's direct delete

Today, if a commit fails because the control plane is unavailable, FileCommitJob deletes the object itself. With split commits, that's dangerous. Picture part 1 sent with an unknown outcome, then part 2 failing because the control plane became unavailable. No part confirmed, so the broker would delete the object, while part 1 can still commit into it.

The new backend declares a capability that switches off the broker's direct delete, and FileCommitJob checks it first. Every upload already has a leased sequence that the tracking partition resolves, so the backend never needs the direct delete. PostgreSQL and the in-memory backend keep their current behavior.

Takeaway

The only remaining leak is an upload that storage completes after its key was deleted. It's bounded and costs storage, not data. Only the tracking partition's queue deletes objects.

What this leaves open

The deletion model is done. But the coordinator partition is itself a Kafka partition, with leaders, elections, admins, and upgrades. Each of those can hurt it in ways a normal topic doesn't feel.

Part 5

Protecting the coordinator itself

A coordinator partition is a Kafka partition, so it inherits Kafka's behavior during leader changes, admin requests, crashes, and upgrades. For a normal topic, those behaviors are fine. For a partition that holds the index of a whole slice of the cluster, some of them aren't. These four chapters cover the protections the design adds on top of plain Kafka behavior.

23Reads after a leader change: the barrier

Why this exists

A leader that lost its leadership doesn't know it right away, and keeps answering from old state. On a classic topic, the consumer protects itself with leader epochs (KIP-320). Diskless consumers never see coordinator epochs, so one false answer from an old leader could make a consumer skip records. The design adds a barrier for exactly that answer.

Read consistency after a leader changeData-loss bar

When a coordinator leader gets cut off from the controller and its followers, the controller elects a new leader. The old leader, now deposed, keeps answering reads from its own SQLite until it learns the news. This is the deposed window. Its state isn't wrong, only older: it's a committed prefix of the new leader's log.

Most answers from older state are safe, because they're lower or unknown. "The latest offset is 1,000" when it's really 1,500 makes a consumer re-read or wait. It never makes a consumer skip a record. The group coordinator has the same window and the same property.

There's one exception. A consumer asks for offset 1,400, which was committed under the new leader. The deposed leader's high watermark is 1,000, so it answers OFFSET_OUT_OF_RANGE. That answer is false, and it's harmful: the consumer resets its position according to auto.offset.reset. With earliest it rewinds to the start. With latest it jumps to the end and skips records.

The fix: before a leader answers "out of range" above its high watermark, it appends an empty barrier record and waits for it to commit. A deposed leader's barrier can never commit, because its followers stopped fetching from it. After 500 ms the leader answers OFFSET_NOT_AVAILABLE instead, which makes the consumer refresh its metadata and retry, and it finds the real leader. A current leader commits the barrier in one replication round trip and gives the true answer.

Try it: a consumer meets a deposed leader
Step through

Broker 1 led cp0 and was cut off. Broker 2 is the new leader and committed orders-0 up to offset 1,500. Broker 1 still thinks the high watermark is 1,000. A consumer resumes from its committed offset 1,400, and its fetch reaches broker 1.

A consumer that keeps up with the log never reaches the barrier, because asking for exactly the high watermark is in range. Only a deposed leader, a genuine seek past the end, or a client that keeps fetching past the end reaches it, and even then at most one barrier is appended per flush. The broker's delayed-fetch check, which polls for new data while a fetch waits, never runs the barrier.

The alternative was a leader lease: a leader stops serving once it hasn't heard from its followers for a while, and a new leader waits that long before it serves. It would bound the window, but it adds a wait to every failover and makes safety depend on how fast clocks drift. It was rejected.

Takeaway

Older answers are safe because they're lower or unknown. The one false answer, out of range above the high watermark, is only given after a barrier proves the leader is still the leader.

What this leaves open

Reads are safe. What about someone deleting the topic itself?

24Protecting __diskless_metadata from admins and clients

Why this exists

Deleting __diskless_metadata loses the batch index of every diskless partition, every lease, and every deletion queue, and there's no rollback to PostgreSQL. Kafka's "internal topic" status guards almost nothing: only produce, which has a bypass, and DeleteRecords.

What internal-topic status protectsData-loss bar

In upstream Kafka, a principal with the right permission can delete __consumer_offsets. Any client can produce to an internal topic by using the client ID __admin_client. For the coordinator topic, either one would be a disaster: a foreign record would be applied on every replica and would take an offset the leader's overlay doesn't expect.

So the topic joins Kafka's list of internal topics, and the design adds explicit guards in the controller and broker. The guards key on the name __diskless_metadata only, so the other internal topics keep upstream behavior. No guard has a bypass.

25Who may lead after everyone crashed

Why this exists

After a correlated power loss, Kafka has an automatic path that elects the last known leader, even with unclean election turned off. If that broker returns under the same ID with a wiped disk, it's elected with an empty log, and every other replica truncates to match it. The design decides who may lead by storage identity, not by whether the shutdown was clean.

Last-known-leader election (KIP-966)Data-loss bar

Some background. Kafka's eligible leader replicas (ELR) are replicas that dropped out of the in-sync set but still hold every acknowledged record, so they may safely become leader. When a broker shuts down uncleanly, upstream Kafka removes it from the ELR, because it may have lost data that was still in memory. If the in-sync set and the ELR are both empty, the controller falls back to the last known leader.

On a normal topic, an empty log after a wiped disk loses that partition's data. On a coordinator partition, it loses the whole batch index, the leases, and the deletion queues for its share of the cluster, while object storage keeps every object. The election also destroys the copies that survived on the other replicas.

The design changes two rules for this topic only:

  • An unclean shutdown keeps a replica in the ELR. With flush.messages=1, its disk holds every acknowledged record, so nothing is lost by trusting it.
  • A changed disk removes it. Every log directory has an ID that's created when the disk is formatted. When a broker registers, the controller checks whether the directory that held each coordinator replica is still there. If not, the broker leaves the ELR and the last-known-leader list for that partition.

Interactive

Brokers 1, 2, and 3 host cp0. Broker 1 was the leader. All three lose power within seconds. The controller noticed broker 3 first, while two replicas were still in sync, so broker 3 may miss the newest records and isn't in the ELR. Brokers 1 and 2 are. Pick which broker comes back first and whether its disk survived. The others come back later with their disks intact.

A related rule: changing the cluster-wide min.insync.replicas makes Kafka clear the ELR of every topic. The design skips __diskless_metadata in that clear and fixes the topic's own min.insync.replicas at creation, so an operator can't erase the safe candidates by accident in the middle of an outage.

Takeaway

After a crash, any replica whose disk survived may lead, and a replica whose disk changed never leads. A coordinator partition stays offline for good only if every replica lost its storage, which is the same loss a classic topic can't survive either.

What this leaves open

During a rolling upgrade, replicas run different binaries. What if one meets a record it doesn't understand?

26Brokers of different versions: stop, never skip

Why this exists

Kafka's coordinator loader skips record types it doesn't know. That's safe for consumer groups, because each group record is a full snapshot of one key's state. Coordinator records are changes, so a skipped record makes a replica different from the others forever, silently.

Record compatibility across broker versionsRolling upgrades

Every coordinator record is a delta: "remove these batches," "these keys were deleted." No later record repeats it. A replica that skipped "retention applied" would keep batch rows that every other replica removed. If it later became leader, it would serve batches whose objects might be gone.

So the rule is: a replica that meets an unknown record type, version, or tagged field stops applying that coordinator partition at that offset. Its SQLite stays put. It stops serving, and a leader resigns. It keeps fetching bytes, so it stays in sync and loses nothing. A metric and an error log name the record. Once the broker runs a binary that understands the record, it resumes from where it stopped.

Two more rules keep this from happening in normal operation. A feature level controls which record versions the leader may write, so a new record type appears only after every broker supports it. And the controller refuses every downgrade of that feature, because old binaries would stop on records already in the log.

The SQLite file has its own schema version too. A binary that finds a newer schema than it knows treats the database as missing and rebuilds from a snapshot or the log, instead of opening a file it doesn't understand.

Takeaway

A replica never guesses. If it can't read a record, it waits at that record until it can, and every replica stays identical.

Putting it together

This part replays a produce and a fetch through every piece of the design, sums up why it beats the owner approach, and lists what the design still accepts and where it's heading.

27A produce and a fetch, end to end

Broker 3 is in zone A. Its epoch is 7 and its tracking partition is cp2, where it holds the lease [0, 1023]. A producer in zone A sends a batch for orders-0.

  1. Buffer. Broker 3 adds the batch to its current file along with batches for other partitions (chapter 2).
  2. Close. After 250 ms, FileCommitter closes the file and gives it the pair (7, 41) from the lease. No request is sent (chapters 16 and 18).
  3. Name. The object key is <clusterId>.3.7.41 (chapter 17).
  4. Upload. Broker 3 uploads the object. Retries reuse the same key.
  5. Split. The file's batches map to cp0, cp1, and cp3 by hash (chapter 10). Broker 3 sends one part to each, plus a part to cp2 that carries the participant set (chapters 11 and 20).
  6. Check. Each leader checks the mapping, the broker epoch, the broker row, and the producer's own idempotence rules. It reserves offsets against SQLite plus its overlay (chapters 7 and 16).
  7. Append. Each leader appends a file-committed record, in a batch with other commits, with acks=-1 and an fsync on every replica (chapters 5 and 8).
  8. Apply and reply. When the high watermark passes the record, the leader applies it to SQLite, moves broker 3's row to (7, 41), and replies with the offsets (chapter 6).
  9. Answer the producer. Once every part has answered, broker 3 merges the results and responds. The batch for orders-0 got its offsets from cp0.
  10. Fetch. Later, a consumer in zone B fetches orders-0 from a broker in zone B. On a cache miss, that broker asks cp0's leader with findBatches, reads the byte range from the object, and fills in the offsets (chapter 3).
  11. Release. Days later, retention removes the batches on cp0. cp0's apply finds that nothing points into 3.7.41 any more and reports a release to cp2. cp1 and cp3 do the same on their own schedules (chapter 20).
  12. Delete. When every participant is released, cp2 queues the key. After one minute, FileCleaner on cp2's leader deletes it and records a files-deleted record.

29Risks the design accepts

Each accepted risk passes the data-loss bar because a classic topic has the same exposure, or it costs storage or availability instead of data. Each one has a signal or an operator procedure.

The benchmark question, whether N leaders sharing brokers with normal traffic can carry production load, is still open, and benchmarks will answer it. Their results could call for a separate SQLite disk, a cap on findBatches results, or a different default N.

30Where this is heading

The longer-term goal is one metadata component that indexes every form diskless data can take, instead of splitting the truth between the coordinator, tiered storage metadata, and KRaft. Several decisions in this design keep that path open on purpose:

  • Growing the coordinator. The slot layer and the power-of-two rule let a later change split each coordinator partition in two, moving half of its slots, without remapping everything.
  • Extents. A batch row must be able to describe an extent, an offset range mapped to an object and a byte range. Merged or consolidated objects can then replace many batch rows with one, and old objects are released through the same release and fence path.
  • Tiered metadata in the coordinator. Remote segment metadata for a diskless partition could live in the same coordinator partition as its batches, under the same log key. That answers concerns Jun Rao raised in the KIP-1163 discussion about remote log metadata at diskless volumes.
  • Partitionless key ranges. Every record names its log with a Log structure rather than a bare topic and partition, so a later log key encoding can describe a key range instead of a fixed partition.

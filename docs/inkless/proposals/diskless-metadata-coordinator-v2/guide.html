1 · Start with the problem

Diskless data still needs ordered metadata

Object storage holds the bytes, but it does not assign Kafka offsets or tell a reader where a batch lives. Inkless needs a durable control plane for those coordinates.

A diskless topic writes producer data into shared write-ahead-log (WAL) objects. One object can contain batches from many user partitions. The object store knows the object key and bytes. It does not know that a batch belongs to orders-7, covers offsets 120–128, or occupies a particular byte range.

The control plane records that relationship. It assigns offsets in order, commits the batch coordinate, and answers reads. The existing production implementation uses PostgreSQL. That works, but every broker depends on a separate database cluster. The in-memory implementation serves tests and loses state on restart.

Version 2 adds a third backend. It stores the same control-plane state in Kafka, so the cluster can run without a separate database while retaining Kafka's replication, high-watermark, and recovery machinery.

Design target: match the data safety of a classic Kafka topic under the same failure. The design also keeps partial commit behavior: one user partition can succeed while another fails.

2 · Replace the external index

The big idea: Kafka stores the control plane

The __diskless_metadata topic is the source of truth. Its coordinator leaders are the writers, and each replica rebuilds a local SQLite view from the log.

The topic has a fixed number N of coordinator partitions, with a provisional default of 8. Each one has its own log, leader, SQLite database, snapshots, and in-memory overlay. A coordinator leader is the single writer for the user partitions assigned to it.

The topic uses ordinary Kafka replication. A coordinator append uses acks=-1, so the leader rejects a write when the ISR is below the topic's fixed min.insync.replicas. The high watermark advances only after the required replicas have the record. flush.messages=1 protects the cross-partition relationship between a tracking record, participant records, and object storage.

The broker-side delegate splits a request by coordinator partition and sends parts in parallel. A coordinator partition that is unavailable delays only the user partitions mapped to it. The design does not use two-phase commit: Kafka already exposes per-partition outcomes, and commitFile already returns a result per batch.

        Worked example: one object from lease to deletion

        Use one object to connect the terms. The coordinator mapping below is a concrete example, not a replacement for the hash rule in the routing section.

        1. Broker 2 registers at epoch 7. Its lease is [0, 1023] from tracking partition CP3. The sequence source hands file sequence 5 to the WAL committer.
        2. The pair is (7, 5). The object key is <cluster>.2.7.5.
        3. The file has batches for orders-0 on CP0 and orders-1 on CP1. It splits into two commit parts and a tracking part on CP3. CP0 and CP1 are the participants.
        4. CP0's overlay reserves offsets. Its outcome record passes the high watermark. The applied offset advances, and the broker row for broker 2 at CP0 becomes (7, 5) with the stored result.
        5. Retention removes CP0's last batch for the key. CP0 emits a release to CP3. CP1 becomes silent while it still could reference the object, so CP3 sends a fence to CP1 and records its answer.
        6. When CP3 knows every participant is released or fenced, the key enters the deletion queue. It waits through the grace period, then FileCleaner deletes it.

        4 · Route with stable slots

        A fixed slot layer makes growth predictable

        A user partition hashes to one of 4096 protocol slots, then the slot maps to a coordinator partition. Because N is a power of two, doubling N splits each old partition's slots in half instead of reshuffling every user partition.

        The log key is exactly 20 bytes: the topic UUID's 16 bytes in most-significant-bit-first order, followed by the partition index as a four-byte big-endian integer. Kafka's Murmur2 implementation hashes that key. The design uses the same positive-value conversion as Kafka clients.

        slot = toPositive(murmur2(logKey)) % 4096;    coordinator = slot % N

        With N=8, each coordinator owns 512 slots. If the topic grows to N=16, old partition p keeps the slots whose new remainder is p, and new partition p+8 takes the other half. Existing coordinator IDs stay in place. A future handoff still needs to move the corresponding state; the mapping only makes that move bounded and explicit.

        A broker's tracking partition normally uses toPositive(murmur2(brokerId)) % N. The design leaves the broker-ID byte encoding as an implementation item. This guide uses four-byte big-endian broker IDs so the toy has a deterministic rule.

        5 · Follow one file

        A commit fans out, then completes per part

        A WAL file can touch several coordinator partitions. The broker sends one part to every touched coordinator and one part to the tracking partition, with one ordered queue per destination.

        Suppose a closed file contains batches for user partitions mapped to coordinator partitions 0, 1, and 2. The file also sends a tracking part that names its participant set. Those parts run in parallel after the upload completes.

        Each per-coordinator commit queue preserves the broker's sequence order for that coordinator. A slow partition holds only its own queue. Healthy queues continue to commit later files. The shared commit deadline starts when the file closes. At the deadline, confirmed parts return their per-batch results and unconfirmed parts return KAFKA_STORAGE_ERROR with an unknown outcome.

        This is partial success, not a transaction. Consumers can see committed batches from healthy coordinators while the producer retries only the failed user partitions. The tracking path keeps the object alive until every reference is released or fenced.

          6 · Name every upload

          Leases remove the round trip before an upload

          A broker leases sequence ranges ahead of time. At file close it takes the next sequence, builds a deterministic object key, and uploads without asking the coordinator first.

          The default range size is K=1024. The broker's sequence source hands out a lease at its tracking partition and renews it in the background when fewer than half the range remains. It chooses the start above every range it requested in that epoch, including requests whose replies were lost. That prevents overlap across fallback tracking partitions.

          The object key is <clusterId>.<brokerId>.<brokerEpoch>.<sequence>. The cluster ID keeps two clusters sharing a bucket and prefix from touching each other's objects. Retries reuse the same key and storage overwrites it unconditionally.

          If the normal tracking partition is unavailable, the broker asks (t + 1) % N, then continues around the ring. The lease records which partition issued the range. A broker restart creates a higher epoch, ends the old epoch's leases, and starts sequences again for the new epoch.

            7 · Make retries deterministic

            The broker row remembers the answer

            Each coordinator partition keeps one durable broker row per uploading broker. The row stores the last committed pair, its complete result, a separate fenced-through pair, and a retired marker.

            The pair (epoch, sequence) orders a broker's files. The row's floor is the higher of the last committed pair and the fenced-through pair. A new commit must be above that floor. The stored result remains available after retention or DeleteRecords removes the batch rows, so a retry still gets the original offsets and errors.

            The tracking partition checks that a sequence belongs to a lease. Participant partitions do not need the lease table: their broker row floor is enough to reject stale pairs. A higher epoch replaces the row and makes every lower epoch stale. A broker-epoch-retired record makes that fencing durable across a leader change.

            The leader checks the mapping and epoch, compares against pending overlay state and SQLite, validates producer sequencing, assigns offsets, appends one file-committed record, and replies only after the record passes the high watermark.

            Commit pairLeader action
            Retired row or lower epochReject as stale epoch.
            Same as pending last commitAppend nothing. Wait for the pending result.
            Same as applied last commitReturn the stored result, even if batches are gone.
            Above the floor, or no rowRun producer checks and accept as a new commit.
            Anything elseReject as stale sequence and return the floor.

              8 · Delete only after proof

              The tracking partition owns object deletion

              An object enters the deletion queue only after every participant reports no remaining batch or a fence proves that participant cannot reference the object. The grace period delays the delete but never establishes safety.

              The tracking partition records the object's participant set. When an apply removes the last local batch for that object, the participant reports a release to the tracking partition. The report is durable and idempotent. A new participant leader resends releases that lack a release-accepted record.

              A silent participant cannot be trusted to report. Once the tracking partition and every participant it has heard from are released, it sends a range fence to each silent participant. The participant raises its fenced-through mark and answers which sequences it still holds. Referenced sequences wait for their own release; sequences with no remaining batch count as released.

              The same mechanism handles a missed sequence: a tracking part may fail while other parts commit. When a later sequence appears at the tracking partition, the missed range is fenced at all coordinator partitions. Leftover sequences at lease end follow the same path.

              The safety rule: no clock decides whether a deletion is safe. The log position, release state, and fence state decide that. The clock only decides when FileCleaner deletes a key already in the deletion queue.

                9 · Separate pending from committed

                The leader overlay ends at the high watermark

                A leader reserves offsets in an in-memory overlay, appends the reservations, and applies them to SQLite only when the high watermark passes them. A leader change drops an uncommitted suffix and makes callers retry.

                The overlay lets the single writer reserve offsets without waiting for every append to apply. A later request reads SQLite plus earlier overlay entries, so two pending commits cannot receive the same offsets. The runtime batches reservations for one append linger batch.

                Followers keep no overlay. They apply only records at or below the high watermark. If an append fails, the leader resigns, or a new leader truncates the unreplicated suffix, the leader drops that entry and every later entry and fails parked replies with a retriable error.

                A new leader starts empty and waits until its high watermark reaches the log end it observed at election. That high-watermark gate prevents a read or commit from seeing an older prefix as complete.

                  10 · Keep stale reads from resetting consumers

                  A barrier makes an out-of-range answer truthful

                  A deposed leader may serve an older committed prefix, which is safe for reads that return data or a lower position. An offset above its high watermark is different, so findBatches appends a barrier record before returning OFFSET_OUT_OF_RANGE.

                  When a coordinator leader loses leadership, it can keep answering during the deposed window until it learns the new metadata. Its state is a committed prefix of the new leader's state. A lower listOffsets answer makes a consumer reread. An unknown answer makes it retry. Neither skips data.

                  For an offset above the high watermark, the old leader could falsely conclude that the consumer is past the end. A consumer using earliest could rewind, and one using latest could skip records. The leader therefore parks the request and appends a new barrier record.

                  When the barrier passes the high watermark, the leader checks again. If the offset is still beyond the end, it returns OFFSET_OUT_OF_RANGE. If the request waits 500 ms first, it returns OFFSET_NOT_AVAILABLE. A barrier from a deposed leader never commits because followers stop fetching from it.

                  If the high watermark passes the requested offset while the request is parked, the fetch returns batches after the barrier commits.

                  The delayed-fetch probe uses a no-wait request and never appends a barrier. It returns OFFSET_NOT_AVAILABLE immediately, then the real fetch path decides what to do.

                    11 · Rebuild local state safely

                    SQLite is a cache of the log, not a second source of truth

                    Each replica stores its coordinator partition in a local SQLite database and records the applied offset and leader epoch in the same transaction as the state change. A replica never applies above the high watermark.

                    On restart, a replica checks that its stored applied offset and epoch still match the log. A power loss can roll back the latest SQLite applies, but the replica then replays those records from the Kafka log. An unreadable record is never skipped: the replica stops applying that partition, stops serving it, and keeps fetching bytes so it remains in the ISR.

                    Snapshots let the leader move Kafka's log start forward. Every replica keeps the newest snapshot and one older snapshot on local disk. The leader advances the log start only to the lower of its own older snapshot and the highest offset reported by enough other in-sync replicas. With min.insync.replicas=2, one other in-sync replica must report a covering snapshot.

                    newLogStart = min(leaderOlderSnapshot, highestReportedBy(minISR − 1) other in-sync replicas)

                    A report stops counting when its replica leaves the ISR. If no surviving replica has a snapshot covering the log start, a rebuild cannot serve partial state; that coordinator partition stays unavailable until a covering snapshot exists.

                      12 · Protect the control plane

                      The metadata topic is an internal safety boundary

                      An operator must not be able to delete, resize, weaken, or inject foreign records into __diskless_metadata. The controller and brokers enforce those boundaries by name and by fixed topic settings.

                      The topic joins Kafka's internal-topic set and inherits internal behavior such as hidden listings and no tiered storage. Explicit guards also reject DeleteTopics, client and auto-created CreateTopics, CreatePartitions, unclean elections, replica-count changes, client produce, and client DeleteRecords. The coordinator's own append origin is allowed.

                      The controller fixes flush.messages=1, unclean.leader.election.enable=false, retention.ms=-1, retention.bytes=-1, cleanup.policy=delete, and the creation-time minimum ISR. Later config alters cannot weaken those rules.

                      Automatic last-known-leader recovery stays available after a correlated restart, but storage identity decides whether a broker may lead. If a broker returns with a wiped, replaced, or reformatted directory, the controller removes it from the eligible leader records for this topic before election can use it.

                      The coordinator feature is finalized at cluster format time. The configured control-plane class must match the feature. The controller rejects downgrades, and a broker without the finalized feature cannot register. Existing PostgreSQL-backed clusters do not migrate through this design.

                      Why the guards matter: the topic contains offsets, leases, fences, and the only deletion queue. A seemingly ordinary admin operation could make a live object reference a deleted key or cause a second writer for a user partition.

                      13 · Learn from version 1

                      What changed, and why

                      Version 2 removes extra upload-path work and moves safety decisions into durable, replayable coordinator state.

                      Version 1 problem

                      • A per-object intent added a replicated round trip before every upload.
                      • Deletion safety depended on broker clocks and maximum commit age.
                      • A broker could delete an object after only part of a multi-part commit ran.
                      • Admin paths could delete or weaken the coordinator topic.
                      • A deposed leader could return a false out-of-range answer.
                      • A replica could skip a record it could not decode.
                      • A broker with a wiped disk could win a last-known-leader election.

                      Version 2 decision

                      • Leased sequence ranges name objects before upload, with no per-object intent.
                      • Release records and fences prove when a key cannot be referenced.
                      • The tracking partition's deletion queue is the only delete path.
                      • Name-keyed guards and fixed configs protect the internal topic.
                      • A committed barrier confirms leadership before out-of-range.
                      • Apply stops at an unknown record instead of silently diverging.
                      • Storage identity filters unsafe election candidates.

                      The common thread is durable ordering. If a decision affects whether an object can be referenced, a coordinator record makes that decision visible to every replica. A replay sees the same facts and reaches the same result without consulting a wall clock or an external database.

                      14 · Know the boundaries

                      Some risks remain explicit

                      The design accepts a few failure modes that Kafka or PostgreSQL already expose. Naming them keeps the safety boundary clear.

                      • If every replica of one coordinator partition is lost, the mapped diskless partitions and their untracked WAL objects are lost. The blast radius is one coordinator partition, so rack-aware replication factor 3 is the deployment recommendation.
                      • A late storage upload can finish after its key enters the deletion queue and gets deleted. That leaks storage, not data. The grace period covers normal in-flight work, and the lease bounds a cut-off broker's remaining uploads.
                      • A non-idempotent producer that retries through another broker can see a late copy after the retry. Classic Kafka's acks=all timeout and the PostgreSQL backend have the same window.
                      • Retention and LogAppendTime remain exposed to clock skew in the same way as classic Kafka. Operators need NTP monitoring well below half the file-cleaner grace period.
                      • Capacity and isolation remain open for benchmarking. SQLite shares the coordinator leader's heap, page cache, disk, and garbage collector with its other broker work.
                      Implementation items left open in design.md: private request names and error codes, the SQLite driver and packaging, how a leader gives up leadership when it cannot rebuild, the commit deadline, the idle lease timeout, the broker-ID byte encoding, the overlay size cap, and the append linger default.

                      15 · Keep the vocabulary straight

                      Glossary

                      These terms connect the Kafka pieces to the object-storage lifecycle.

                      Where state lives

                      __diskless_metadata topic v2
                      __diskless_metadata is the internal Kafka topic that stores coordinator state in a fixed number of partitions.
                      Coordinator partition v2
                      A coordinator partition is one partition of __diskless_metadata that owns the mapped user partitions.
                      Coordinator leader v2
                      The coordinator leader is the Kafka leader that acts as the single writer for one coordinator partition.
                      User partition Kafka
                      A user partition is a partition of a diskless Kafka topic whose batches map to one coordinator partition.
                      Batch coordinate v2
                      A batch coordinate maps a user-partition offset range to an object and byte range.
                      Slot v2
                      A slot is one of 4096 stable hash buckets that sits between a user partition and a coordinator partition.
                      Log key v2
                      A log key is the 20-byte topic-ID and big-endian partition encoding that the mapping hash consumes.
                      Outcome record v2
                      An outcome record is an append-only coordinator record that carries a state change, assigned values, and batch results.
                      Applied offset v2
                      The applied offset is the last coordinator-log offset that a replica applied to SQLite.
                      SQLite database v2
                      The replica's SQLite database is a rebuildable local cache of its coordinator log.
                      Snapshot v2
                      A snapshot is a finished point-in-time SQLite copy tagged with the applied offset and epoch.

                      How a leader writes

                      Overlay v2
                      The overlay is the leader-only in-memory view of appended records that have not reached the high watermark.
                      High watermark Kafka
                      The high watermark is the replicated log position at which a coordinator entry may apply and its reply may go out.
                      Append linger batch v2
                      An append linger batch is the short group of reservations the leader collects before one coordinator-log append.
                      High-watermark gate v2
                      The high-watermark gate keeps a new leader from serving until it reaches the log end seen at election.

                      How a broker names and commits a file

                      Broker epoch Kafka
                      A broker epoch identifies one registration incarnation of a broker and rises when a new incarnation starts.
                      Sequence v2
                      A sequence is an increasing 64-bit file number within one broker epoch, with gaps allowed.
                      Epoch and sequence pair v2
                      The pair (epoch, sequence) identifies and orders a file, comparing epoch first and sequence second.
                      Sequence source v2
                      The sequence source gives FileCommitter the next leased sequence for the current broker epoch.
                      Lease v2
                      A lease is a range of up to K=1024 sequences that a tracking partition grants to one broker epoch ahead of upload.
                      Object key v2
                      An object key is <clusterId>.<brokerId>.<epoch>.<sequence>, the deterministic storage name for a WAL file.
                      Commit part v2
                      A commit part contains one file's batches for one coordinator partition, plus a tracking part that records participants.
                      Per-coordinator commit queue v2
                      A commit queue orders one broker's file parts for one coordinator partition and lets other queues proceed.
                      Commit deadline v2
                      A commit deadline is the per-file time limit measured from file close, with each part expiring from its own close.
                      Unknown outcome v2
                      An unknown outcome means a part returned KAFKA_STORAGE_ERROR before the leader proved whether its last request committed.

                      How a coordinator remembers a broker

                      Broker row v2
                      A broker row stores one uploader's epoch, last committed sequence and result, fenced-through mark, and retired marker at one coordinator partition.
                      Fenced-through mark v2
                      The fenced-through mark is the highest (epoch, sequence) that a fence makes impossible at one coordinator partition.
                      Floor v2
                      The floor is the higher of a broker row's last committed pair and its fenced-through pair.
                      Broker-epoch-retired record v2
                      A broker-epoch-retired record durably moves a row to a newer epoch or marks an unregistered broker retired.

                      How objects get deleted safely

                      Tracking partition v2
                      The tracking partition issues leases, records object participants, receives releases and fences, and owns the deletion queue.
                      Participant v2
                      A participant is a coordinator partition that holds at least one batch reference to an object.
                      Release v2
                      A release reports that a participant removed its last batch reference to an object.
                      Fence v2
                      A fence raises a participant's sequence boundary so pairs at or below it cannot commit; a sequence fence covers one pair and a range fence covers unused or missed sequences.
                      Missed sequence v2
                      A missed sequence is a sequence the tracking partition never recorded while it did record a later sequence in the same range.
                      Leftover sequence v2
                      A leftover sequence is a leased sequence that the broker never committed before its lease ended.
                      Deletion queue v2
                      The deletion queue holds object keys that the tracking partition has proved cannot be referenced again.
                      Grace period Kafka
                      The grace period is the wait after a key enters the deletion queue before storage deletion runs.
                      FileCleaner Kafka
                      FileCleaner deletes queue entries after the grace period and records which storage keys succeeded.

                      How reads stay safe

                      Deposed leader Kafka
                      A deposed leader is an old coordinator leader that can still answer from its committed local state before learning the new leadership.
                      Deposed window v2
                      The deposed window is the time an old coordinator leader answers before it applies the new-leader metadata.
                      Barrier record v2
                      A barrier record is an empty log record a leader commits before answering out-of-range above its high watermark.
                      Log start Kafka
                      The log start is the earliest coordinator-log offset still retained after enough replicas hold covering snapshots.

The control plane moves into Kafka

Diskless metadata coordinator v2

A presenter’s path through routing, leases, partial commits, deletion safety, failover, and snapshots.

This design removes PostgreSQL from the diskless control-plane deployment. Kafka stores the ordered state, while object storage continues to hold WAL bytes.

The rest of the deck follows one file from routing through upload, commit, failover, and eventual deletion. The key question is always which durable fact makes the next decision safe.

The problemWhy a control plane exists

Object storage holds bytes, but only metadata gives them meaning

A WAL object can contain batches from many user partitions. Consumers still need ordered offsets and byte coordinates before they can read.

Read by offset

Consumers find coordinates, then fetch bytes.

P

PostgreSQL works

It supplies durable shared state, but every broker reaches a separate database cluster.

M

Memory is for tests

It has no external dependency, but restart loses the control-plane state.

Design target: remove the external database without losing any data that a classic Kafka topic keeps through the same failure.

Object storage is deliberately focused: it stores the bytes and serves them by key. It does not know that a batch belongs to orders-7, covers offsets 120–128, or occupies a byte range.

The control plane is the index and the ordering authority. Version 2 keeps the existing control-plane interface while changing where that state lives.

The big ideaKafka becomes the source of truth

A protected internal topic becomes the durable control plane

__diskless_metadata has fixed coordinator partitions. Each leader is the single writer for the user partitions mapped to it, and each replica rebuilds a local SQLite view.

1

Partitioned logs

One unavailable coordinator delays only its mapped user partitions.

2

Replayable state

Records carry assigned values, so replicas do not recompute decisions.

3

Kafka durability

acks=-1, a fixed minimum ISR, and the high watermark gate replies.

The topic is not a generic key-value store. Each coordinator partition is an independent state machine with its own log, leader, SQLite database, snapshots, and overlay.

The leader appends an outcome record, and replicas apply it only after the high watermark passes it. The record contains every assigned value and batch result, so replay reaches the same state on every replica.

The topic is protected because it contains offsets, leases, fences, and the only deletion queue. A normal admin action cannot weaken or remove it.

RoutingInteractive toy 1

A stable hash sends each user partition to one coordinator leader

The protocol hashes a 20-byte user-partition key into 4096 slots, then maps the slot to slot % N. The same rule also pins a broker’s tracking partition.

Partition mapping

Real Kafka Murmur2 over topic ID plus big-endian partition index

One color per coordinator

The log key is exactly the topic ID in most-significant-byte order followed by the partition index as four big-endian bytes. Kafka’s Murmur2 and positive-value conversion produce the slot.

The deck uses a fixed topic ID so the result stays reproducible. The design allows only a power of two for N, and every broker reads that value from the metadata image.

The toy uses four-byte big-endian broker IDs for the tracking hash. The design leaves that broker-ID byte encoding as an implementation item, so this is a presentation assumption rather than a protocol decision.

Why slotsGrowth without a full reshuffle

The 4096-slot layer makes a future doubling bounded

When the coordinator count doubles, each old coordinator keeps half its slots and its new partner takes the other half. The mapping identifies the bounded handoff.

Each coordinator owns every fourth slot.

After: N=8

0123 4567 891011 12131415

Old CP p keeps slots with new remainder p; CP p+4 receives the other half.

Stable protocol

S=4096 is fixed, so brokers agree across versions.

No table to synchronize

A power-of-two N makes the two modulo steps equivalent to modulo N.

Growth remains future work

The mapping bounds the move, but state handoff still needs an explicit procedure.

A plain modulo by the current partition count would move almost every user partition when the count changes. The fixed slot layer turns a future doubling into a split of known slot ranges.

Version 2 keeps the count fixed after topic creation. The deck shows why the protocol reserves a path for growth without pretending that the handoff itself is implemented.

Every part shares the file deadline, but a part’s outcome can remain unknown after that deadline until a later durable event resolves it.

At file close, the broker assigns the pair and deterministic key. That is why the upload can begin without another round trip and why a retry does not create a new object name.

The file fans out only after upload. Each coordinator partition decides its own batches, and the broker merges those per-batch results in the original request order.

A part that reaches its deadline returns KAFKA_STORAGE_ERROR, but its request may still commit later. A later commit, fence, epoch retirement, or lease end closes that unknown-outcome window.

Partial failureInteractive toy 2

Per-partition queues isolate a slow coordinator

A later file waits behind an earlier part only on the same coordinator queue. Healthy queues keep committing while a stuck part reaches its own file deadline.

    The broker used to have one commit thread, so one unavailable coordinator could hold every later file. Version 2 changes the shared caller to keep one ordered queue per commit queue.

    In the toy, F2’s CP0, CP2, and tracking parts can complete while F1’s CP1 part waits. At its own deadline, the part returns KAFKA_STORAGE_ERROR, but the outcome remains unknown until the coordinator’s durable sequence rules resolve it.

    LeasesInteractive toy 3

    Leased ranges remove the round trip before an upload

    The broker leases sequence ranges ahead of time, names each object deterministically, and falls back to another tracking partition when its normal one is unavailable.

    Leases and object keys

    The toy uses K=8; the protocol constant is 1024

    Broker 2 · N=4

      The tracking partition confirms ranges, not individual objects. The broker can therefore close a file, derive its key, and upload immediately.

      The pair orders files by epoch first and sequence second. The broker chooses lease starts above every range requested in the epoch, including a request whose reply was lost, so fallback partitions cannot overlap.

      A restart raises the broker epoch and ends old leases. The toy uses a short range so the renewal and fallback behavior is visible in a few clicks.

      RetriesInteractive toy 4

      The broker row remembers the answer

      Each coordinator partition stores the last result, a separate fenced-through pair, and a retired marker. A retry compares its pair with that durable floor.

      Broker row and acceptance rules

      Try a new pair, retry it before and after apply, then raise the fence

      Broker 2 · one coordinator

        The row’s floor is the higher of the last committed pair and the fenced-through pair. A pair equal to the last commit returns the stored result even after retention removes the batch rows.

        A pair above the floor enters the leader overlay and eventually becomes the new remembered result. Anything below the floor is stale, while a retired row rejects the old epoch.

        Only the tracking partition checks that the sequence belongs to a lease. Participant partitions use the durable floor and fences.

        No two-phase commitPer-part outcomes are enough

        Partial commit is a feature of the existing control-plane contract

        A WAL file can succeed on CP0 and CP2 while CP1 fails. The broker returns the results it knows and retries only the failed user partitions.

        What two-phase commit would add

        • A serial prepare step before the file can finish.
        • A coordinator that must hold every participant open together.
        • A failure mode that blocks healthy partitions behind one unavailable participant.

        What v2 keeps

        • Kafka’s existing per-partition outcome model.
        • One queue and one deadline per coordinator part.
        • Tracking state that keeps the shared object safe across partial success.

        The control-plane contract already returns a result per batch. A non-transactional Kafka produce does not promise atomicity across partitions, so a two-phase protocol would add blocking without preserving a guarantee clients do not have.

        The tracking part is not a prepare record. It records participants and later proves that no participant can still reference the object.

        DeletionInteractive toy 5

        The tracking partition deletes only after releases or fences prove safety

        The tracking partition queues a key only when every participant releases it or a fence proves that participant cannot still reference it. A clock decides only when the queued key is deleted.

        Safe object deletion

        Release CP0 and CP1, make CP2 silent, then resolve its fence

        Grace period 3 ticks

          Participants release an object when an apply removes their last batch. The report is durable and idempotent; a new participant leader resends releases that have no release-accepted record.

          A silent participant cannot be trusted to report, so the tracking partition sends a range fence. The participant answers which sequences it still holds, and only those referenced sequences wait for a later release.

          The grace period protects readers and shrinks the late-upload leak. It never establishes safety. The log position, release state, and fence state do that.

          FailoverInteractive toy 6

          The leader overlay ends at the high watermark

          A leader reserves offsets in memory, but SQLite sees them only after replication. An unreplicated suffix disappears on leader change, and callers retry.

          Leader overlay and high watermark

          Append, replicate, or crash before followers fetch

          Leader A → Leader B

            The overlay lets one writer reserve offsets for later requests without giving followers a speculative view. Followers apply only records at or below the high watermark.

            If an append fails, leadership changes, or a new leader truncates the unreplicated suffix, the overlay entry and every later entry are dropped. Parked replies get retriable errors, so no caller treats speculative state as durable.

            A new leader waits until its high watermark reaches the log end it saw at election before serving. That gate prevents it from answering from an older prefix.

            ReadsInteractive toy 7

            A barrier makes an out-of-range answer truthful

            A current leader answers below its high watermark directly. Above it, the current leader commits a barrier before returning OFFSET_OUT_OF_RANGE; a deposed leader times out with OFFSET_NOT_AVAILABLE.

            Deposed leader and the barrier

            Old high watermark 42 · current high watermark 45 · barrier deadline 500 ms

            Try offset 44, then 50

              A deposed leader serves a committed prefix, which makes stale data lower or unknown. An out-of-range response above its high watermark is different: it can make a consumer reset and skip records committed under the new leader.

              The current leader’s barrier commits in one replication round trip. If the requested offset is still beyond the watermark, the answer is truthful. A barrier from the deposed leader never commits because followers no longer fetch from it, so its 500 ms deadline returns OFFSET_NOT_AVAILABLE.

              The delayed-fetch probe uses a no-wait request and never appends the barrier.

              Local stateInteractive toy 8

              SQLite is a cache of the log, and snapshots move the log start safely

              Each replica stores applied state and its offset in one transaction. The leader advances log start only when its older snapshot and enough in-sync peer reports cover the same prefix.

              Snapshots and log start

              Three replicas · min.insync.replicas=2 · newest plus one older snapshot

              Reports count only in ISR

                The database is a cache, not another source of truth. A power loss can roll back recent SQLite applies together with the applied offset, and replay from the durable log restores them.

                Every replica keeps a newest snapshot and one older snapshot. The leader uses its older snapshot and the highest report from enough other in-sync replicas, so a report from a replica outside the ISR cannot advance log start.

                If no replica has a covering snapshot after log start moves, the coordinator stays unavailable rather than serving partial state. Snapshot transfer uses one snapshot ID so a resumed transfer cannot mix files.

                ProtectionDurability and isolation

                Durability comes from Kafka rules plus a protected topic

                The topic’s settings and request guards close the paths that could resurrect offsets, bypass one-writer ownership, or delete a live object.

                ✓

                Fixed safety settings

                • flush.messages=1
                • acks=-1 for coordinator appends
                • Creation-time minimum ISR
                • No unclean election
                • No time or size retention, no compaction
                • Storage identity filters unsafe leaders
                !

                Requests the topic rejects

                • Client produce, including admin-client bypasses
                • DeleteTopics and client creation
                • CreatePartitions
                • Unclean ElectLeaders
                • Replica-count changes
                • Client DeleteRecords
                Feature gate: a new cluster finalizes the coordinator feature at format time. The configured control-plane class must match; existing PostgreSQL-backed clusters stay on PostgreSQL.

                The internal-topic flag alone does not protect every admin request, so the design adds explicit name-keyed guards with no bypass. The coordinator’s own append origin remains allowed, while client and broker admin paths are rejected.

                flush.messages=1 matters because state spans a tracking partition, participant partitions, and object storage. A lost tail on one side could otherwise queue deletion while another side resurrects a batch reference.

                Storage identity, rather than clean shutdown state, decides whether a returning replica can lead. This prevents a wiped or reformatted directory from winning last-known-leader recovery.

                LifecycleController and coordinator have different jobs

                KRaft owns topic intent, while the coordinator reconciles state asynchronously

                Topic creation and deletion commit to cluster metadata only. The mapped coordinator leader observes that image, appends its own state record, and never makes the controller wait.

                A

                Metadata image

                KRaft records the diskless topic or its deletion.

                B

                Coordinator diff

                The leader compares the image with its SQLite rows and pending overlay.

                C

                Durable record

                Partition creation, topic deletion, initialization, or repair becomes ordered state.

                D

                Readiness gate

                A produce before reconciliation gets a retriable error, not a second writer.

                Same mapping

                Lifecycle records use the same coordinator as commits for that user partition.

                Delete retries itself

                If SQLite still holds a topic ID absent from the metadata image, the next update or election appends topic-deleted. The log record is the retry; no separate queue exists.

                Maintenance stays local

                Retention, purge, prune, and cross-tier reports run at the coordinator that owns the state.

                The controller owns cluster intent and must not block on a coordinator leader. The coordinator turns that intent into an ordered record in the same partition that owns the user partition’s commits.

                That separation also makes deletes retryable. If the coordinator is down when metadata removes a topic, the next metadata update or election presents the deletion again.

                v1 to v2Why the design changed

                Version 2 moves safety from guesses into durable records

                The common pattern is durable ordering: if a fact controls whether an object can be referenced, the log records that fact so every replica can replay it.

                Version 1 problem

                • Per-object intent added a replicated append before every upload.
                • Deletion safety depended on broker clocks.
                • Partial sends could trigger direct broker deletion.
                • Admin paths could weaken the coordinator topic.
                • A deposed leader could return a false out-of-range.
                • Unreadable records could be skipped.
                • A wiped disk could win a last-known-leader election.

                Version 2 decision

                • Leases name keys before upload with no per-object intent.
                • Releases and fences prove when a key cannot be referenced.
                • The tracking queue is the only delete path after a commit may land.
                • Name-keyed guards and fixed configs protect the topic.
                • A committed barrier confirms leadership before out-of-range.
                • Apply stops at a record it cannot read.
                • Storage identity filters unsafe election candidates.

                Version 1 made the upload path pay for an intent record and asked clocks to decide when a key was safe to remove. Those choices added latency and left races around partial commits and failover.

                Version 2 pushes decisions into replayable state: leases, broker rows, fences, barriers, topic guards, and snapshot metadata. The result is not a transaction across coordinator partitions; it is a set of ordered per-part decisions with explicit object tracking.

                BoundariesAccepted risks and open items

                The remaining risks are explicit and bounded

                The design accepts a few failure modes that Kafka or PostgreSQL already expose. Naming the boundary keeps the safety claim precise.

                All replicas lost

                Loss affects the 1/N user partitions mapped to that coordinator, and their WAL objects become orphans. Rack- or zone-aware replication factor 3 makes this unlikely; it does not reduce the affected set.

                Late upload

                Storage can finish an upload after its key is deleted. That leaks storage, not data; the lease bounds a cut-off broker’s remaining files.

                Non-idempotent retry

                A late part can appear after a retry through another broker, as with a classic acks=all timeout.

                Clock skew

                Retention and cleaner grace periods keep Kafka’s existing time exposure. Operators need NTP monitoring.

                Capacity

                SQLite shares heap, page cache, disk, and garbage collection with the broker. Benchmarks decide the deployment shape.

                Open implementation choices include private request names and error codes, the SQLite driver, commit and idle-lease timeouts, broker-ID encoding, overlay size, and append linger.

                These risks do not silently weaken the core invariant. Losing every replica is the same class of loss as losing every replica of a classic Kafka partition, while a late upload produces an orphaned object rather than a missing committed batch.

                The performance and packaging questions remain open by design. The review can decide them with benchmarks and dependency checks without changing the ordering model.

                RecapCarry these rules into review

                Six rules explain the design

                1

                Kafka is the truth

                SQLite accelerates reads and restart, but the coordinator log decides state.

                2

                One writer owns each user partition

                Hashing routes it to one coordinator leader, even when a file spans many leaders.

                3

                Slots make growth bounded

                4096 fixed slots turn a future power-of-two split into a known handoff.

                4

                Pairs make retries deterministic

                Leases, deterministic keys, broker rows, and floors make old pairs stale.

                5

                Fences prove deletion safety

                Releases and fences decide whether a key can still be referenced; the clock only schedules cleanup.

                6

                Barriers protect consumer position

                A current leader proves its view before out-of-range, while a deposed leader returns a retriable answer.

                Availability shape: a coordinator failure stalls its own mapped partitions, not every diskless produce.

                The design is easiest to review by asking which rule covers each failure. Routing covers ownership, pairs cover retries, releases and fences cover objects, and barriers cover the one stale-read case that could make a consumer skip.

                The high watermark ties leader replies to replicated state. The protected topic makes the assumptions durable instead of leaving them to operator discipline.

                GlossaryEnd with shared language

                The vocabulary maps each failure mode to one durable fact

                Coordinator partition
                A partition of __diskless_metadata whose leader writes mapped user-partition state.
                Tracking partition
                The partition that issues leases, records participants, receives releases, and owns the deletion queue.
                Overlay
                A leader’s in-memory view of appended records that have not passed the high watermark.
                Broker row
                Per-uploader epoch, last result, fenced-through pair, and retired marker.
                Floor
                The higher of the last committed pair and the fenced-through pair.
                Fence
                A durable range boundary that makes every lower sequence impossible to commit at a participant.
                Barrier
                A record that a leader commits before answering out-of-range above its high watermark.
                High watermark
                The highest replicated position eligible for state application and a durable reply.
                Questions to carry into implementation review: Which record closes this race? Which replica proves this prefix? Which request is allowed to write this topic?

                These terms are deliberately operational. A coordinator partition owns ordered user state, a tracking partition owns object lifecycle, and the broker row remembers the answer that retries need.

                When a review finds a new race, ask which durable fact resolves it. If the answer is only a wall clock or an external scan, the design boundary needs another look.

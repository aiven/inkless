Inkless design explainer · Status of the design: draft for handoff

The diskless metadata coordinator, explained

Inkless stores the data of diskless topics in object storage. A service called the batch coordinator decides the order of that data. Today that service needs a PostgreSQL database. This design moves the coordinator's state into an internal Kafka topic, with a local SQLite copy on every replica. The rest of this page builds that design up one idea at a time.

Background: diskless topics and the control plane

A diskless topic keeps its records in object storage, such as S3, GCS, or Azure Blob Storage, instead of on broker disks. Kafka has no inter-broker data replication for these topics, because object storage is already durable. Any broker accepts a produce request for any diskless partition, so the data path has no partition leader.

That raises a question classic Kafka never has to answer. If three brokers accept records for orders-0 at the same moment, who decides which record gets offset 120 and which gets 121? Inkless answers it with a central service, the batch coordinator. Step through the produce path to see where it fits.

FigureThe diskless produce and fetch path

The broker talks to the batch coordinator through a Java interface called ControlPlane. Its main methods are:

Two implementations exist. InMemoryControlPlane is for tests and loses everything on restart. PostgresControlPlane is the production backend, and every broker connects to one shared PostgreSQL database. The class is chosen with inkless.control.plane.class.

The problem and the goal

A cluster that wants durable diskless topics has to run and monitor a PostgreSQL database next to Kafka. KIP-1164 proposes a Diskless Coordinator that keeps this state inside Kafka instead. The full KIP adds public protocol, ownership handoff, and orphan scanning. This design takes a minimal subset of it that fits behind the existing ControlPlane interface, so no caller changes.

Goals

  • A third backend, DisklessMetadataControlPlane, selected with inkless.control.plane.class.
  • State in the internal topic __diskless_metadata, split across a fixed number of partitions by a hash.
  • A local SQLite copy on every replica, rebuilt from the log and from snapshots.
  • Every object the design can orphan gets deleted, by one owner.
  • Pass the shared AbstractControlPlaneTest suite and new cluster tests.
  • No public Kafka protocol. New requests use private ApiKeys, 504 and above.

Non-goals

  • Changing the partition count after creation.
  • Moving an object's owner, or a user partition, to another coordinator partition.
  • A scanner that deletes orphan objects.
  • Follower reads, produce gateways, and transaction state.
  • The KIP's public APIs (keys 95 to 101).
  • Migrating existing Postgres clusters. New clusters only.
  • A Raft quorum for this metadata.

The design in one picture

Here is the whole design in five sentences. The rest of the page explains each one.

  1. 1The coordinator's state lives in an internal topic, __diskless_metadata, with N partitions (8 by default). Each partition is a coordinator partition, an independent coordinator with its own leader.
  2. 2Every diskless user partition maps, by a fixed hash, to exactly one coordinator partition. That coordinator partition's leader is the only broker that assigns offsets for it.
  3. 3Every state change is a record appended to the coordinator partition's log. Every replica applies the records, in order, to its own local SQLite database.
  4. 4Replicas take snapshots of SQLite, so the leader can delete old log records without losing the ability to rebuild a replica.
  5. 5A WAL object holds batches for many user partitions, so it touches several coordinator partitions. One of them is its owner, and only the owner deletes it.

Kafka concepts you need

The design reuses ordinary Kafka replication for __diskless_metadata. If you know the following terms, skip ahead.

FigureOne partition's log and its three positions

Replicas and leaders

Each partition has several replicas on different brokers. One is the leader: it takes all writes. The others are followers that fetch from the leader. The in-sync replica set (ISR) is the replicas that are caught up. min.insync.replicas is how many ISR members a write needs.

Offsets that matter

The log end offset (LEO) is the next offset to be written. The high watermark (HW) is the offset up to which every ISR member has the records. A record below the HW survives the loss of any one ISR member. The log start offset is the first offset still on disk. Records below it are deleted.

Leader epoch

Each time a partition gets a new leader, its leader epoch increases. Every record carries the epoch it was written in. A new leader can truncate records that never reached the HW. Comparing offset and epoch tells a replica whether its copy still matches the log.

fsync and KRaft

By default Kafka writes to the operating system's page cache and lets the OS flush to disk later. fsync forces the flush. KRaft is Kafka's metadata quorum. Each broker holds a metadata image: the current topics, partitions, leaders, and ISRs.

The __diskless_metadata topic

The controller creates __diskless_metadata when the feature is first enabled. It places the replicas across racks where it can. The topic's settings are unusual, and each one has a reason:

Why fsync every batch

Replication protects against one broker failing. It doesn't protect against a correlated power loss, where every replica loses power before the OS writes its page cache to disk. For an ordinary topic that loses a few records. For a coordinator partition the damage spreads to every user partition and object it serves. KRaft's own metadata log fsyncs every batch for the same reason. The leader's append linger groups many commits into one batch, so the cost is one fsync per batch, not one per commit.

Mapping user partitions to coordinator partitions

Every broker must agree on which coordinator partition owns a given user partition. If two brokers disagreed, the user partition would have two writers that assign the same offsets. So the mapping is a pure function of the user partition's identity, fixed as part of the protocol.

Three steps

  1. Build the log key: the 16 bytes of the topic ID, most significant bits first, followed by the partition index as 4 big-endian bytes. That's 20 bytes.
  2. Hash it into a slot: slot = Utils.toPositive(Utils.murmur2(logKey)) % S, where S = 4096 is a protocol constant.
  3. Map the slot to a coordinator partition: partition = slot % N, where N is the partition count of __diskless_metadata, read from the metadata image.

The calculator below runs the same murmur2 as Kafka's Utils class, so its results match a real broker.

Because the partition index is part of the log key, the partitions of one topic spread across coordinator partitions. A busy topic doesn't put all its load on one leader.

Why the slot layer, and why a power of two

If N is a power of two, then slot % N equals toPositive(murmur2(logKey)) % N. The slot layer costs nothing at runtime, and brokers store no slot table. So why have it at all?

The slot layer exists for the future. N can't change today, because a different N would move user partitions between coordinators, and that's out of scope. But the mapping is part of the protocol and can't change after release. Fixing slots now keeps one growth path open: doubling N by splitting each coordinator partition in two. When N doubles, partition p keeps half its slots and the new partition p + N takes the other half. Every other slot stays put. Try it.

InteractiveThe 4096 slots

Each square is one slot, colored by the coordinator partition it maps to. Compare growing N by doubling with growing it to an arbitrary number.

Rules that protect the mapping
  • The config accepts only a power of two from 1 to 4096, the slot count. It sets N only when the controller creates the topic. Changing the config later has no effect.
  • The controller rejects CreatePartitions for __diskless_metadata.
  • Every leader recomputes the mapping for each user partition in a request. If one doesn't map to it, the leader rejects the request with INVALID_REQUEST and counts a mismatch. A broker with a different mapping would otherwise create a second writer.
  • A unit test pins the mapping with fixed expected values, so any change fails the build.
  • With N=1, everything maps to partition 0 and the design reduces to a single coordinator.

Records name the log they change with a Log struct that holds TopicId and PartitionIndex. That struct is the record form of the log key. A later log key encoding, such as one for partitionless key ranges, would add a tagged field that older readers skip.

An operator sets diskless.metadata.topic.num.partitions=12. What happens?

The config rejects it, because 12 isn't a power of two. With 12, slot % 12 would no longer equal murmur2 % 12, and a later doubling to 24 would move far more than half of each partition's slots.

Objects span coordinator partitions

__consumer_offsets splits its state by group ID, because each request touches one group. A WAL object is different. A broker fills one object with batches from every partition it received produce requests for, often across many topics. Offsets for each user partition still have to come from one writer.

So the coordinator splits its state by user partition. Each user partition keeps exactly one writer, and a commit goes to every coordinator partition that the object's batches map to. Those coordinator partitions are the object's participants. Build an object and see.

InteractiveBuild a WAL object

Pick the user partitions whose batches went into this object. The mapping is computed with the real hash over fixed example topic IDs. You can also mark coordinator partitions as unavailable.

This split needs no two-phase commit. Kafka doesn't make a non-transactional produce atomic across partitions, and commitFile already returns one result per batch. So a commit can succeed on one coordinator partition and fail on another, the same way a produce request can succeed for some partitions and fail for others.

The only state that spans coordinator partitions is the object itself: does any batch still reference it, and was it ever committed at all? That question gets an answer from one participant, the object's owner. The ownership section covers it in depth. For now, know that the broker picks the preferred owner by hashing the object key over the sorted participant list, and falls back to the next participant if the preferred one is unavailable.

Rejected alternatives for the split
  • Two-phase commit across participants. A non-transactional produce has no cross-partition atomicity to preserve, and the extra round trip would block every commit.
  • One upload per coordinator partition per commit interval. It removes every cross-partition reference, but multiplies object-storage writes by up to N and shrinks each object.
  • Routing produce so each broker writes for one coordinator partition. Clients could no longer produce to any broker, and every availability zone would need a broker for each coordinator partition.

The delegate and private RPCs

Each broker holds a DisklessMetadataControlPlane instance, called the delegate. The rest of the broker calls it like any other ControlPlane. For each call, the delegate:

  1. Maps every user partition in the request to its coordinator partition.
  2. Splits the request into one part per coordinator partition.
  3. Sends the parts in parallel. A part runs locally when this broker leads that coordinator partition. Otherwise it goes over a private RPC to the leader, which the broker finds in its metadata cache.
  4. Merges the results back into the order of the original request, because every ControlPlane method promises results in request order.
FigureSplit, send, and merge

A broker that receives a request for a coordinator partition it doesn't lead answers NOT_COORDINATOR, and the delegate retries against the new leader. Why new RPCs at all? A commit must return the offsets it assigned, and the Produce response has no place for them. The full RPC list is in the reference section. They use private ApiKeys, 504 and above, so no public protocol changes.

Records and deterministic apply

A coordinator partition's log is a sequence of records. The leader appends one outcome record per committed call, or per part of a call. Every replica applies records to its SQLite database in log order, and only up to the high watermark. The determinism rule

RuleApply reads nothing outside its own coordinator partition's log, and it never reads a clock. Every time-based decision is a record that the leader appends.

This rule is what makes every replica reach the same state from the same log, and what lets a snapshot be described by one log position. The panel shows what goes wrong without it.

InteractiveTwo replicas apply the same record at different times

A tombstone was created at 10:00 and expires two hours later. Replica A applies the next records at 11:59:58. Replica B is a little behind and applies them at 12:00:03. The log holds a late commit for the same object key.

The same reasoning covers topic deletion. If each replica dropped a topic's rows when its own metadata image lost the topic, each replica would drop them at a different log position. Instead, KRaft remains the source of intent ("this topic is gone"), and the coordinator leader appends a topic-deleted record that fixes where among the commits the deletion happens. Reconciliation describes how.

The high watermark and the overlay

Two invariants keep replicas safe:

Invariants
  • Every replica applies a record to SQLite only once the record is at or below the high watermark. A replica learns the HW from each fetch response.
  • The applied offset is therefore always at or below the HW, so a leader change that truncates unreplicated records never undoes an applied SQLite row.

That creates a problem for the leader. Replicating a record takes a round trip. During that time more commits arrive for the same user partition, and they need the next offsets. SQLite doesn't have the pending commit yet, because it isn't applied. So the leader keeps an in-memory overlay: records it has reserved or appended but not yet applied. A new commit reads SQLite plus every earlier overlay entry. Followers keep no overlay.

Leader overlay and SQLite

Parked replies and events

The overlay's rules:

  • An overlay entry holds the object key, the assigned offsets, the producer epoch and sequence numbers, and a pending fence or intent when the entry is one.
  • The leader checks and reserves on one thread, so two commits can't receive the same offsets.
  • The leader collects reservations for one append linger interval, then appends them as one log batch. One replication round trip and one fsync cover the whole batch.
  • When the HW passes an entry, the leader applies it to SQLite, removes it from the overlay, and sends the parked reply.
  • If an append fails, the leader resigns, or the log truncates an entry, the leader removes that entry and every entry after it, and fails their parked replies with a retriable error. A later entry took its offsets from an earlier one, so no suffix past a broken entry is valid.
  • The overlay has a cap. Past it, the leader rejects new commits with a retriable error.
  • A new leader starts with an empty overlay.

Running on CoordinatorRuntime

Kafka already has a framework for exactly this loop. CoordinatorRuntime runs the group coordinator and the share coordinator. It supplies the single writer thread, the append linger, the revert to the last committed state after a failed append, the parked replies that complete when the HW moves, and the NOT_COORDINATOR failure on resignation.

The runtime runs one shard per partition of a coordinator topic, as the group coordinator does for __consumer_offsets. Here each coordinator partition is one shard, loaded and unloaded with its leadership. The shard keeps the overlay in timeline structures backed by a SnapshotRegistry, the runtime's mechanism for rolling in-memory state back to a committed point. Committed state stays in SQLite.

Reused from the runtime

  • Single writer thread per shard
  • Append linger and batching
  • Revert after a failed append
  • Parked replies completed by the HW
  • NOT_COORDINATOR on resignation

Written for this design

  • A custom CoordinatorLoader that replays from the applied offset stored in SQLite. The stock loader starts at the log start and would replay records SQLite already holds.
  • A follower applier that writes fetched records to SQLite up to the HW. The runtime runs on the leader only.
Rejected alternatives
  • A write loop written for this coordinator. It would reimplement batching, revert, parked replies, and resignation handling.
  • The full state in CoordinatorRuntime timeline maps. Every election would replay the whole log, and findBatches and listOffsets would scan indexes held on the heap.

The commit path and retries

A commit starts before the upload. The order is:

  1. The broker closes the WAL object and computes its participants.
  2. It stores an intent at the owner. If no participant can store it, the broker uploads nothing and the produce fails with KAFKA_STORAGE_ERROR.
  3. It uploads the object.
  4. It sends one commit part to each participant's leader, in parallel.

Every part carries the object key, the participant set, the owner that stored the intent, and the first-send time: the broker's wall-clock time when the delegate first sent that part. Retries reuse it. Each leader then runs its part through five steps. Change the inputs and see which step decides.

InteractiveWhat one leader does with a commit part

The maximum commit age, diskless.metadata.commit.max.age.ms, is 60 minutes by default (provisional).

Why retries are safe

The broker generates a fresh object key for every upload, so the key identifies the upload. Deduplication runs per coordinator partition, against the overlay and SQLite. Checking SQLite alone wouldn't be enough: a files row exists only after apply, so a retry that arrives during the HW wait would miss it. Because the identity is the file, not the batch, the check also covers producers that aren't idempotent. (The Postgres backend's files insert is a plain INSERT, so a repeated key fails there. The new backend changes that.)

The delegate retries each part on its own, against the current leader, after NOT_COORDINATOR or a retriable error. It reuses the same object key and first-send time, and stops at a commit deadline that doesn't exceed the produce request timeout. The delegate never fences anything. Strict apply rules

The leader's checks make the following cases unreachable, so a replica that meets one treats it as a bug:

  • A file-committed record for a key already applied with identical content is a no-op for file state. The applied offset still advances.
  • A file-committed record for a key already applied with different content, or for a fenced or tombstoned key, is an invariant violation. The replica stops serving that coordinator partition and reports corruption.
  • A file-fenced record for a key already fenced is a no-op. A file-fenced record for a key with an applied commit leaves the commit in place, and its answer is "referenced", naming the owner from that commit.
A retry arrives while the first attempt's record is appended but still above the HW. How many records end up in the log?

One. The leader finds the key in the overlay, appends nothing, and parks the retry on the same entry. When the HW passes the record, both the original and the retry complete with the same offsets.

Owners, participants, and fences

This section answers one question: when is it safe to delete a WAL object from storage? It's the hardest part of the design, because no single coordinator partition sees the whole object. The owner protocol is the only path that deletes an object.

Two different situations leave an object to clean up:

  • A referenced object stops being referenced. Retention, DeleteRecords, topic purge, or consolidation removes the batches that pointed at it, one participant at a time.
  • An object was never fully committed. The broker crashed after the upload, or some commit parts never landed. Without a record of the upload, nothing would ever delete it.

The owner and its entry

  • The participants are the coordinator partitions that the object's batches map to.
  • The preferred owner is the participant at index toPositive(murmur2(objectKeyBytes)) % participants.size() in the sorted participant list. If it can't store the intent (NOT_COORDINATOR, a retriable error, or a timeout), the broker tries the next participants in sorted order. Only the user partitions of an unavailable coordinator partition then fail, not the whole object.
  • The owner is whichever participant stored the intent. Every commit part names it and every record stores it, so no replica recomputes it. It never changes after the commit.
  • The intent creates the owner's entry for the object. The entry tracks each other participant's state as the owner sees it. The owner tracks its own state locally: referenced while its own part holds batches, and released once it holds none.
  • The broker gives up on the upload and the commit once the intent is older than the maximum commit age. A slow upload can't finish after the owner deleted the object, short of storage completing a request the broker already abandoned.
FigureA participant's state, as the owner sees it

A state only moves forward. A delayed answer for a participant that is already released is a no-op.

Releases: the only thing participants report

  • A participant releases an object when apply removes its last batch of that object.
  • The participant's leader sends a release report to the owner named in its part. The broker's scheduler sends and retries it with Kafka's ExponentialBackoff client defaults. The report is idempotent. When the participant is the owner, it records the release locally.
  • When the owner accepts the report, the participant appends an owner-accepted record. A new participant leader resends only the releases without one.
  • When the owner-accepted record applies, the participant deletes its row for the object if the part's first-send time is older than the maximum commit age. Otherwise it keeps a tombstone that rejects any later commit for the key. The next section explains why.

Participants don't report commits. The owner learns about commits only through fences.

Fences: resolving silent participants

A silent participant either holds batches and hasn't released yet, or never committed its part. Only a fence tells the two apart. The owner fences only when doing so can unblock deletion:

When the owner fencesOnce the intent is older than the maximum commit age, and the owner and every participant it has heard from are released, the owner fences the participants that are still silent. Each participant is fenced at most once per object.
  • The age counts from the intent's append time, so a new owner leader needs no extra state to restart the timer.
  • By then the broker has stopped retrying, because it gave up at the same age. A part that still arrives later reaches a fenced partition and is rejected.
  • If the owner's own part hasn't committed when the intent passes the maximum commit age, the owner fences the key on itself and counts as released.
  • A fence is final. A participant that holds a commit for the key answers referenced, naming the owner from its part, and the owner waits for its release report without fencing again. Any other participant records the fence, rejects later commits for the key, and answers released.

Stale owners

Suppose the preferred owner stored the intent, but its reply was lost, so the broker fell back to another participant. Now two partitions hold an intent for the same object. The first one is a stale owner. It finds out from a fence answer that names a different owner, or from its own committed part naming another owner. Either way it appends an owner-entry-dropped record and never deletes the object.

Deletion

  • The owner appends a file-delete-marked record once every participant is released and the intent is older than the maximum commit age.
  • FileCleaner runs on owner leaders only. It deletes the object after the deletion grace period, as it does today, so readers holding cached coordinates can finish.
  • Deleting a missing object counts as success. S3 answers a missing key with success, and the GCS and Azure backends map not-found to success.
  • Storage needs no transactions. It needs a delete by key, and an upload that's never visible as a partial object. S3 PutObject, GCS single-request and resumable uploads, and Azure block blobs all provide that.
When an object leaksAn object leaks only if storage completes an upload after the owner deleted it, or if a bug loses a record. Every object the design itself can orphan has an intent, so its owner resolves it.

Why doesn't the owner fence every silent participant as soon as the intent is older than T?

A fence is useful only if it can unblock deletion. If the owner itself, or a participant that reported "referenced", still holds batches, the object can't be deleted anyway. Waiting means most objects need no fence at all, because every participant releases on its own first.

Which records does the owner rely on to restart its fence timer after a leader change?

Only the intent-registered record. The timer counts from the intent's append time, which is in the log, so a new owner leader recomputes it without extra state.

Tombstones, expiry, and clocks

A late commit part is dangerous after a release. Imagine this order of events: a part commits, DeleteRecords removes its batches, the participant releases, and the owner deletes the object. Then a delayed retry of the original part arrives. Without protection, it would re-add batches that point into a deleted object.

The age check covers most of this window: any part whose first-send time is older than T is rejected. A tombstone covers the rest. When a participant releases within T of the part's first-send time, it keeps a tombstone that rejects any commit for that key.

Tombstones and fences can't live forever, or SQLite would grow with every object the cluster ever deleted. Each one is created after the commit it guards was first sent, so it can go once it's older than 2T. A leader appends a keys-expired record for them, and apply removes them. That bound assumes broker clocks differ by less than T.

A broker clock that runs behind is harmless: its stamps look old, so its parts get rejected sooner. A clock that runs ahead stretches the window in which a late part passes the age check. The metric for parts rejected by the age check shows skew before it gets that large.

Why not a scanner

The obvious alternative is a background scanner: list every object in storage, ask every coordinator partition whether it knows each key, and delete the ones nobody knows. The design rejects this for deleting, and the reason fits in one sentence:

The deciding differenceOwner-based deletion fails toward a leak. A scanner fails toward data loss.

A scanner deletes what the coordinator state doesn't know. If that state is wrong, because a replica rebuilt from a stale snapshot, a restore rolled state back, two clusters share a bucket prefix, or an operator configured the wrong prefix, the scanner deletes live data. That could be a large share of the cluster's data in one pass. The owner deletes only what it recorded and resolved.

Does this still work for merged objects later?

Yes. A merged object that replaces many small WAL objects is a new object with its own intent and owner. Each participant swaps its batch rows for extent rows on its own schedule, with one record, and then releases the old objects through the normal path. No two-phase commit is needed: before the swap readers find the old rows, after it they find the new ones, and both point at valid data for the same offsets. The deletion grace period covers readers holding cached coordinates.

SQLite on every replica

Each replica of a coordinator partition keeps that partition's state in its own SQLite database. A broker that hosts several coordinator partitions keeps one database for each. The database is a cache. The log is the source of truth.

Two different things called WALIn Inkless, a "WAL object" is an uploaded file of produced batches. SQLite also has a "WAL journal mode", where writes go to a write-ahead log file next to the database. They're unrelated. This section uses "WAL mode" only for the SQLite setting.
  • Applied offset and epoch. Each apply stores the applied offset and the leader epoch of that record in the same transaction as the state change. On restart, the replica replays from there.
  • Open check. On open, the replica checks that the log still holds the stored offset and that the record there carries the stored epoch. A flushed log can still be truncated and rewritten by a later leader, so the offset alone doesn't prove SQLite matches the log. KRaft makes the same check for a snapshot's OffsetAndEpoch.
  • WAL mode. A reader doesn't block a writer, so a snapshot backup or a findBatches read doesn't stall applies. The WAL file grows during a long backup and shrinks after it.
  • synchronous=NORMAL. A power loss can roll back the most recent applies, but never corrupts the database. Each rolled-back apply takes its applied offset with it, so the replica replays from the log, which flush.messages=1 keeps durable. synchronous=FULL would add a second fsync to the leader's reply path.
  • Schema. Tables for logs, files, batches, producer state, owner entries, participant states, tombstones and fences, and the applied offset. The layout is the implementer's choice, but it needs indexed lookup by partition and offset, and by object key.
  • Extents. A coordinate row must be able to describe an extent: an offset range mapped to an object and byte range, with optional producer fields. This effort writes only WAL batch rows, but the requirement keeps merged objects possible later.

Snapshots and the log start

The coordinator topic has unlimited retention, so without help its log would grow forever. Snapshots solve that. A replica that keeps up with the log never needs another replica's snapshot. Snapshots exist so the leader can delete the log prefix, and snapshot transfer exists for the replica that needs records the leader deleted. Each coordinator partition runs these rules on its own.

Taking a snapshot

  • Every replica takes its own snapshot from its own applied state, when diskless.metadata.snapshot.interval.ms (1 hour) elapses or diskless.metadata.snapshot.max.bytes.between.snapshots (1 GiB) of log has been applied since the last one, whichever comes first. The trigger counts bytes because one file-committed record can carry hundreds of batches. Both defaults are provisional.
  • The SQLite backup API writes a point-in-time copy to a temporary file. The snapshot's offset and epoch come from the applied-offset row inside the finished copy. A tag read from the live database before the backup could be too low, and one read after could be too high, which would let the leader delete records the copy doesn't contain.
  • Each replica keeps exactly two snapshots: the newest and one older. That count is a constant, because the log-start rule depends on the pair.
  • Snapshots stay on the broker's disk. They never go to object storage, so failover works while object storage is unavailable.
FigureWriting and rotating a snapshot, with a crash at any step

Advancing the log start

The log start is Kafka's own log start offset for the coordinator partition. Only the leader advances it, with maybeIncrementLogStartOffset, the call the DeleteRecords path uses. Followers adopt it from fetch responses. Kafka refuses a log start above the HW.

The log-start ruleThe leader advances the log start only to an offset that at least min.insync.replicas in-sync replicas, the leader included, hold a covering snapshot for. The new log start is the lower of:
  • the offset of the leader's own older snapshot, and
  • the highest offset that at least min.insync.replicas - 1 other in-sync replicas have reported a snapshot at or beyond.
With a single replica, the leader uses its older snapshot alone.

A snapshot at offset s covers log start L when s ≥ L: a replica can load the snapshot and replay every record after s, because those records are still in the log.

InteractiveLog-start calculator

Each replica holds two snapshots. Followers report their newest snapshot to the leader. Drag the offsets, change ISR membership, and see where the leader may move the log start. The HW is at 1000.

  • Why the older snapshot? At its next rotation the leader deletes its older snapshot and keeps its current newest one, which is at or above the old one. Using the older snapshot as the bound means the snapshot the leader keeps after rotating still covers the log start.
  • Why only in-sync reports? A report counts only while its replica is in the leader's committed ISR with no pending removal. When a replica leaves the ISR, the leader drops its report, because the replica may have lost its files while it was out.
  • No waiting on the hot path. The rule delays log-start advancement only. Produce and fetch never wait on a snapshot report.
  • Before the first advancement the log start stays at 0. A replica that loses its database replays from 0 and needs no snapshot, so a new cluster has no unavailability window.

Reporting snapshots

A replica reports its newest snapshot offset to the leader on a private request after it finishes a snapshot, when it sees a new leader, and when it rejoins the ISR. The broker's scheduler sends the report, with ExponentialBackoff (100 ms initial, 1 s maximum, multiplier 2, 20% jitter). The replica fetcher thread never sends it, because a report blocked on an unresponsive leader would stall fetching and push the follower out of the ISR.

Fetching a snapshot

A replica fetches a peer's snapshot only when it needs records below the log start: it starts empty (a replaced broker or a reassignment), its database is lost or corrupt and its own snapshots don't reach the log start, or it was out of the ISR while the log start moved past its newest snapshot. The protocol follows KRaft's FetchSnapshot (KIP-630), carried on a private RPC because a normal topic has no FetchSnapshot.

FigureA replaced broker rebuilds its replica
  • Follower first. The receiver asks an in-sync follower with a covering snapshot, and the leader only when no follower has one. The leader already carries every commit and cache-miss read.
  • Named transfers. Every request names the snapshot ID (offset and epoch) and a byte position, so a resume never splices bytes from two snapshots. Rotation keeps a file while its transfer is active, until diskless.metadata.snapshot.transfer.idle.timeout.ms (60 s) passes with no chunk request.
  • Chunks. At most 8 MiB, KRaft's MAX_FETCH_SIZE_BYTES, sent from the file with zero copy through a records-typed field.
  • Concurrency limit. A broker serves at most diskless.metadata.snapshot.max.concurrent.transfers (1) transfers across all its coordinator partitions. More get a retriable busy error, and the receiver tries the next source.
  • Serving while broken. A replica serves its finished snapshot files whatever the state of its live database, and stops only when a file fails its checksum. Two replicas that both need a rebuild can serve each other.
  • Rebuild before serving. A replica whose database fails the open check, or whose applied offset is ahead of its log, rebuilds before it serves, and that includes a newly elected leader. If no replica holds a covering snapshot, the coordinator partition stays unavailable rather than serve partial state. How such a leader gives up leadership of one partition is an open item.

Reads

Only the leader answers reads. findBatches, listOffsets, and every other call go to the leader of each user partition's coordinator partition, which serves them from state that includes every committed record. Brokers absorb most fetch-side lookups in the existing batch coordinate cache. A cache miss goes to the leader. Follower reads are out of scope.

findBatches takes a fetchMaxBytes budget that applies across the whole request. The delegate can't know in advance how to divide it between parts, so it sends the full budget with each part, merges the results in request order, and trims the merged list to the budget. The results are coordinates, not data, so the extra rows cost little.

Leader change

Each coordinator partition changes leader on its own. A leader change stalls only that partition's commit parts, intents, reads, and owned objects. Everything else keeps working.

  • The HW gate. A new leader starts with an empty overlay and rejects requests with a retriable error until its HW reaches the log end offset it saw at election. Until then it might not hold every committed record, so a strict read could be wrong.
  • Truncated records. Records that never reached the HW under the old leader may be truncated. Their requests were never acknowledged, so the retry rule covers them. Because the applied offset never exceeds the HW, no SQLite row is undone.
  • Retries. The delegate retries against the new leader with the same object key and first-send time, until the commit deadline.
  • Ownership timers. A new owner leader restarts its fence timers from the intents' append times. A new participant leader resends the releases that have no owner-accepted record.
  • Rebuild first. A new leader with a missing or corrupt database rebuilds from a peer's snapshot before its gate opens.

The replication playground lets you crash a leader and watch the gate, the truncation, and the overlay reset.

Topic lifecycle and reconciliation

Today, ControllerApis.createTopicsDiskless and the diskless delete path call the control plane directly, with a ten-second metadata wait on the request thread. In this design the controller never calls the coordinator. Creating or deleting a diskless topic commits to cluster metadata only.

Each coordinator partition's leader then reconciles. On election and on every metadata update from BrokerMetadataPublisher.onMetadataUpdate, it compares two sets:

  • The diskless user partitions in the metadata image that map to its coordinator partition.
  • The user partitions in its SQLite, plus pending overlay entries.

For each mapped partition in the image that the coordinator doesn't hold, it appends a partition-created record. For each topic ID the coordinator holds that the image no longer has, it appends a topic-deleted record. The metadata log is the retry record: a leader that was down catches up when it returns, so the coordinator keeps no separate queue.

InteractiveReconciliation on coordinator partition 2

Toggle topics in the metadata image (what KRaft says exists). Then reconcile, and apply the records once the HW passes them. Try reconciling twice before applying.

  • Why diff by topic ID instead of reading deletes from the delta? A broker that loads a metadata snapshot never sees a delete event for a topic it didn't hold. Diffing the full image catches every case. It also means a topic recreated under the same name is a new ID and doesn't collide with the one being deleted.
  • Double guard. The diff counts pending overlay entries, and apply is idempotent as well: a repeated partition-created or topic-deleted record is a no-op, though the applied offset still advances.
  • Different coordinator partitions, different times. The partitions of one topic map to several coordinator partitions, so each creates or deletes its share at slightly different moments. KRaft already stops produce to a deleted topic at the broker. A produce to a partition the leader hasn't reconciled yet gets a retriable error.
  • The classic-to-diskless switch. ControllerApis.handleInitDisklessLogRequest writes the seal into cluster metadata. Later, InitDisklessLogManager on the partition leader calls initDisklessLog. The same partition leader calls repairDisklessLog from ReplicaManager.
  • Ordering. A user partition's create, delete, initialization, and repair go to the same coordinator partition as its commits, so they're ordered with every commit to that user partition. Ordering across user partitions isn't guaranteed, and nothing depends on it.

Maintenance, consolidation, and cross-tier offsets

Runs on each coordinator leader

  • Retention for its own user partitions. Each run appends its outcome records.
  • Topic purge in capped passes, as purge_deleted_logs_v1 does in Postgres. Each pass appends one deleted-log-purged record per partition it touched, in one batch. Apply removes batches below the boundary, or all of them, and drops the log and producer-state rows when the partition is empty. Objects that lose their last local batch are released and reported to their owners.
  • Expiry of tombstones and fences, through keys-expired records.

Runs on owner leaders only

  • File deletion marking, once every participant is released.
  • Object deletion by FileCleaner, after the deletion grace period.

Consolidation and cross-tier offsets

For a consolidated topic, the broker that hosts a partition's local log decides how far the diskless log can be pruned, from highestOffsetInRemoteStorage and the classic-to-diskless seal. The coordinator leader never reads a partition log, so it doesn't need to host one.

  1. The hosting broker decides the safe prune offset.
  2. It sends pruneDisklessLogs or advanceCrossTierLogStartOffset to the leader.
  3. The leader appends the outcome record.
  4. The broker advances its own prune floor only from the leader's response.

CrossTierLogStartReporter and the delete-records path follow the same pattern.

Capacity and isolation: the open risk

Status: openHow serious this risk is stays unknown until benchmarks run against the Postgres backend. The results can change the design.

Each coordinator leader serves every commit part, intent, release report, cache-miss read, and maintenance job for its user partitions and owned objects, on top of the broker's own partitions. Two effects pull in opposite directions:

Cheaper per call

SQLite runs in the broker process: no network round trip, connection pool, or remote query planning. The Postgres backend spends part of its commit latency on those.

Co-tenancy

SQLite shares the broker's heap, page cache, disk, and garbage collector. A large findBatches scan can evict the broker's log pages. A GC pause on one broker stalls every commit that has a part on the coordinator partitions it leads, and with most objects spanning most coordinator partitions, that's most commits.

Splitting reduces the work per batch, but not the number of commit calls. An object usually holds batches for most coordinator partitions, so each leader still gets about one commit part per broker per commit interval. A produce waits for the intent and then for its slowest part, so the latency tail grows with N. A cluster-wide consumer restart empties every broker's batch coordinate cache at once, and every miss reaches the leaders together.

Planned benchmarks (Postgres backend compared with this backend, at N=1 and N=8)
  • Commit throughput: the commit rate at which P99 FileCommitTime doubles, including the fsync cost.
  • Partition count: fixed commit rate at N of 1, 4, 8, and 16. Confirms or replaces the default of 8.
  • Intent cost: latency the intent adds to each produce.
  • Partial failure: one coordinator partition offline under load, with owner fallback on and off.
  • Read-heavy load and cache storm: lagging consumers and an all-consumer restart.
  • Co-tenancy: a heavily loaded leader broker compared with one that leads nothing.
  • State size: growing row counts across orders of magnitude, with consolidated topics.
  • Failover and snapshot transfer under load.

Results decide whether the coordinator needs a separate SQLite disk, a findBatches result cap, a higher concurrent-transfer default, a different partition count, a lower maximum commit age, or a return to Kafka's default flush.

Rollout

  • A new cluster finalizes the coordinator feature at format time, with kafka-storage format --feature. The coordinator is active from the first startup.
  • The controller creates __diskless_metadata with the configured partition count, and rejects CreatePartitions for it afterward.
  • The controller rejects registration from a broker that doesn't support the finalized feature.
  • inkless.control.plane.class must name the new class. If it names the in-memory or Postgres class while the feature is finalized, the broker refuses to start.
  • Diskless topics still need the existing Inkless storage configuration and diskless.enable=true.
  • There's no rollback onto Postgres, and no migration. Clusters already on Postgres are never formatted with the feature and stay on Postgres.

Metrics and testing

Metrics

These metrics show whether the owner mechanism resolves every object and keeps state bounded:

  • Unknown-outcome parts per coordinator partition: parts that reached the commit deadline unconfirmed.
  • Open owner entries per owner, and the age of the oldest. An old entry with unanswered fences points to a stuck resolution.
  • Fences by answer: referenced, released, or owned elsewhere.
  • Tombstones and fences held per coordinator partition.
  • Parts rejected by the age check. A nonzero rate points to a stuck request path or clock skew.
  • Mapping mismatches: requests rejected with INVALID_REQUEST.

Testing

  1. The shared suite. AbstractControlPlaneTest runs against the new backend at N=1 and N=8. One broker leads every coordinator partition, so the second run covers splitting, merging, intents, and releases.
  2. Multi-broker cluster tests with KafkaClusterTestKit: failover mid-commit, truncation, pending retries, partial commits, owner fallback, lost intent replies, broker stops between intent, upload, and commit, the age check, tombstones, owner leader change, snapshots, rebuilds, the log-start rule, purge, reconciliation while a leader is down, and the format-time gate.
  3. Fault injection on the client side of the private RPC: drop a reply after append, drop an intent reply, delay a request during catch-up, and stop a broker between steps.

Unit tests pin the mapping and the preferred-owner choice with fixed values. Snapshot writing, rotation, and transfer get unit tests with a fault hook at each step. Apply rules get unit tests at the replica state layer, the one deliberate internal seam, because no public call can produce a duplicate or conflicting record.

Future work and open items

None of these items is part of this spec. Each depends on a decision the spec makes and must keep intact.

Grow by splitting partitions

Doubling N moves half of partition p's slots to p + N. It needs a handoff of each moved slot's logs, batches, and producer state, owner entries that stay correct, and a stored slot table once a slot's owner is no longer slot % N.

Merge WAL objects into extents

A merged object gets its own intent. Each participant appends a record that swaps batch rows for extent rows, then releases the old objects. Needs a swap record type and extent-to-BatchInfo conversion.

Tiered metadata in the coordinator

Remote log segment metadata for a diskless partition would live in the same coordinator partition as its batches, behind a composite RemoteLogMetadataManager. Constraint kept now: same log key, and pruning decided on the hosting broker.

Partitionless key ranges

A log covering a key range gets a second log key encoding, as a tagged field on the Log struct. If a parent range and its children map to one coordinator partition, a split is ordered with their commits.

Open items for the implementer

None of these change the design:

  • Names and ApiKey numbers of the private requests.
  • Error codes for a busy snapshot source and an age-check rejection.
  • Feature flag name and metadata version.
  • Deletion grace period default for FileCleaner.
  • SQLite driver choice, license, and packaging.
  • How a leader that can't rebuild gives up leadership of one coordinator partition. Until a controller request exists, it marks only that partition offline.
  • Commit deadline default (at most the produce request timeout).
  • How often leaders append keys-expired records.
  • The overlay cap.
  • The append linger default.

One item can change the design: the benchmark workloads, scales, and pass criteria described under capacity.

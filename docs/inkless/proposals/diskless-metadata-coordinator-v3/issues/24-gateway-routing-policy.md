# Routing policy for clients a gateway can't serve

Type: grilling
Status: closed
Assignee: viktor.somogyi-vass
Blocked by: 20

## Question

Which clients and topics does the broker route to gateways, and what does a broker do with a produce for a coordinator partition it isn't a gateway for?

[Routing produce by coordinator partition](20-gateway-routing.md) found that routing can reach every diskless client, but some topics and failures keep sending produce to a broker that isn't a gateway. The facts are in [the routing research](../research/gateway-routing.md).

Settle these points:

- Remote-storage topics and switched partitions with a local classic prefix route only to replicas, because their fetches read a local log. Either keep replica-only routing and accept their misroutes for good, or align replica placement with coordinator partitions, which changes controller placement.
- Clients without `diskless_az` get a rewritten `LeaderId` today, hashed over all brokers. Either route them to a gateway in any rack, or keep today's hash.
- A live old gateway keeps receiving produce for up to `metadata.max.age.ms`, 5 minutes by default. Choose one: accept the window, recommend a lower `metadata.max.age.ms`, or have a broker that isn't a gateway answer with an error that makes the client refresh, at the cost of one retry per misroute.
- When routing turns on: only with the coordinator backend and once `__diskless_metadata` exists. [Gateway assignment](21-gateway-assignment.md) settled controlled shutdown: a broker in controlled shutdown stays a candidate until the controller fences it.
- Managed partitions without remote storage: today's transformer prefers replicas in the client's AZ. [Gateway assignment](21-gateway-assignment.md)'s fallback order drops that preference on the gateway path. The routing research found that safe, because diskless produce has no replica check and these fetches don't read a local log. Confirm or keep the preference.
- A fenced broker that clients can still reach, for example one cut off from the controller: the assignment drops it at the fence, but clients with open connections keep producing to it until they refresh. The routing research couldn't confirm whether `AppendHandler` refuses diskless produce on a fenced broker.

Named test: a produce that reaches a broker that isn't a gateway behaves as the chosen policy says, and still commits if the policy accepts it.

## Working notes

Terms used in this ticket, as [Gateway assignment](21-gateway-assignment.md) defines them:

- Gateway: a broker that routing sends one rack's clients to for a coordinator partition's user partitions. It accepts their produce, uploads the WAL file, and sends a commit part to the coordinator partition's leader. It holds no coordinator state.
- Coordinator leader: the leader of a `__diskless_metadata` partition. It assigns offsets, appends and replicates the commit record, and is the only broker that can commit a part. Being a gateway and being a coordinator leader are independent.
- Replica-only routing: the transformer picks the `LeaderId` only from the partition's assigned replicas, as it does today for topics with remote storage and for switched partitions whose classic prefix is only on local disks.
- Misroute: a batch that reaches a broker that isn't a gateway of its coordinator partition in the broker's own rack.

Facts checked in code before grilling:

- Consolidation, `diskless.remote.storage.consolidation.enable`, defaults to `false`. With it on, creating a diskless topic also enables remote storage ([FEATURES.md](../../../docs/inkless/FEATURES.md), `CREATE_TOPICS`), so every new diskless topic takes replica-only routing.
- `consolidationActiveFor` is a topic-level check (`ReplicaManager.scala:538`), so it's true on every broker. A broker that isn't a replica answers every fetch for a consolidating partition with the `getPartitionOrError` error (`ReplicaManager.scala:2718`, `:2808`).
- `ListOffsets` for a consolidating partition with a specific timestamp tries the local log first (`DisklessFetchOffsetRouter.scala:157-159`). Consumers send `ListOffsets` to the leader, never to a preferred read replica.
- A consumer follows a `preferredReadReplica` from any broker that returns one and keeps it for `metadata.max.age.ms` (`kafka:clients/.../FetchCollector.java:308-314`, `AbstractFetch.java:371-388`).
- Managed replicas without remote storage are metadata-only. They give deterministic placement and leadership, and no local data ([FEATURES.md](../../../docs/inkless/FEATURES.md), Managed Replicas).
- Diskless produce has no fencing check. `ReplicaManager.appendRecords` sends diskless entries to `AppendHandler` (`ReplicaManager.scala:1013-1014`), and `AppendHandler` checks only transactional batches and `ControlPlaneAvailability` (`AppendHandler.java:100-117`). `ControlPlaneAvailability` tracks whether the control-plane delegate is configured and built, not the broker's fencing state.
- v2's coordinator doesn't reject a fenced uploader, so a short heartbeat gap doesn't fail commits in flight ([v2 design](../../diskless-metadata-coordinator-v2/design.md), Commit path step 2).
- A running broker ignores `isFenced` in heartbeat responses (`kafka:server/.../BrokerLifecycleManager.java:674-677`). After the first unfence, the controller fences a running broker only on a session timeout (`maybeFenceOneStaleBroker`) or a shutdown, and it unfences the broker at its next heartbeat that's caught up (`kafka:metadata/.../BrokerHeartbeatManager.java:409-430`). A KRaft broker fetches metadata from the quorum leader, which is the active controller, so a broker cut off from the controller doesn't see its own fence in its image.
- A starting broker opens its client sockets only after the controller unfences it (`kafka:core/.../BrokerServer.scala:621-638`), so clients never reach a broker that is fenced at startup.

- For data older than `fetch.lagging.consumer.threshold.ms`, the diskless read path skips the cache and reads object storage on any broker (`FetchPlanner.java:239-246`, `:332-355`). By default that threshold follows the 60-second cache lifespan (`InklessConfig.java:97`, `:244`). For a partition without a local log, a catch-up read costs the same on every broker.
- Production read sources, from [Consumer read sources on consolidation services](../research/24-consolidation-read-share.md): on the two services with consolidation on, local-log reads are 0.035% and 0.00014% of `BytesOut`, the remote tier serves nothing, and the object cache serves 99.1% and 99.999% of consumer bytes. Catch-up reads are too small to measure there, and they're 0% to 7.4% of requests on five diskless services without consolidation. Tail reads of a consolidating partition sit above the replica's local log end, so `fetchMessages` sends them to the diskless path (`ReplicaManager.scala:2805-2806`). Both consolidation services are small, so a replay-heavy workload could look different.

Upstream direction, from the grilling session:

- Consolidation and the classic-to-diskless switch are Inkless-specific. Upstream plans a merge framework that combines WAL segments into larger objects holding one or a few partitions' data, in the same object storage and the same format as WAL segments. Any broker reads them the way it reads WAL files, so upstream reads never need a broker-local log. An upstream switch isn't planned, but a classic prefix on local disks would need replica routing while it lasts, as Inkless phase 1 does.

Settled during grilling, before the resolution:

- Local-log partitions: every diskless partition routes to gateways, except a partition whose fetches need a broker-local log. Such a local-log partition keeps the implementation's replica routing. The design states this rule without naming Inkless mechanisms. Upstream, the merge framework writes merged data in the WAL format to the same object storage, so no partition needs a local log and gateways reach every diskless partition. A future upstream switch would fall under the exception only while a classic prefix sits on local disks. In Inkless, consolidating partitions, tiered partitions, and phase-1 switched partitions are local-log partitions: a broker that isn't a replica refuses every fetch for a consolidating partition (`ReplicaManager.scala:538`, `:2808`).
  - Cost in Inkless: replica-only traffic spreads over all `N` coordinator partitions, so it adds parts even to a gateway's files. With `k` local-log partitions in a file at `N=8`, a gateway's file sends `1 + 7 × (1 − (7/8)^k)` parts: 1.9 at `k=1`, 2.6 at 2, 3.9 at 4, 4.9 at 6, 5.6 at 8, 7.2 at 16, and 8.0 at 64. With consolidation on, every new diskless topic gets remote storage, so every file sends about 8 parts and gateways save nothing. In a mixed cluster with 10% of traffic on consolidating topics, about 6 such partitions per broker at 64 per broker give about 4.9 parts per file instead of 1.
  - Example: in the 24-broker cluster of [Tracking part under gateways](22-tracking-part-under-gateways.md), rack 0's brokers 1, 4, 7, 10, 13, 16, 19, and 22 are the gateways of coordinator partitions 0, 6, 1, 4, 2, 3, 7, and 5. `orders-17` maps to coordinator partition 4, with replicas on brokers 7, 11, and 15. Upstream, a rack-0 producer and consumer both reach broker 10, its file sends 1 part, and the consumer reads recent batches from broker 10's upload cache and older ones from merged objects. In Inkless with `orders-17` consolidating, both reach replica 7, and broker 7's files send 8 parts.
  - Meter: the commit-parts meter from [Gateway assignment](21-gateway-assignment.md) and [Tracking part under gateways](22-tracking-part-under-gateways.md) gets a fourth value, `off-gateway`, for a part whose batches all belong to partitions kept off gateways. A part with any batch on the gateway path keeps ticket 21's `routed` or `misrouted` rule. Without it, parts per file from the meter undercount by every local-log part. The name describes the routing decision, not an Inkless mechanism.
  - Effect on [Tracking part under gateways](22-tracking-part-under-gateways.md): local-log traffic spreads over all coordinator partitions, so it never creates the steady traffic for one coordinator partition that the traffic-following future work would act on. A broker that carries it rarely sends an empty tracking part.
- Per-read rule, which amends the local-log decision above: the design routes every diskless partition to gateways and sends only a read that a replica alone can serve to a replica, the one today's replica routing picks. The mechanisms are named:
  - Fetch: the gateway answers with KIP-392's `preferredReadReplica` and no records. The field exists from fetch version 11, is non-ignorable (`kafka:clients/src/main/resources/common/message/FetchResponse.json:113`), and the Java consumer honors it from any broker for `metadata.max.age.ms` without `client.rack`. For fetch versions 4 to 10, which brokers still accept, the gateway forwards the fetch to the replica, because an error would leave the client stuck: a metadata refresh returns the gateway again.
  - `ListOffsets` and `OffsetForLeaderEpoch`: the gateway forwards them to the replica, as Inkless forwards `DeleteRecords` (`KafkaApis.scala:1619-1641`). Neither response has a redirect field, and consumers send both to the leader.
  - Trigger: a read below the WAL start, the first offset still in the diskless WAL, and the lookups that need the local log or the tiered index (`EARLIEST_LOCAL`, `LATEST_TIERED`, timestamps below the WAL start, and epoch lookups on switched partitions). A catch-up read inside the WAL stays on the gateway and takes the cold path.
  - Cost: a redirect costs the consumer one extra round trip per partition per `metadata.max.age.ms` while it reads below the WAL start. Forwarding every fetch would cost no client round trip but add a broker hop to every response and push its bytes through the gateway.
  - Upstream, no read qualifies, because merged objects use the WAL format. A future upstream switch would qualify for its classic prefix. A partition whose recent data only a local log holds, as in Inkless phase 1, keeps replica routing for all requests.
  - Inkless in v3 keeps per-partition replica routing for consolidating and tiered partitions, so the cost figures under the local-log decision stay true for v3. The implementation is future work, and the design states the gap.
  - Why per read: tail reads of a consolidating partition land above the replica's local log end and come from the diskless path (`ReplicaManager.scala:2805-2806`). On the two consolidation services in [Consumer read sources on consolidation services](../research/24-consolidation-read-share.md), local-log reads are 0.035% and 0.00014% of `BytesOut`, and the remote tier serves nothing. A per-partition rule would give up the gateway saving for every produce to protect those reads.
  - Example: `orders-17` is consolidating, in coordinator partition 4, with replicas on brokers 7, 11, and 15. The remote tier holds offsets 0 to 1,190,000, the WAL start is 1,200,000, the log end is 1,250,000, and replica 7's local log holds 900,000 to 1,249,000. Under the rule, a rack-0 producer and a tail consumer at 1,249,500 reach broker 10, the gateway, and its file sends 1 part instead of about 8. A catch-up read at 1,220,000 stays on broker 10 on the cold path. A read at 1,000,000 gets `preferredReadReplica=7`, and the consumer reads from broker 7 for 5 minutes. A `ListOffsets` by timestamp below the WAL start is forwarded to broker 7.
  - Unverified: whether clients other than the Java client honor `preferredReadReplica`. A version-11 client that ignores it gets empty fetches below the WAL start.
- Unknown client AZ: the transformer treats a client whose AZ resolves to `null` as a client of the rack-less group from [Gateway assignment](21-gateway-assignment.md), and the fallback order runs unchanged. A client resolves to `null` when its client ID has no `diskless_az`, its listener has no AZ mapping, or its AZ string matches no rack (`InklessTopicMetadataTransformer.java:461-475`, `ClientAZExtractor.java:42-76`).
  - Behavior: in a cluster with no racks, every broker is in the rack-less group, so step 1 picks a gateway. In a mixed cluster, the rack-less brokers serve these clients first, as ticket 21 already assumed. When every broker has a rack, steps 1 and 2 match nothing, and step 3 picks the gateway of the coordinator partition with the highest `hash(logKey, brokerId)` across racks, so the producer and consumer of a user partition reach one broker.
  - Why: without the client's AZ, no rule can lower cross-AZ bytes. With 3 racks, about 2 picks in 3 cross an AZ under today's hash and under this rule alike. The rule only decides whether the pick already sends a part for the coordinator partition. Today's hash over all brokers lands on a broker that isn't a gateway of the partition's coordinator partition in its rack for 67% of user partitions at 3 per rack, 88% at 8, 93% at 15, and 87% at 16, measured over 2,048 user partitions with the capped rule from [22-tracking-sim.py](../research/22-tracking-sim.py).
  - Example: in the 24-broker cluster, coordinator partition 4's gateways are broker 10 in rack 0, broker 14 in rack 1, and broker 15 in rack 2. An unknown-AZ producer and consumer of `payments-5` reach the one of 10, 14, and 15 with the highest log-key rendezvous, and its file sends no extra part.
- Produce at a broker that isn't a gateway: the broker rejects a misrouted batch with `NOT_LEADER_OR_FOLLOWER`, at most once per connection and partition per `metadata.max.age.ms`, and accepts and commits it otherwise. The test is the misroute test from [Gateway assignment](21-gateway-assignment.md): the receiving broker isn't a gateway of the batch's coordinator partition in its own rack, or own group for a rack-less broker. The rejection applies only to user partitions on the gateway path, never to partitions on replica routing, and never with the gateway switch off. Fetches are always served. Other partitions in the same produce request commit as usual.
  - Why: diskless produce never answers `NOT_LEADER_OR_FOLLOWER`, so a client keeps sending to a live broker that lost a gateway slot until `metadata.max.age.ms`, 5 minutes by default. `NOT_LEADER_OR_FOLLOWER` is an `InvalidMetadataException`, so the producer refreshes at once and retries (`kafka:clients/.../Sender.java:713-730`). Its KIP-951 hint applies only to a newer leader epoch, and the transformer keeps the controller's epoch, so the client does a full refresh. The broker rejects before writing, so idempotent sequences stay intact. A crash or controlled shutdown drops connections, so the stale window follows only moves away from a live broker: a return taking slots back from stand-ins, extra moves among live brokers, joins, and exclusions.
  - Numbers: stale slot moves per rolling restart, averaged over 200 random clusters at `N=8` with 3 racks, are 29 at 3 per rack, 43 at 4, 130 at 8, 43 at 10, 32 at 15, and 450 at 16. The peaks at 8 and 16 come from the cap and `g` changing when one broker is fenced. In the 24-broker example cluster, 116 stale moves at 4 files per second per broker and up to 1,200 extra parts each give up to about 139,000 extra parts per rolling restart, against about 138,000 routed parts in the 24 minutes it takes at 60 seconds per broker. With the rejection, each producer of a moved coordinator partition in that rack pays one retry backoff, 100 ms by default, plus a metadata round trip, and the extra parts drop to a few per move.
  - The guard: a broker rejects a partition on a connection at most once per `metadata.max.age.ms`, then accepts. So every false positive costs one retry and then commits, which keeps the map's rule that a produce reaching any broker commits. False positives come from step 2 or 4 of the fallback order, image skew between brokers, and a rolling upgrade that changes the rule, where a client could refresh from a broker that disagrees. The state is a map per connection from partition to time of the last rejection. `KafkaApis` passes the connection ID to the produce path, an edit in an interleaved upstream file. The misrouted meters count the batch on the rejection and again if it's accepted later, so the spec defines the meter on accepted batches only and adds a rejection count.
  - Effect on [Tracking part under gateways](22-tracking-part-under-gateways.md): stale traffic now ends within one retry, so the first-empty-part trigger makes about the same switches as a switch on the image change, plus 2 to 4 empty parts per change. Its cost bound doesn't change, and most of its savings go, about 90 switches, 1,600 records, and 720 range fences per rolling restart of 24 brokers, against about 139,000 parts the rejection saves.
- A fenced broker that clients can still reach: diskless produce gets no fencing check, as in v2, where the coordinator doesn't reject a fenced uploader. The broker's own image decides.
  - Why: after its first unfence, the controller fences a running broker only on a missed session (9 seconds by default) or a shutdown, and starting brokers open sockets only after the unfence (`BrokerServer.scala:621-638`). A missed session has three causes. If the broker paused or the controller processed its heartbeats late, the broker applies its own fence record. It isn't in its own candidate set, so decision 5 rejects its first batch per connection and partition, its own metadata answers name the stand-in, and its next heartbeat unfences it about 2 seconds later. If the broker is cut off from the controller, its image never shows the fence, because a running broker ignores `isFenced` in heartbeat responses (`BrokerLifecycleManager.java:674-677`). It keeps counting itself the gateway and commits produce while it reaches the coordinator leaders. Any broker commits any produce, so that window costs extra parts and loses nothing. If it can't reach the coordinator leaders either, commits fail with `KAFKA_STORAGE_ERROR` and clients refresh, as with a classic leader that's cut off.
  - Example: broker 10, rack 0's gateway of coordinator partition 4, is cut off from the controller and fenced at about 9 seconds. Other brokers' images move coordinator partition 4 to broker 16, and coordinator partition 5 from broker 22 to broker 13. Clients that refresh elsewhere move to broker 16, while clients of broker 10 stay until it heals, after which decision 5 ends broker 16's stale window.
  - Accepted risk, cost only: a cut-off gateway keeps receiving its clients' produce for the length of the cut-off. Its clients refresh every `metadata.max.age.ms`, and a refresh from the cut-off broker names it again while one from any other broker names the stand-in, so the rack's clients of that coordinator partition split between the two and drift to the stand-in. The costs:
    - Extra parts: both brokers send parts for the coordinator partition, up to one extra part per file. At 4 files per second per broker in the example, that's about 36 instead of 32 parts per second in rack 0, and 100 instead of 96 in the cluster. A crash doesn't cost this, because its clients reconnect and all reach the stand-in.
    - Cache misses: consumers split the same way, so a tail read of batches the other broker uploaded misses the cache and reads object storage.
    - Uneven load: the stand-in carries two coordinator partitions, as after any fence.
    - Failed produce: if the cut-off broker can't reach the coordinator leaders either, its commits fail with `KAFKA_STORAGE_ERROR`. A client that refreshes from it gets it again, so its batches can fail until `delivery.timeout.ms`, 120 seconds by default, as with a classic leader that's cut off under `acks=all`. Nothing commits wrongly and nothing acknowledged is lost.
    - Duration: until the broker heals and its next heartbeat unfences it, or until each client refreshes from another broker. Decision 5 then clears the stand-in's stale clients with one retry each.
- When routing turns on: gateway routing is on only when three image inputs hold. The coordinator feature, for example `diskless.coordinator.version`, is finalized at level 1 or higher in `FeaturesImage`. `__diskless_metadata` is in the image, which gives `N`. The gateway switch is on. Otherwise the transformer uses today's hash and decision 5's rejection is off. The switch is a cluster-level dynamic config that brokers read from `ConfigurationsImage`, like the per-broker exclusion from [Gateway assignment](21-gateway-assignment.md), so every broker flips at the same image offset. [Gateway benchmark](23-gateway-benchmark.md) keeps the switch's name, its default, and when to flip it.
  - Why: the finalized feature names the backend and never changes at runtime. v2 has no migration from Postgres, refuses every downgrade, and refuses to start a broker whose `inkless.control.plane.class` names another backend while the feature is finalized (v2 `spec.md`, Rollout). Before the controller creates `__diskless_metadata`, there's no `N`, and a coordinator call gets a retriable error (v2 `design.md`, Coordinator partitions), so produce fails whatever the routing. Every input comes from the image, so brokers agree, and decision 5's guard turns the skew at each change into at most one retry.
  - Example: a new 24-broker cluster is formatted with the feature at level 1. Until the topic appears, `payments-5` goes where today's hash puts it, for example broker 7. Once each broker applies the topic's records, coordinator partition 4's rack-0 gateway is broker 10. The client's next batch at broker 7 gets one `NOT_LEADER_OR_FOLLOWER`, and the client refreshes to broker 10. Turning the switch off sends every broker back to the hash with no rejections, and clients converge within `metadata.max.age.ms`. Turning it back on costs each producer one retry.
  - Cost: two new `MetadataView` reads, the feature level and the switch, next to the partition count from [Routing produce by coordinator partition](20-gateway-routing.md).
- Replica preference: the gateway path drops today's preference for replicas in the client's AZ. For a managed partition that doesn't need a local log, the fallback order from [Gateway assignment](21-gateway-assignment.md) applies as written, and replica assignment isn't an input. The response keeps the real replicas, ISR, and offline replicas, and only `LeaderId` changes.
  - Why: no client path needs a replica for such a partition. Managed replicas hold no data. Produce, fetch, `ListOffsets`, and `OffsetForLeaderEpoch` run on any broker through the diskless path and the control plane (`ReplicaManager.scala:1013`, `DisklessFetchOffsetRouter.scala:165-167`, `ReplicaManager.scala:3987-3988`), and `DeleteRecords` already forwards to the real KRaft leader (`KafkaApis.scala:1619-1641`). Tail reads keep their cache hits, because produce and fetch still reach one broker per AZ. Catch-up reads cost the same on every broker, because data older than the 60-second cache lifespan skips the cache everywhere. Production data agrees: catch-up is 0% to 7.4% of consumer requests on diskless services ([Consumer read sources on consolidation services](../research/24-consolidation-read-share.md)).
  - Example: in the 24-broker cluster, a managed topic with RF=3 and no remote storage has `payments-5` in coordinator partition 4, with replicas on brokers 7, 11, and 15. A rack-0 producer and consumer reach broker 10, the gateway of coordinator partition 4, and the file sends 1 part. With the preference, they'd reach replica 7, the gateway of coordinator partition 1, and the batch would be a misroute.
  - Cost: reassigning a replica no longer moves that partition's client traffic. The design says so, and names the operator levers: the per-broker exclusion from [Gateway assignment](21-gateway-assignment.md), which moves whole coordinator partitions, and the gateway switch, which returns to today's routing with the preference.

### Rejected alternatives

The rewrite carries these into the design's rejected alternatives. Each decision in this ticket adds its own subsection.

#### Local-log partitions

- Naming remote storage, consolidation, and the switch in the design as the reasons for replica routing: it puts fork mechanics into a document the KIP carries forward. Upstream reads never need a local log, so the design states the general rule and Inkless lists its cases.
- Placing replicas on the gateways of their coordinator partition: the controller would put each partition's replica in a rack on the gateway of its coordinator partition there. Every join, fence, return, and exclusion moves gateway slots without moving replicas, so placement drifts and the partition misroutes until a reassignment. A reassigned consolidating replica rebuilds its tier state and answers `OFFSET_NOT_AVAILABLE` meanwhile, and a phase-1 replica copies data. Tiered partitions with one replica align in one rack only. It needs an Inkless edit in upstream controller placement and a rebalance after every membership change, and it helps only Inkless. [Gateway assignment](21-gateway-assignment.md) rejects the reverse, gateways that follow replicas, for the same drift.

#### Per-read rule

- A per-partition rule, which keeps a partition on replica routing whenever any of its reads needs a local log: the production data shows that reads needing the local log are under 0.04% of bytes on consolidation services, and the rule gives up the gateway saving for every produce to the partition.
- A mechanism the implementation chooses, unnamed in the design: every choice costs clients or brokers something, a redirect round trip or a forwarding hop, so the design names the cost by naming the mechanism.
- Forwarding every fetch that needs a replica, instead of a redirect: no client round trip, but every response takes a broker hop and its bytes pass through the gateway for as long as the consumer reads old data. Forwarding stays only for fetch versions without the redirect field and for requests without one.
- An error that makes the client refresh its metadata: the refresh returns the gateway again, so the client loops.

#### Unknown client AZ

- Today's hash of `"<topicId>-<partitionIndex>"` over all alive brokers: the same cross-AZ share, but 67% to 93% of these clients' user partitions misroute. A broker that gets `k` such partitions sends `1 + 7 × (1 − (7/8)^k)` parts per file at `N=8`.
- The gateway in the coordinator leader's rack: commit parts would cross no AZ, but every election moves these clients, which [Gateway assignment](21-gateway-assignment.md) rejects for the leader preference. It saves an intra-AZ commit hop and none of the client's cross-AZ bytes.

#### Produce at a broker that isn't a gateway

- Accepting the stale window: no code, but up to about 139,000 extra parts and their coordinator log flushes per rolling restart at 24 brokers, about as many as the routed parts in the same time.
- Recommending a lower `metadata.max.age.ms`, such as 30 seconds: it cuts the bound tenfold, but each client sends metadata requests 10 times as often, and it helps only clients that follow the docs.
- The rejection without a guard: image skew, or a rolling upgrade that changes the rule, can loop a client between brokers that disagree until `delivery.timeout.ms`, 120 seconds by default, fails the batch. That breaks the rule that a produce reaching any broker commits.
- Rejecting misrouted fetches too: the fetch cost of the stale window is GETs for files the new gateway uploaded, which the old gateway then caches, not commit parts. A second rejection path isn't worth it.

#### Fenced broker that clients can still reach

- Refusing diskless produce once the broker's own heartbeats have failed for longer than the session timeout: a controller-quorum outage fails every broker's heartbeats, so every broker would refuse diskless produce. Classic topics keep serving through a controller outage, so this fails the first data-loss clause on availability.
- Using that trigger only to stop naming itself in metadata responses: during a controller outage each broker excludes only itself and computes a different assignment, so decision 5 rejects on every broker and traffic splits. It also breaks the rule from [Gateway assignment](21-gateway-assignment.md) that the image is the only input.

#### When routing turns on

- The backend from the broker's `inkless.control.plane.class`: once the startup check holds, it gives the same answer as the feature. But it's a local Inkless config outside the image, which breaks the image-only rule, while the feature is upstream.
- A static per-broker switch: a flip needs a rolling restart, and brokers disagree for its length, 24 minutes at 24 brokers. Decision 5 then rejects on the brokers that flipped, while clients refresh at random brokers, so traffic splits for the whole restart.

#### Replica preference

- Keeping the replica preference ahead of the gateways: rack-aware placement puts a replica in every rack when RF is at least the rack count, so the gateway step is never reached. Managed topics would send about 8 parts per file at `N=8`, the same as without gateways, and gateways would help only in a rack with no replica.
- The preference as a tiebreaker among several gateways of one coordinator partition in a rack: from `2N` brokers per rack up, it picks the gateway that is a replica, which happens for about 2 in 16 partitions at 16 per rack. It replaces the rendezvous pick on the user partition's log key with a rule that changes on every reassignment, for no data locality, because these replicas hold no data.

### Future work

The rewrite carries these into the design's Future work.

- The per-read rule in Inkless, for consolidating and tiered partitions: a broker that isn't a replica serves fetches at or above the WAL start from the diskless path, where the code already treats a missing local log as "diskless serves the whole range" (`ReplicaManager.scala:2746-2748`) but fails the partition lookup first (`:2808`). It answers fetches below the WAL start with `preferredReadReplica`, forwards them for fetch versions 4 to 10, and forwards `ListOffsets` and `OffsetForLeaderEpoch` lookups that need the local log or the tiered index (`DisklessFetchOffsetRouter.scala:133-159`, `ReplicaManager.scala:3991-4002`). It takes consolidation clusters from about 8 parts per file to 1 at saturation. Catch-up reads inside the WAL move from the local log to cold object reads, about 0.04% of bytes on today's consolidation services ([Consumer read sources on consolidation services](../research/24-consolidation-read-share.md)) and more for a replay-heavy workload. If Inkless consolidation instead writes merge-format objects that any broker reads, as upstream's merge framework plans, no read qualifies and none of this is needed. Support for `preferredReadReplica` in clients other than the Java client needs checking first.
- Cold-path fetches at brokers with an empty gateway set, unanalyzed: a gateway could answer a fetch older than `fetch.lagging.consumer.threshold.ms` with a `preferredReadReplica` that names a broker in the client's rack with no gateway slot. Such brokers exist from `N` per rack up when the rack size isn't a multiple of `N`, for example 2 of 10 at `N=8`, and at 5 to 7 per rack, where the cap leaves some brokers with none. These reads skip the cache on every broker, so moving them costs no cache hits, and it takes object-storage reads off the busiest gateways, up to 1.7 times today's busiest broker at 15 per rack. Still to analyze: how much catch-up traffic there is to move, which spare a gateway picks, the client's extra round trip per partition per `metadata.max.age.ms`, and support in clients other than the Java client.

## Resolution

Resolved on 2026-11-20 in a grilling session.

Amended by [Consequences for the cross-cutting sections](18-cross-cutting-consequences.md#placement-of-costs-that-arent-data-loss): the gateway cut off from the controller is a failure row in the Gateway routing group, tested by test 6, not an accepted risk. The meters are `CommitPartRate{kind}` and `MisroutedBytesRate`, and the rejection count is `MisroutedBatchRejectRate` in `WriterMetrics`.

Every diskless user partition routes to gateways once routing is on, except a partition whose fetches need a broker-local log. A broker that isn't a gateway ends a stale client's misroute with one guarded `NOT_LEADER_OR_FOLLOWER`, and otherwise commits what it gets. The working notes hold each decision's reasons and numbers, and the rejected alternatives and future work go into the rewrite.

- Local-log partitions: the design states a general rule. A partition whose fetches need a broker-local log keeps replica routing, and every other diskless partition routes to gateways. Upstream, no partition qualifies, because merged objects use the WAL format. In Inkless, consolidating, tiered, and phase-1 switched partitions qualify. With consolidation on, every file sends about 8 parts at `N=8`, and at a 10% mix about 4.9. The commit-parts meter gets a fourth value, `off-gateway`, for a part whose batches all belong to such partitions.
- Per-read rule: the design sends only a read that a replica alone can serve to a replica. A fetch below the WAL start gets KIP-392's `preferredReadReplica` from fetch version 11 and is forwarded for versions 4 to 10. A `ListOffsets` or `OffsetForLeaderEpoch` lookup that needs the local log or the tiered index is forwarded. Catch-up inside the WAL stays on the gateway's cold path. Inkless v3 keeps per-partition replica routing for consolidating and tiered partitions, and the per-read implementation is future work, because local-log reads are under 0.04% of bytes on today's consolidation services.
- Unknown client AZ: a client whose AZ resolves to `null` counts as a client of the rack-less group, and the fallback order runs unchanged. When every broker has a rack, it reaches the gateway of its coordinator partition with the highest log-key rendezvous across racks. Today's hash would misroute 67% to 93% of these clients' user partitions.
- Replica preference: the gateway path drops today's preference for replicas in the client's AZ, and replica assignment isn't an input to the fallback order. No client path needs a replica for a partition without a local log, and catch-up reads cost the same on every broker. Reassigning a replica no longer moves client traffic. The per-broker exclusion and the gateway switch are the levers.
- Produce at a broker that isn't a gateway: on the gateway path, the broker rejects a misrouted batch with `NOT_LEADER_OR_FOLLOWER` at most once per connection and partition per `metadata.max.age.ms`, before writing, and accepts and commits it otherwise. Fetches are always served, replica-routed partitions are never rejected, and the rejection is off with the gateway switch off. In the 24-broker example, it saves up to about 139,000 extra parts per rolling restart for one retry per producer per move. The misrouted meters count accepted batches only, and a rejection count joins them.
- Fenced broker that clients can still reach: diskless produce gets no fencing check, and the broker's own image decides. A broker that sees its own fence isn't in its own candidate set, so the rejection moves its clients. A broker cut off from the controller can't see its fence, keeps committing, and is an accepted risk with a cost only.
- When routing turns on: only when the coordinator feature is finalized at level 1 or higher in `FeaturesImage`, `__diskless_metadata` is in the image, and the gateway switch is on. Otherwise the transformer uses today's hash and the rejection is off. The switch is a cluster-level dynamic config read from `ConfigurationsImage`, so every broker flips at the same image offset. [Gateway benchmark](23-gateway-benchmark.md) keeps its name, its default, and when to flip it.

### Tests

Placement in the test layers belongs to [Consequences for the cross-cutting sections](18-cross-cutting-consequences.md):

1. Misrouted produce, the ticket's named test: a produce on the gateway path at a broker that isn't a gateway gets one `NOT_LEADER_OR_FOLLOWER` and writes nothing. The client refreshes, and the batch commits at the gateway. A second misrouted batch on the same connection and partition within `metadata.max.age.ms` commits at the broker that isn't a gateway. Other partitions in the rejected request commit. The rejection count rises by one, and the misrouted meters count only the accepted batch. With the switch off, or for a replica-routed partition, nothing is rejected.
2. No loop under disagreement: with two brokers given different assignments through the stub interface, a client that refreshes from each in turn commits after at most one retry per broker.
3. Unknown AZ, a transformer unit test: a `null`-AZ client reaches the rack-less group's gateway in a cluster without racks, the rack-less brokers first in a mixed cluster, and the cross-rack gateway with the highest log-key rendezvous when every broker has a rack.
4. No replica preference, a transformer unit test: for a managed partition without remote storage, a client in a rack whose replica isn't the gateway gets the gateway as `LeaderId`, and the replicas, ISR, and offline replicas stay as the controller wrote them.
5. Local-log partitions: consolidating, tiered, and phase-1 switched partitions keep replica routing, are never rejected, and their parts count as `off-gateway`.
6. Fenced broker: a broker that applies its own fence rejects once per connection and partition and names the stand-in, and moves back after its unfence. A broker cut off from the controller keeps committing produce while other brokers name the stand-in, and once it's also cut off from the coordinator leaders, its produce fails with `KAFKA_STORAGE_ERROR`.
7. Routing switch-on, a transformer unit test: the hash applies while the feature is unfinalized, while `__diskless_metadata` is missing, or while the switch is off, and gateway routing applies once all three hold. A switch change takes effect at its config record, with no restart.

### Correction from ticket 23

[Gateway benchmark](23-gateway-benchmark.md#resolution) corrects the 10%-mix figure. The estimate of about 4.9 parts per file counted 6 local-log partitions per file, 10% of the 64 partitions per broker. A broker carries its rack's traffic for `n_racks × 64 = 192` user partitions' worth, so about 19 consolidating partitions route to it, and a 256-batch file touches about 14 of them. With equal traffic per partition, a 10% mix sends about 6.8 parts per file at 24 brokers, 5% about 5.1, 2% about 3.1, and 1% about 2.1. The decisions don't change, and their cost is larger: 1% of traffic on consolidating topics doubles parts per file at saturation, which raises the value of the per-read rule in Future work.

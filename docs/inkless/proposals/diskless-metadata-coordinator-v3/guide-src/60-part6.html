Part 6

Putting it together

This part follows one produce and one fetch through every piece, shows how the design is checked before and after it's built, lists what it accepts, and collects the alternatives it rejected, including the two earlier versions of this design.

41A produce and a fetch, end to end

The cluster has 3 racks of 8 brokers and N = 8, so racks are at saturation. Broker 3 is in rack a, in zone A. It's the rack-a gateway for cp0, so its gateway set is {cp0} and its tracking partition is cp0. Its epoch is 7, and it holds the lease [0, 1023] at cp0. A producer in zone A writes to orders-0, which maps to cp0.

  1. Route. The producer asks any broker for metadata. Every broker computes the same gateways from its image, so each one names broker 3 as the leader of orders-0 for a zone-A client (chapters 30 and 31).
  2. Buffer. Broker 3 adds the batch to its current file. Its other zone-A clients for cp0's user partitions write there too, so the file holds cp0 batches only (chapter 2).
  3. Close. After 250 ms, FileCommitter closes the file and gives it the pair (7, 41) from the lease. No request is sent (chapters 18 and 20).
  4. Name and upload. The object key is <clusterId>.3.7.41. Retries reuse the same key (chapter 19).
  5. Split. All of the file's batches map to cp0, which is also the tracking partition. So the file sends exactly one part: it carries the batches, the participant set {cp0}, and the finish report for earlier files (chapters 22, 23, and 32).
  6. Check. cp0's leader checks the mapping, the broker epoch, the lease, the broker row, and the producer's own idempotence rules. It reserves offsets against SQLite plus its overlay (chapters 9, 18, and 20).
  7. Append. The leader adds a file-committed record to the current batch and appends with acks=-1. The leader and each follower fsync it (chapter 10).
  8. Apply and reply. When the high watermark passes the record, the leader applies it to SQLite in a group with other records, moves broker 3's row to (7, 41), and replies with the offsets and the Recorded flag (chapters 11 and 23).
  9. Answer the producer. The producer's request waits only for the parts that hold its batches, here one. Broker 3 responds and fills its batch coordinate cache (chapter 15).
  10. Fetch. A consumer in zone A reads orders-0. Routing sends it to broker 3 too, so the read is usually a cache hit. On a miss, broker 3 asks cp0's leader, whose read pool answers from SQLite without touching the commit thread (chapter 34).
  11. Release. Days later, retention removes the batches on cp0. In the same transaction, the emptiness check finds nothing pointing into 3.7.41. cp0 is the tracking partition, so the release is local, and the key goes straight into cp0's deletion queue (chapter 22).
  12. Delete. After one minute, FileCleaner on cp0's leader deletes the key and appends a files-deleted record.

Compare this with the same produce on a cluster without routing: the file would hold batches for all 8 coordinator partitions and send 8 parts, plus 7 release reports later, one from each participant other than the tracking partition. If the producer's metadata had been stale, broker 3 would have rejected its first misrouted batch once, and the retry would have reached the right gateway.

42How the design is checked

Why this exists

Both reviews of the earlier version asked for proof, not prose: a model check of the fence, floor, and release protocol, and benchmarks with pass rules decided before anyone runs them. A benchmark without a pass rule invites arguing about the result after the fact.

Council review: model-check the protocolCouncil review: benchmark pass criteria

The model check

A TLA+ model covers leases, the switch and fallback, commits, late attempts, finish reports, fences, floors, releases, lease ends, retention, and the deletion queue. It has four modules: FencesFloors, FFScenarios, TrackingEntries, and EpochRetirement. It checks four invariants:

  • NoDeleteReferenced: no object is deleted or queued while a batch references it.
  • NoCutLive: no fence raises a floor past a part the broker still sends, or past a sequence it still plans to use.
  • NoLeak: once an epoch ended and the coordinator is quiet, every uploaded key that no partition holds is queued.
  • EndedKnown: once the lease covering a finished file ends, its tracking partition knows the key.

Within its bounds of 3 partitions, ranges of 2 sequences, up to 4 files, 1 late attempt, 1 pause, and 1 or 2 epochs, no invariant fails. Each rule the model guards has a flag, and turning it off reproduces the race that rule closes within seconds. The model leaves out the overlay, a tracking leader change, and more than one broker. Shared tests, cluster tests, and seam tests cover those.

Benchmarks with pass rules

The baseline is the PostgreSQL backend as Inkless runs it in production. A latency comparison passes when the coordinator's P50 and P99 produce latency are each at most 1.1 times PostgreSQL's at the same throughput. Each side runs 3 times for 30 minutes after a 10-minute warmup, and the comparison uses the median. Sizes are 3, 12, and 24 brokers in 3 racks, at 16 MiB/s per broker, with 64 diskless partitions per broker. Every possible result maps to a decision in advance.

Accepted limits

Performance limits aren't risks to data. Each one has a signal and a lever:

  • Outgrowing N. Each coordinator partition has one writer, so N caps commit throughput, and N can't change after creation. Choose N for the cluster's expected peak size, and reassign coordinator leaders to less loaded brokers. Splitting partitions is future work.
  • A hot gateway. The busiest gateway can carry up to 1.7 times today's busiest broker at some rack sizes. Watch BytesInPerSec against the rack mean. The levers are racks of up to 4 brokers or a multiple of N, or the routing switch off.

44Rejected alternatives and earlier versions

Why this exists

Knowing what a design rejected, and why, is often the fastest way to understand it. This design went through two earlier versions, each reviewed against the same bars. This chapter collects what they did and what replaced it, plus the larger alternatives the design turned down.

Design historyReviews

Version 1: an owner and an intent for every object

The first version kept KIP-1164's idea of an owner, but one owner collected everything instead of handing the object along. Before every upload, the broker sent an intent to an owner chosen among the participants: the random object key, the participants, and the owner. The owner appended and fsynced it before the upload could start. Each commit part carried the broker's clock reading. After a maximum commit age of 5 minutes, the owner fenced participants it hadn't heard from. Participants kept a tombstone per released key so a late retry couldn't add the batches back, and tombstones expired after twice the maximum commit age.

It failed both bars:

  • Performance. The intent is a replicated, fsynced append on the produce path, which PostgreSQL doesn't have.
  • Data loss. Safety depended on broker clocks. If two clocks differed by more than the maximum commit age, a late part could pass the age check after its tombstone expired, and commit batches into a deleted object.
  • Machinery. Intent records, owner hashing and fallback, predecessor fences, per-key tombstones, and expiry records, each a source of bugs.

Some council proposals weren't adopted into this design. An admission cap or retry budget was rejected in favor of in-flight limits (chapter 40). Object footers, soft delete with a deletion-rate cap, and an empty restart are recorded in full as future work.

Other rejected alternatives

  • An external database, a cluster KRaft quorum, or a separate KRaft quorum. KIP-1164 itself rejected these (chapter 4).
  • Coordinator-less designs, where partition leaders act as coordinators. KIP-1163 rejected them for separating stateful coordinators from stateless replicas.
  • A deleting scanner. It fails toward data loss (chapter 17).
  • Committing at the tracking partition first. It adds a second serial round trip to every commit (chapter 15).
  • A live-batch count per object. A count can drift toward zero while batches remain (chapter 22).
  • Follower reads and a leader lease. Followers widen the stale-read problem, and a lease adds a wait to every failover (chapter 34).
  • A controller-written gateway assignment, plain rendezvous, and round-robin. The first costs a new record type and controller code, the second leaves balance to chance, and the third moves too many slots (chapter 30).
  • Co-location mirroring, where gateways follow coordinator leadership. The coordinator still sends one part per coordinator partition, so it saves nothing and ties gateways to elections.
  • A monotonic grace period. It delays every delete by one grace period after each failover (chapter 27).

45Where this is heading

The north-star RFC's goal is one metadata component that indexes every form diskless data takes, instead of splitting the truth between the coordinator, tiered storage metadata, and KRaft. None of the following is part of this design, but each depends on a decision this design keeps intact:

  • Grow the coordinator by splitting partitions. With slot % N and a power-of-two N, doubling N moves exactly half of each partition's slots. It still needs a handoff of a slot's state.
  • Merge WAL objects into extents. A merged object replaces many batch rows with one extent row, and old objects release through the normal path. Merged objects in the WAL format also remove local-log partitions, so every partition can use gateways.
  • Tiered metadata in the coordinator. Remote segment metadata for a diskless partition would live in the same coordinator partition as its batches, which answers concerns Jun Rao raised in the KIP-1163 discussion.
  • Partitionless key ranges. Every record names its log with a Log structure, so a later encoding can describe a key range.
  • A report-only orphan scanner. It lists keys nobody holds without deleting them, the only detector for the two accepted leaks.
  • Object footers and recovery. A footer naming each object's partition runs would let an operator rebuild a coordinator partition after losing every replica, removing clause 2's exception.
  • Deletion bounds. Soft delete or bucket versioning for 7 days, checked by a probe, plus a deletion-rate cap. A wrongly deleted object could then be restored by name.
  • An empty restart. A coordinator partition that lost every replica could come back empty instead of staying offline.
  • Extra gateways for a hot coordinator partition, and the per-read rule, which routes every diskless partition to gateways and sends only reads that need a replica to one.

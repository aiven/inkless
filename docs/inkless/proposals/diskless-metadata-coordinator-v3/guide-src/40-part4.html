Part 4

Gateway routing: fewer parts per file

Splitting the coordinator into N partitions spread the work, but it also made every file talk to almost every partition. This part shows the cost of that, and how routing clients to the right brokers cuts it to about one part per file in a large cluster, without changing any public protocol.

29The cost of talking to every partition

Why this exists

Chapter 10 showed that each commit part costs a replicated, fsynced append on the leader and on every follower. Without routing, a broker's file holds batches for almost every coordinator partition, so each file costs up to N parts and up to N × R flushes. That's the main cost the coordinator adds over PostgreSQL. KIP-1164 sketches an answer: gateways, a few brokers per rack that collect the traffic for one coordinator.

KIP-1164: GatewaysPerformance bar

Today, Inkless's metadata transformer tells each client to produce to a broker chosen by a hash of the user partition. Every broker gets a slice of every topic. With 64 partitions per broker and N = 8, a 250 ms file holds about 256 batches and hits all 8 coordinator partitions. So each file sends 8 parts, and each coordinator leader receives one part from every broker on every round.

The fix doesn't touch the coordinator at all. It changes which broker a client talks to. If every client that writes to cp3's user partitions in rack a talks to the same broker, that broker's files hold mostly cp3 batches, and each file sends about one part. That broker is a gateway for cp3 in rack a.

  • A gateway accepts produce, uploads the WAL file, and sends the commit part. It holds no coordinator state.
  • A coordinator leader assigns offsets and replicates the commit. Being a gateway and being a leader are independent.
  • Routing is only a hint. A produce that reaches any broker still commits, at the cost of extra parts. Routing never decides correctness, and it doesn't change the number of files or PUTs: each broker still uploads one file per commit tick. It only decides what each file holds.
  • No public protocol changes. The transformer rewrites LeaderId in metadata responses, as it already does.

Takeaway

Routing each rack's clients for a coordinator partition to one broker turns about N parts per file into about one, once a rack has at least N brokers. With 3 racks of 8, that's 8 times fewer parts and flushes.

What this leaves open

Every broker must agree on who the gateways are, without talking to each other. How?

30Choosing gateways without asking anyone

Why this exists

Any broker can answer a metadata request, so every broker must give the same answer. A controller-written assignment would need a new metadata record and controller code for every fence and registration. Instead, every broker computes the gateways from its metadata image alone, with a rule that gives the same answer everywhere and moves as few gateways as possible when a broker joins or leaves.

KIP-1164: max(1, n_brokers / n_dcs / n_racks) gatewaysRendezvous hashing

The rule works per rack, and no rack reads another rack's brokers:

  • Candidates are the registered, unfenced brokers in the image, minus the ones an operator excluded with diskless.gateway.candidate.enable=false. Brokers without a rack form their own group.
  • How many gateways. Each coordinator partition gets g = max(1, ⌊b_r / N⌋) gateways in a rack with b_r candidates. KIP-1164 proposed counting across the whole cluster. Counting per rack fits racks of different sizes.
  • Scores. Each pair of a coordinator partition and a broker gets a score: toPositive(murmur2(bytes(cp) ++ bytes(brokerId))), with both as 4-byte big-endian integers. This is rendezvous hashing: everyone computes the same scores, and a broker's scores don't depend on anyone else.
  • A cap. Plain rendezvous leaves balance to chance: at 3 brokers and N = 8, about 1 cluster in 4 puts 5 or more coordinator partitions on one broker. So the rule walks the pairs from the highest score down and assigns a pair only if the coordinator partition still needs a gateway and the broker holds fewer than ⌈N × g / b_r⌉. Equal scores go to the lower broker ID.
  • Spares. From N brokers per rack up, each gateway serves exactly one coordinator partition. That's saturation. Leftover brokers are spares and get no gateway traffic.
  • Leadership isn't an input. An election moves no client traffic.

In simulations of random clusters at N = 8, the capped rule always met the cap. It moved 2.7 gateway slots on average when a fourth broker joined a rack, against an ideal of 2, and 1.1 when one of 10 left, against about 0.8. Round-robin over sorted IDs, by comparison, moves 6.6 slots on a join, because one new ID shifts every later position. The design's simulation used MD5, so the reference implementation measures the bound again with murmur2.

A gateway crash needs no extra mechanism. Until the controller fences the broker, its coordinator partitions stall in its rack, as a classic partition does when its leader crashes. Other racks keep committing. After the fence, the same rule on the remaining brokers picks stand-ins.

Takeaway

Every broker computes the same gateways from the image, with capped rendezvous hashing per rack. No RPC, no controller record, and few moves when membership changes.

What this leaves open

What does a broker tell a client whose rack has no gateway it can use, or whose rack is unknown? And what about clients with old metadata?

31Routing a client, and correcting stale ones

Why this exists

Diskless topics exist to avoid cross-AZ traffic, so routing must never move a client's bytes to another AZ when a broker in its own AZ can take them. And clients cache metadata for up to 5 minutes, so after a gateway moves they keep producing to the old broker. Without a correction, a rolling restart of 24 brokers costs up to about 139,000 extra parts.

Cross-AZ costStale metadata after a move

For a client in rack r and a user partition of coordinator partition p, the transformer answers with the first match:

  1. A gateway of p in r.
  2. Another broker in r, in the order of p's scores.
  3. A gateway of p in another rack.
  4. Any broker.

The order keeps traffic in the client's AZ whenever a broker there can take it, at the cost of an extra part. When it can't, it crosses AZs only to a gateway that already sends a part for p. Each choice among several brokers takes the highest hash(logKey, brokerId), so the producer and consumers of one user partition reach the same broker.

A client whose AZ is unknown, because its client ID has no diskless_az, counts as a client of the rack-less group. When every broker has a rack, step 3 picks a gateway in some rack. About 2 picks in 3 cross an AZ with 3 racks under any rule, so the rule only makes sure the pick already sends a part for p.

The misroute rejection

A batch is misrouted when the receiving broker isn't a gateway of its coordinator partition in its own rack. On the gateway path, the broker rejects a misrouted batch with NOT_LEADER_OR_FOLLOWER, before writing it. Producers treat that error as stale metadata: they refresh at once and retry, and idempotent sequences stay intact. The broker rejects at most once per connection and partition per metadata.max.age.ms, and accepts and commits the batch otherwise. That guard matters. Two brokers whose images differ for a moment could otherwise bounce a client back and forth until its delivery timeout. With the guard, a false positive costs one retry, and then the batch commits.

Takeaway

The fallback order stays in the client's AZ whenever it can. One guarded rejection per connection and partition moves stale clients within a retry, so a rolling restart costs a few extra parts per move, not about 139,000.

What this leaves open

A routed file now sends about one part. But every file also sends a tracking part. If the tracking partition isn't the gateway's own coordinator partition, every file pays a second part.

32Picking the tracking partition

Why this exists

A tracking partition fixed by a hash of the broker ID matches a gateway's own coordinator partition only 1 time in N. At saturation, files then send about 1.88 parts instead of 1, every leader receives 5.6 parts per round instead of 3, and every object needs a release report across partitions. If the tracking partition is one of the broker's own gateway partitions, a routed file sends no extra part for tracking, and its releases are local.

Review finding: the fixed hash doubles partsPerformance bar

A broker's gateway set is the coordinator partitions it's a gateway for in its own rack. A spare's set is empty. The broker picks its preferred tracking partition from that set with the sticky rule:

  • While the current tracking partition stays in the set, keep it.
  • When it leaves the set, or at the start of an epoch, take the member with the highest score, the same score the gateway rule uses. At saturation the set has one member, so this only chooses below N brokers per rack.
  • With an empty set, keep the current one. At the start of an epoch with an empty set, take the highest score over all N.

Why sticky, and not always the highest score? Because a broker that only gains coordinator partitions, such as a stand-in during a fence, never switches, so a rolling restart doesn't bounce tracking partitions back and forth. Always taking the highest score switches about twice as often below saturation.

The rule produces the ordered list that lease renewals walk, as chapter 20 described: the preferred tracking partition, then the rest of the gateway set by score, then every other coordinator partition by score.

When to switch

When the preferred partition changes, the broker switches once it closes the first file with no batch for its current tracking partition. Until then, clients with cached metadata still send it that partition's traffic, so its tracking part isn't empty and a switch would save nothing. Each switch costs one lease request at the new partition, one lease release at the old one, and N lease-end range fences merged into pending batches: about 18 records at N = 8.

A broker tracks its objects at one of its own gateway partitions, so a routed file sends one part, not two. The sticky rule switches only when the broker loses that partition, and only once stale traffic has stopped.

What this leaves open

Where does routing not help, and what can an operator do when it hurts?

33Where routing stops helping, and the operator's levers

Why this exists

Routing has costs. Some partitions can't use gateways, a gateway carries whole coordinator partitions and can get hot, and brokers must agree on when routing is on. The design names each limit with a signal and a lever, so nobody discovers them in production.

Accepted limitsOperability

Partitions that need a broker-local log

Some diskless partitions keep data in a broker-local log: consolidating partitions, tiered partitions, and switched partitions whose classic prefix is still on local disks. Their fetches need a replica, so they keep the transformer's replica routing. Their traffic spreads over all N coordinator partitions and adds parts even to a gateway's files. With consolidation on, every new diskless topic also gets remote storage, so every file sends about 8 parts, and gateways save nothing.

A narrower rule is future work: route every diskless partition to gateways, and send only the reads that need a replica to one. On two production services with consolidation on, such reads are 0.035% and 0.00014% of bytes out.

A hot gateway

The assignment counts brokers, not traffic, because every broker must compute the same answer and each one only sees its own traffic. A gateway carries whole coordinator partitions, so at some rack sizes the busiest broker carries more than it does today.

When routing is on

Routing is on only when three inputs in the image hold: the coordinator feature is finalized, __diskless_metadata exists, which gives N, and diskless.gateway.routing.enable is on. Every input comes from the image, so brokers flip at the same offset.

  • diskless.gateway.routing.enable: the cluster-wide switch, default true. It can only be set at the cluster default. The controller rejects a per-broker value, and a broker refuses a static one at startup, because brokers that disagree would split traffic. Turn it off for a hot gateway that hurts produce latency or for a suspected routing defect, not for rolling restarts or upgrades.
  • diskless.gateway.candidate.enable: per broker only, default true. false excludes a degraded broker or one about to be decommissioned. A cluster default of false is rejected, because it would remove every candidate.

A change to the rule itself needs no version gate. During a rolling upgrade, old and new brokers compute different gateways, which adds parts until the upgrade ends and never affects correctness.

Fenced and cut-off brokers

Diskless produce has no fencing check: each broker's own image decides. A broker that applies its own fence isn't in its own candidate set, so it rejects its first misrouted batch per connection and partition, and sends clients to the stand-in. A broker cut off from the controller never sees its fence. It keeps acting as the gateway while it reaches the coordinator leaders, and its clients drift to the stand-in as they refresh from other brokers. The cost is up to one extra part per file and uneven load. Nothing acknowledged is lost.

Takeaway

Routing saves the most in large, evenly sized racks, and nothing for partitions that need a local log. A hot gateway can carry up to 1.7 times today's busiest broker. One cluster-wide switch and one per-broker exclusion are the levers.

What this leaves open

Commits, deletion, and routing are designed. Now the coordinator itself needs protection: from reading data that might vanish, from wrong configs, and from losing a replica.

The diskless metadata coordinator, from first principles

Diskless topics keep Kafka data in object storage instead of on broker disks. Something still has to put that data in order, remember where every batch lives, and decide when an object in storage can be deleted. This guide builds that component, the diskless metadata coordinator, one idea at a time. Every idea starts with the problem that prompted it, and most come with a demo you can play with.

Part 1

Why a diskless topic needs a coordinator, and why build a new one

Before you can understand a design, you need to know what the thing does and why it has to change. This part starts with classic Kafka, removes one piece at a time until the coordinator's job is the only thing left, and then explains why that job can't stay where it runs today.

1Classic Kafka in one picture

Why this exists

Diskless topics exist to remove a cost that classic topics can't avoid. To see that cost, you first need to see how a classic topic stores data.

KIP-1150: Diskless TopicsKIP-1163: motivation

A Kafka topic is split into partitions. Each partition is an append-only log: a list of records where every record gets the next number, called its offset. Offsets are how consumers keep their place: "I've read up to offset 1,400."

In a classic topic, each partition has one leader broker and a few followers. The producer sends its records to the leader. The leader writes them to its local disk and gives them offsets, and the followers copy them. With three copies in three availability zones, the data survives the loss of a whole zone.

That safety has a price. Cloud providers charge for every byte that crosses from one zone to another. The producer's zone matches the leader's zone only one time in three, and the two follower copies always cross a zone. The leader also needs a disk big enough for all the data it keeps.

2Diskless topics: let object storage keep the copies

Why this exists

Object storage, such as Amazon S3, Google Cloud Storage, or Azure Blob Storage, already stores data durably across zones, and writing to it from inside a zone doesn't add a cross-zone charge. KIP-1150 and KIP-1163 propose that Kafka hand replication to object storage instead of doing it itself.

KIP-1163: "Kafka delegates replication of diskless topics to object storage"

In a diskless topic, the producer sends its records to any broker, usually one in its own zone. The broker doesn't write them to disk. It collects produce requests in a buffer for a short time, about 250 milliseconds or a few megabytes, and then uploads the whole buffer to object storage as one object.

That object is called a WAL object or WAL file. WAL stands for write-ahead log. Because the broker accepts produce requests for every partition, one WAL object holds batches for many partitions, often from many topics.

Why mix partitions in one object? Object storage charges per request. If each broker uploaded one object per partition every 250 milliseconds, a cluster with thousands of partitions would make thousands of uploads per second. Mixing ties the number of uploads to the number of brokers, not to the number of partitions. KIP-1163 says it directly: mixing "is necessary to keep the object storage write operation costs reasonable." Keep this sentence in mind. Almost every hard problem later in this guide comes from it.

3Data without order: what the coordinator does

Why this exists

In a classic topic, the leader orders the data because it's the only writer. A diskless partition has many writers, so ordering has to move somewhere else. KIP-1163 separates the data, which goes to object storage, from the metadata about the data, which needs strong consistency. The component that owns that metadata is the diskless coordinator, and KIP-1164 describes it.

KIP-1163: "decouple the handling of batch data and batch metadata"KIP-1164: role of the coordinator

Think of a warehouse. Brokers drop boxes into it: the WAL objects. Each box holds pages from many different books: the partitions. Nobody numbers the pages when the box is packed. The coordinator is the catalog at the front desk. When a box arrives, the broker tells the catalog what's inside, and the catalog writes down: "pages 100 to 149 of the book orders-0 are in box X, starting at byte 4,096."

That catalog entry is called a batch coordinate. The coordinator does three kinds of work with coordinates:

  • Commit. After an upload, the broker sends the coordinator a list of the batches in the object. The coordinator checks them, for example rejecting a duplicate from an idempotent producer, gives each batch its offsets, and stores the coordinates. Only then does the producer get its answer. In the code, this is commitFile.
  • Find. When a consumer asks for offset 1,400 of orders-0 and the broker doesn't have it cached, the broker asks the coordinator where those batches are. In the code, this is findBatches. Related lookups, such as "what's the latest offset," go through listOffsets.
  • Housekeeping. Retention, DeleteRecords, and topic deletion remove coordinates. Once no coordinate points into an object, the object can be deleted from storage.

4Where should the catalog live?

Why this exists

Inkless runs the coordinator on PostgreSQL today, and that can't go into Apache Kafka. KIP-1164 compares the places the catalog could live and picks an internal Kafka topic. The north-star RFC adds a second reason: today the truth about diskless data is split across three systems.

KIP-1164: Rejected alternativesKIP-1163: Coordinator-less approachesNorth-star RFC

In Inkless today, the coordinator is a PostgreSQL database. Brokers talk to it through a Java interface called ControlPlane. A commit is a SQL transaction that inserts the batch rows, and a lookup is a SQL query. It works and ships, but it has three costs:

  • Another system to run. Every Kafka cluster with diskless topics also needs a highly available PostgreSQL deployment, with its own backups, upgrades, and on-call rotation.
  • One database for the whole cluster. Every commit and every cache-miss lookup from every broker goes to the same primary, which limits both scale and availability.
  • Upstream Kafka can't depend on it. KIP-1164 rejects an external system "to keep Kafka self-sufficient."

There's a fourth, longer-term cost. The north-star RFC counts three sources of truth for one diskless partition: KRaft knows the partition exists, PostgreSQL knows its batches, and the remote log metadata manager knows its tiered segments. Each change that spans two of them needs care, and each answer to "where is offset X?" has to ask more than one place. The RFC's goal is one metadata component for every form diskless data takes. A coordinator inside Kafka is the first step toward it.

So where should the catalog live instead? The KIPs weigh five options. Click each one to see how it fares.

KIP-1164 chooses the last option. The diskless coordinator is built the way Kafka already builds its group coordinator: the group coordinator keeps consumer group state in the internal topic __consumer_offsets, its partition leaders act as coordinators, and the work runs on a shared runtime called CoordinatorRuntime. The diskless coordinator keeps its state in a new internal topic, __diskless_metadata, with the same model.

The design in this guide implements that choice as a third ControlPlane implementation, DisklessMetadataControlPlane, next to PostgreSQL and an in-memory one used in tests. An operator selects it with inkless.control.plane.class. It's for new clusters only: migrating a PostgreSQL-backed cluster is out of scope.

Takeaway

The catalog moves into Kafka: an internal topic is the storage, and the leaders of its partitions are the coordinators. Kafka stays self-sufficient, cluster metadata stays fast, and the coordinator can grow with the cluster.

What this leaves open

"Inside Kafka" isn't a quality bar. How safe and how fast must the new coordinator be before it can replace PostgreSQL?

5The two bars every decision must pass

Why this exists

A new coordinator replaces one that works. It must not lose data that a classic topic would keep, and it must not be slower than PostgreSQL. The design writes both demands down as bars, and every later chapter cites them, because they decide which ideas survive.

Design goalsReviews of earlier versions

The data-loss bar: Kafka parity

The first bar compares the coordinator with a classic topic. It has three clauses:

  1. Survive what a classic topic survives. Any failure that a classic topic survives, diskless topics survive too.
  2. Keep the damage in one place. A failure that a classic topic doesn't survive can be an accepted risk only if its damage stays within the user partitions of the failed coordinator partition, and it loses no more than a classic topic loses to the same failure. One named exception: losing every replica of a coordinator partition. The design accepts it because it enforces three replicas spread across racks, which makes that loss as rare as it can be.
  3. Never let one loss spread. A failure that lets one coordinator partition's loss delete or resurrect another partition's data can't be an accepted risk. It needs a fix or a bound. The exceptions are three causes that also lose classic data: a lost tail of the log, a bug in the code that applies records, and someone deleting objects from outside Kafka.

Two terms from the clauses come back often. Kafka parity means the coordinator is as safe as a classic topic. The blast radius is the share of diskless partitions a failure can reach. If the coordinator is split into N pieces, as Part 2 explains, losing one piece reaches about 1/N of every diskless topic.

The performance bar: no worse than PostgreSQL

The second bar compares the coordinator with the PostgreSQL backend it replaces. Produce latency at the 50th and 99th percentiles must stay within 1.1 times PostgreSQL's at the same throughput, and object storage must see the same number of uploads. Part 6 shows how benchmarks make this testable. Until then, the bar works as a design rule: no step may sit on the produce path that PostgreSQL doesn't have.

Part 2

Building a coordinator out of Kafka parts

This part explains how a Kafka topic, a local SQLite database, and a few strict rules together replace a PostgreSQL server. These pieces are the foundation for everything after it.

7The log is the truth

Why this exists

A database guarantees that a committed change survives and that everyone sees changes in the same order. A replicated Kafka log gives the same two guarantees, so KIP-1164 makes the log of __diskless_metadata the coordinator's source of truth.

KIP-1164: "The source of truth for the coordinator will be the __diskless_metadata topic"

Every decision the coordinator makes becomes a record in the log. "Object X was committed, and its batch for orders-0 got offsets 100 to 149" is a record. "Retention removed every batch of orders-0 below offset 500" is a record. "Topic clicks was deleted" is a record.

The leader of the coordinator partition is the only writer. It runs every request through the same four steps that KIP-1164 describes, which also match how the KRaft controller works:

  1. Check the request against the current state. For example: is this a duplicate, and what's the next free offset?
  2. Append one record that describes the outcome, including every value it chose, such as the offsets.
  3. Wait until the followers have copied the record. Kafka tracks this with the high watermark: the offset below which every in-sync replica has the record.
  4. Reply to the broker that asked.

One rule makes this work: applying a record never reads anything outside the log. It never reads a clock, and it never reads the broker's own view of cluster metadata, which Kafka calls the metadata image. The record carries every value it needs. Suppose one replica applied "delete topic clicks" when its own image said so, and another replica did it a moment later. They would delete at different positions in the log and end up with different state. Because every replica reads the same records in the same order, every replica ends up with the same state.

Analogy

A bank keeps a journal of transactions. The balance of every account can be recomputed from the journal at any time. If a clerk wrote "the balance is whatever my watch says it should be," two branches would disagree. The coordinator's log is the journal, and every value goes into the journal.

Takeaway

The coordinator writes its decisions as records to a replicated topic. The leader decides, the followers copy, and every replica rebuilds the same state from the same records.

What this leaves open

A log is good for writing, but a consumer's question, "where is offset 1,400 of orders-0?", needs an index. Replaying the whole log for every lookup is far too slow.

8SQLite: a copy you can always rebuild

Why this exists

Kafka's other coordinators keep their whole state in memory. KIP-1164 notes that the diskless coordinator's state is much larger, "up to hundreds of megabytes or even gigabytes," so it proposes SQLite, an embedded database, to hold the state on disk with indexes.

KIP-1164: Local state machine

Every replica of a coordinator partition keeps its own SQLite database. SQLite runs inside the broker process, so a query has no network hop. The tables hold the same things PostgreSQL holds today: logs, files, batches, and producer state.

Each replica applies records from the log to its SQLite database, in log order, and only up to the high watermark. With each apply, it stores the offset it applied, and the leader epoch of that record, in the same SQLite transaction. After a restart, it reads that offset and continues from the next record.

Why only up to the high watermark? A record above the high watermark isn't safe yet. If the leader fails, the new leader may not have that record, and the log is truncated to match the new leader. If SQLite had already applied the record, it would need to undo it, and undo is where bugs hide. By waiting, SQLite only ever moves forward.

The database is a cache, not a source of truth. If it's lost or corrupt, the replica deletes it and rebuilds from the log.

Each replica turns the log into an indexed SQLite database. It applies only what the high watermark covers, so it never has to undo anything, and it can always rebuild from the log.

9Speculative state: checking ahead of replication

Why this exists

KIP-1164 names two requirements that pull against each other. Commits should be pipelined, so the next one can start while the current one replicates. But the local state should only change after replication. The coordinator meets both with an in-memory overlay of pending records.

KIP-1164: How operations are performedPerformance bar

Picture two commits for orders-0, a few milliseconds apart. The first one gets offsets 100 to 149. Its record is on its way to the followers, so SQLite doesn't have it yet. If the leader checked the second commit against SQLite alone, it would also hand out offset 100.

The fix is the overlay: a list, in the leader's memory, of records it has appended but not yet applied. The leader checks each new commit against SQLite plus every overlay entry. The second commit sees the first in the overlay and gets offsets 150 to 199.

  • Batching. The leader can share one log append between commits that queue while it's busy. One replication round trip and one disk sync then cover many commits. This waiting time is called the linger.
  • Apply on the high watermark. When the high watermark passes an entry, the leader applies it to SQLite, removes it from the overlay, and replies.
  • Failure. If an append fails, the leader drops that entry and every entry after it, and those requests get a retriable error. Later entries took their offsets from the failed one, so they're wrong too.
  • Only the leader. Followers keep no overlay. A new leader starts with an empty one.
  • A cap. The overlay holds at most 4 × B entries, where B is the broker count. Above that, the leader answers COORDINATOR_NOT_AVAILABLE. Normal load never gets close. The cap only trips on a bug or a high watermark that stopped moving, and then it keeps the leader's memory bounded.

This loop isn't new code. It runs on CoordinatorRuntime, the runtime that the group and share coordinators use. The runtime already provides the single writer thread, the shared appends, the revert after a failed append, and the parked replies. The design adds a custom loader, because this coordinator's state lives in SQLite instead of memory.

Analogy

A restaurant host writes reservations in pencil while waiting for the manager to confirm them in ink. New guests are seated around the pencil marks, so no table is booked twice. If the manager rejects one reservation, every pencil mark written after it is erased, because those were planned around it.

10Durability: every batch reaches the disk

Why this exists

Clause 3 of the data-loss bar forbids one coordinator partition's loss from damaging another's data. A lost tail of the coordinator log does exactly that, because object storage doesn't lose power along with the brokers. So the design makes flushing every batch to disk mandatory, with no weaker mode.

Data-loss bar, clause 3Correlated power loss

The coordinator writes to __diskless_metadata the way the safest classic producer does:

  • acks=-1: an append counts only when every in-sync replica has it.
  • Replication factor 3 with min.insync.replicas=2: if fewer than two replicas are in sync, appends fail at once with NOT_ENOUGH_REPLICAS instead of hanging. The upstream coordinators append with acks=1, so Inkless brings its own writer for this topic.
  • No unclean leader election: a replica that's missing acknowledged records never becomes leader.

Classic Kafka usually doesn't force each batch to disk with fsync. It relies on copies in different zones: if one broker loses power, the others still have the data. But if every replica loses power at once, a correlated power loss, each one loses what was still in memory. On a classic topic that loses the unflushed tail of that one partition, and nothing else.

On the coordinator, the damage spreads:

  • Reused offsets. A lost commit record frees its offsets. The next commit takes them for different data. Brokers that cached the old coordinates now serve different records for the same offset. One coordinator partition holds this for its share of every diskless partition in the cluster.
  • Deleted objects that the index still points to. Part 3 shows that deleting an object takes records on two coordinator partitions. If one partition's record survives and the other's is lost, the object can be deleted while batch rows elsewhere still point at it. Part 3 names three more versions of this problem.

So __diskless_metadata requires flush.messages=1: every replica syncs every batch to disk before it counts as appended. Thanks to shared appends, that's one sync per batch of commits, not one per commit.

What flushing costs

The flush isn't free, and the design counts it honestly. The leader flushes before the record counts, and each follower flushes before the fetch that moves the high watermark, so every commit waits for two flushes in a row. The leader's flush matches what PostgreSQL does on every commit. The follower's flush is a second one that PostgreSQL pays only with a synchronous standby. The design calls it the price of Kafka parity: the KRaft metadata log pays the same price for the same reason.

The count also grows with the number of coordinator partitions a file talks to. Chapter 14 shows that one file can send a part to each of them, and each part costs one flush on each replica. With 8 coordinator partitions and 3 replicas, one file costs up to 8 × 3 = 24 flushes. That number is the main reason for Part 4, which brings it down to about 3 on larger clusters.

The shared append is adaptive by default, the same as for the group coordinator: a write that arrives while the leader is idle gets its own append right away, and only writes that queue up share one. A fixed linger would cut flushes on paper, but on a small cluster the brokers' commit timers run out of step, so there's little to share, and every part would pay the wait.

Takeaway

An acknowledged coordinator record is on the disk of at least two replicas. A correlated power loss loses nothing that a producer was told is committed. The cost is up to one flush per part per replica, which later chapters work to reduce.

What this leaves open

Every applied record is also a SQLite write. Can SQLite keep up, and can it ever stall the thread that answers commits?

11Keeping SQLite off the commit path

Why this exists

A review of an earlier version found two stalls hiding in SQLite. One transaction per record pays SQLite's commit cost on every record, and SQLite's automatic checkpoint runs on whichever thread happens to cross its threshold, which can be the thread that answers commits. Either one adds waiting that PostgreSQL doesn't have.

Performance barReview finding: checkpoint on the shard thread

SQLite runs in WAL mode: a change goes to a write-ahead file first, and a checkpoint later copies it into the main database file. The design keeps three kinds of SQLite work apart:

  • Group apply. When the high watermark advances past several records, the replica applies them all in one SQLite transaction, up to 4 MiB of log bytes. Each record gets a savepoint, a marker inside the transaction. If one record can't be applied, the replica rolls back to that record's savepoint, commits everything before it, and stops. The applied offset stays exact.
  • A checkpoint thread. Automatic checkpoints are off. One thread per broker runs a non-blocking checkpoint, called PASSIVE, for every coordinator database once its write-ahead file reaches 1,000 pages. A PASSIVE checkpoint never blocks the thread that applies records.
  • A follower-applier thread. On followers, Kafka's replica fetcher thread only fetches bytes. A separate thread per broker applies them to SQLite, so a slow apply never slows down replication.

SQLite's synchronous=NORMAL setting is enough here, because a lost SQLite transaction is replayed from the log, which is already on disk. The design also requires a SQLite version that fixes a known bug in WAL-mode checkpoints.

What this leaves open

12Snapshots: keep the log short

Why this exists

KIP-1164 proposes to "take snapshots of the local state" and prune the log behind them, the way KRaft does under KIP-630. Without that, the log and the rebuild time grow without limit.

KIP-1164: Metadata log size management

A snapshot is a copy of a replica's SQLite file at a known log offset. Once enough replicas hold a snapshot at offset X, nobody needs the records below X: a replica that loses its database can load the snapshot and replay from X. The leader can then move the log's start forward, and Kafka deletes the old segments. The topic's normal retention is off, with retention.ms=-1, so this rule is the only thing that ever deletes coordinator log segments.

  • Every replica snapshots itself. Each one copies its own SQLite every hour or every 1 GiB of applied log, whichever comes first, and keeps exactly two snapshots: the newest and one older.
  • The leader moves the log start carefully. It only advances to an offset that at least min.insync.replicas in-sync replicas, the leader included, hold a covering snapshot for. It uses its older snapshot, so the one it keeps after its next rotation still covers the log start.
  • Followers report their snapshots to the leader on a private request. A report counts only while the replica is in sync. If a replica drops out, its report is ignored, because it may have lost its files meanwhile.
  • A replica that needs records below the log start, for example a brand-new replica, fetches a snapshot in 8 MiB chunks. It asks an in-sync follower first and uses the leader only when no follower has one, because the leader is already the busiest broker. A broker runs at most one transfer at a time by default.

One detail shows how careful the design is about positions. The snapshot's offset is read from the applied-offset row inside the finished copy, never from the live database. A tag read before the copy could be too low. A tag read after could be too high, which would let the leader delete records the copy doesn't contain.

13Many coordinators: splitting the work by hash

Why this exists

KIP-1164 gives __diskless_metadata multiple partitions, "effectively creating multiple coordinators and sharding the space of user partitions for scalability." It also limits the damage of a failure to one share of the cluster, which is what clause 2 of the data-loss bar asks for.

KIP-1164: Partitioning of __diskless_metadataData-loss bar, clause 2

The topic has N partitions, 8 by default. The default stays provisional until a benchmark confirms it. Each partition is a complete, independent coordinator, with its own log, SQLite databases, snapshots, overlay, and leader. Kafka spreads the leaders across brokers as it does for any topic. This guide calls them coordinator partitions and writes them as cp0, cp1, and so on. A partition of a normal topic, such as orders-0, is a user partition.

Every user partition belongs to exactly one coordinator partition, so it keeps exactly one place that hands out its offsets. The mapping is a hash, so no broker needs to store a table:

  1. Build the log key: the 16 bytes of the topic ID followed by the partition index as 4 bytes.
  2. Hash it with Kafka's murmur2 and take the result modulo 4096. That's the slot. The 4096 is a fixed protocol constant.
  3. The coordinator partition is slot % N.

Why the extra step through 4096 slots? It keeps a door open. N must be a power of two. If a later version doubles N, every slot either stays where it is or moves from p to p + N, so exactly half of each partition's work moves and nothing else changes. In this design N is fixed after creation, and the controller refuses CreatePartitions on the topic. The slot layer still costs nothing at runtime: with a power-of-two N, it gives the same answer as murmur2 % N.

KIP-1164 proposed storing each user partition's coordinator in the partition metadata. The hash avoids that stored state. Each leader also recomputes the mapping for every request it receives and rejects a mismatch with INVALID_REQUEST, because a broker that mapped differently would create a second writer for a user partition.

14One file, many coordinators: commit parts

Why this exists

KIP-1163 lets any broker write any partition, so a WAL object usually spans many coordinators. KIP-1164 calls this "undesirable": in the worst case, committing one file takes one network call per coordinator, "which increases the chances for partial failure and higher tail latencies." Before the design can reduce the split, it has to make the split safe.

KIP-1164: Reducing multi-DC commit operationsPerformance bar

The coordinator partitions that an object's batches map to are its participants. When a broker commits an object, it splits the commit into one part per participant and sends the parts in parallel. Each part carries only that coordinator partition's batches. Each part succeeds or fails on its own.

Wouldn't it be safer to make the parts all-or-nothing with a two-phase commit? It would cost an extra round trip on every commit, and it would protect a guarantee Kafka doesn't offer: a non-transactional produce to two partitions isn't atomic in classic Kafka either. The existing commitFile already returns a separate result for each batch. So if one part fails, the producers of those partitions get a retriable error and retry only those partitions, as they would for any partial produce failure.

Commit queues

Today the broker's FileCommitter commits files on one thread, one file after the other. That keeps a broker's commits in order. With many coordinators, that thread becomes a trap: most files have batches for most coordinator partitions, so if one coordinator partition is slow or offline, every later file waits behind it, on every broker.

The order that matters is the order within a user partition, which here means within a coordinator partition. So FileCommitter keeps one ordered queue per coordinator partition. A file's part on cp2 waits only for the same broker's previous part on cp2. Every part shares its file's commit deadline, so a stuck queue delays each waiting part by at most one deadline. PostgreSQL and the in-memory backend map everything to one queue, which keeps today's behavior.

15A produce waits only for its own parts

Why this exists

If every produce request in a file waits for the whole file, a request that only touches cp2 still waits for a slow or stuck cp5. A review of an earlier version, which completed requests per file, flagged it.

Performance barReview finding: per-file completion

  • Batches on parts that confirmed get their offsets.
  • Batches on a part that didn't confirm by the deadline get KAFKA_STORAGE_ERROR, the same error a whole failed commit gets today. The producer retries only those partitions.
  • The file itself still finishes only when every part has finished. Part 3 shows why that moment matters: it's when cleanup decisions can start.

Part 3

The hard problem: deleting objects safely

Committing and finding batches is the smaller half of the coordinator's job. This part covers the hard half: deciding when an object in storage can be deleted. It explains why the problem is hard, then builds the answer one idea at a time, until you can follow any object from upload to deletion.

16Three ways an object gets left behind

Why this exists

Objects cost money for as long as they exist, so every object must eventually be deleted. Deleting one too early loses data. KIP-1163 lists the failure that leaves "garbage objects" behind, and KIP-1164 adds that an object spread across coordinators has "no one owner that controls the file lifetime."

KIP-1163: Error handling and segment object garbage collectionKIP-1164: WAL file management

Deleting an object is safe only when two things are true: no committed batch points into it, and no commit can point into it later. The second condition is the tricky one. Here are the three situations the design must handle:

  • The orphan. The broker uploaded the object and crashed before any commit. The object sits in storage, and no coordinator knows it exists.
  • The shared object. The object's batches are committed on cp0, cp1, and cp3. Retention removes the cp0 batches after one day, but the cp3 batches live for a week. cp0 knows it's done with the object. It doesn't know about cp3.
  • The unknown outcome. A commit part timed out. The broker gave up and told the producer it failed. But the request may still be sitting in the leader's queue, and it may commit later. Until something rules that out, nobody can say the object is unreferenced.

17Scan the bucket, or keep the books?

Why this exists

KIP-1164 proposes a background scanner that lists the bucket and deletes objects that no coordinator knows. The design compares that scanner with deletion driven only by the coordinator's own records, and chooses the records.

KIP-1164: Orphan filesData-loss bar

KIP-1164's scanner works like this: before each pass, it asks every coordinator for the age of the oldest object it knows. It lists the bucket for objects older than that, asks every coordinator whether it knows each one, and deletes the ones nobody knows.

The alternative is to keep the books: the coordinator records every object before or when it's created, tracks who still references it, and deletes only objects its own records name.

The deciding difference is the direction of failure. Every system has bugs and bad days. The question is what happens on a bad day:

  • A scanner deletes what nobody knows. If a coordinator wrongly answers "unknown," live data is deleted. That's data loss.
  • Bookkeeping deletes only what it recorded and resolved. If a record is lost or a bug skips a step, an object stays in storage. That's a leak: it costs money, and nothing is lost.

18The broker as an idempotent producer

Why this exists

To reject a late or repeated commit, a coordinator partition has to remember something. If it remembers object keys, it needs one entry per object, plus a timer to forget them, and timers depend on clocks. Kafka's idempotent producer solves the same problem with one number per producer and no clock. The design reuses that idea for brokers.

Kafka's idempotent producer (KIP-98)Data-loss bar

Kafka's idempotent producer works like this. Each producer has an ID, an epoch, and a sequence number that goes up by one with every batch. The partition leader remembers the last sequence it accepted from each producer. A batch with the same sequence is a retry, so the leader answers "already done." A lower sequence is stale, so the leader rejects it. No clock is involved: order alone decides.

The design treats each uploading broker the same way:

  • The broker's epoch comes from KRaft. Every time a broker registers, for example after a restart, it gets a new, higher epoch. KRaft uses the offset of the registration record in the metadata log as the epoch, which chapter 39 puts to use. Nothing needs to be saved across restarts: the new epoch is higher than everything from before.
  • When FileCommitter closes a file, it gives the file the current broker epoch and the next sequence number. Every commit part of that file carries the pair (epoch, sequence). Pairs compare epoch first, then sequence.
  • Every coordinator partition keeps one broker row per uploading broker: the last pair that committed there, and the complete per-batch result of that commit.
  • Gaps are fine. A file that failed to upload uses a sequence and never commits it. Nothing requires last + 1.

Why a number and not a random ID such as a UUID? Because order lets a partition keep one value per broker instead of a growing set of keys, spot a sequence that's missing, and decide all of it without a clock.

Analogy

A bank doesn't remember every check you ever wrote. It remembers the highest check number it cashed from your account. A check with that number again is a duplicate. A check with a lower number is stale. A new checkbook, a new epoch, voids every check from the old one.

19Object names you can predict

Why this exists

If the object key is random, the coordinator needs a message per object to learn it. If the key is built from the broker's (epoch, sequence), the coordinator can compute every key a broker could have uploaded, with no message at all.

Deterministic object keysPerformance bar

In this design, every object name has this form:

<clusterId>.<brokerId>.<brokerEpoch>.<sequence>

  • Known in advance. If the coordinator knows broker 3 may use sequences 0 to 1023 in epoch 7, it knows the exact names of up to 1,024 objects, whether they were uploaded or not.
  • The cluster ID keeps two clusters that share a bucket and prefix from overwriting or deleting each other's objects. KRaft never reuses a broker epoch inside one cluster, so the name is unique.
  • Upload retries are harmless. Every attempt for one file uses the same name, and every supported object store overwrites the key.
  • The prefix comes from the uploader. A deletion builds the full path with the uploading broker's inkless.object.key.prefix, which the lease records. A cluster whose brokers differ in prefix would otherwise delete keys that were never written and leak the real ones.

20Leases: numbers handed out ahead of time

Why this exists

A message before every upload would put a replicated, fsynced append on the produce path, which PostgreSQL doesn't have. A lease moves that round trip off the produce path: the broker reserves a whole range of sequence numbers in advance, in the background. Every key the broker may upload is then on record before the upload, with no message per object.

Performance barOrphans from chapter 16

Each broker leases its numbers from one coordinator partition, its tracking partition. Chapter 22 describes everything else it does, and chapter 32 explains how a broker picks it. For now, picture broker 3 with tracking partition cp2.

Getting and using a lease

  • Ask for a range. The broker asks its tracking partition for a range [a, b] of sequences for its current epoch. The tracking partition appends a sequences-leased record and replies once it applies, so a confirmed lease survives a leader change. A range holds at most K = 1024 sequences.
  • Use it. At file close, the broker takes the next leased sequence. No request is needed.
  • Renew early. When fewer than half the range is left, the broker asks for the next range in the background, and uses up the rest of its current range first.
  • Nothing leased, no upload. If the broker has no leased sequence, the file fails at once with a retriable error and isn't uploaded. Nothing unrecorded ever reaches storage.

Why 1024? With one file every 250 ms, a range lasts about four minutes, and about 85 seconds when a broker closes files as fast as it can. When a lease ends early, the unused numbers become deletes of keys that were never written. Those are cheap: deletes are free on S3, Google Cloud Storage, and Azure. K is a protocol constant, not a config, because nobody would tune it.

Keeping a lease alive

A lease can end, and its unused numbers are then cleaned up. Three events end one: the broker's epoch is retired, the broker asks for a lease at a newer epoch, or the tracking partition writes a lease-ended record. The tracking partition also has an idle timer: if it hears nothing from a broker for 15 minutes, it ends that broker's lease. That timer exists for brokers that are cut off or paused, so their leftover keys still get collected.

A live broker must never be caught by the idle timer. If a quiet broker's lease ended without its knowledge, its first file after the quiet period would fail. So a live broker never relies on the timer:

  • Keepalives. If the broker has had no answer from its tracking partition for half the idle timeout, it sends a keepalive: a lease request for a range it already holds. The tracking partition treats it as a retry, confirms the range, appends nothing, and restarts its timer.
  • Switch at once. If the tracking partition doesn't answer a renewal, the broker walks an ordered list of other coordinator partitions and leases from the first one that answers. As soon as a range at another partition is confirmed, the broker switches to it and abandons its old ranges, including the unused rest of the current one. When a later renewal reaches the preferred partition again, it switches back the same way.
  • Lease releases. The broker ends every range it abandons with a lease release to that partition, scoped to the highest range end b it gives up there. It sends the release only once every file with a sequence at or below b is finished, and once no sequence it still plans to use is at or below b.

Why switch at once instead of finishing the old range first? Picture a broker that falls back to cp5 at a low file rate. If it kept using cp2's remainder, cp5's new range would get no parts for a long time, and cp5's idle timer could fire first. Ending that range fences it, and Chapter 21 shows that a fence raises a floor at every partition, past sequences the broker still plans to use. Switching at once means a lease end or a release never cuts a range in use. Four reasons start a renewal, and a metric counts each: fewer than half left, an unanswered keepalive, a failed tracking part, and a change in the broker's preferred tracking partition.

21Floors and fences: closing the door without a clock

Why this exists

The obvious way to stop late commits is time: reject any part older than a few minutes. That makes safety depend on two brokers' clocks agreeing, and the rejected-alternatives chapter shows how that loses data. This design uses order instead: it raises a floor, and every pair at or below the floor is rejected forever.

Data-loss barNo clock decides safety

Each broker row has a fenced-through mark next to its last commit. The floor is the highest of three things: the last commit, the fenced-through mark, and the first pair after retiredThrough. A new commit needs a pair above the floor. The floor only rises:

  • The broker commits a newer file at that partition. This happens all the time on a busy broker.
  • A broker epoch is retired. Every pair of the old epoch is now below the floor.
  • A fence. Another coordinator partition asks: "Which of broker 3's sequences between a and b in epoch 7 do you hold?" The asked partition appends a sequences-fenced record that raises its fenced-through mark to (7, b), and answers with the sequences it holds batches for. Every other sequence in the range is now released: it never committed or its batches are gone, and it can never commit there again.

The fenced-through mark is kept apart from the last commit. A fence that overwrote the last commit would make a retry of that commit look stale while the broker still waits for its answer.

22The tracking partition: one bookkeeper per broker

Why this exists

An object's batches live on several coordinator partitions, and none of them can see the others. One place has to collect what they know and decide. KIP-1164 picks an owner per object and hands the object from owner to owner. This design picks one bookkeeper per broker, fixed before any upload: the tracking partition that issued the lease. Because it issued the lease, it already knows every key the broker may upload.

KIP-1164: WAL file managementPerformance bar

The tracking partition has three jobs for the brokers it serves:

  • Leases: the ranges from chapter 20.
  • Tracking entries: for each committed object, which participants still reference it. Every file sends a part to its tracking partition, the tracking part, even when the tracking partition holds none of the file's batches. That part carries the participant set. If the tracking partition holds some of the file's batches, it's a participant too, and its own entry is handled locally.
  • The deletion queue: keys that are safe to delete, each with the time it was marked. Only tracking partitions keep a queue.

Nothing outside the broker computes its tracking partition. Every commit part names it, and every report goes to the partition the part names, so no agreement across brokers or versions is needed.

Releases

When an apply removes batches, through retention, DeleteRecords, topic purge, or consolidation pruning, the participant checks each object it touched: does any batch still point into it? An index on batches(file_id) makes the check cheap, and it runs in the same SQLite transaction. If the answer is no, the participant has released the object, and it reports the release to the object's tracking partition.

Why not keep a count of live batches per object instead? A count fails toward data loss: one code path that adds a batch without raising the count, and the count reaches zero while batches remain. The query reads the batch rows themselves, so it can't drift. PostgreSQL makes the same check today.

Deletion

Once every participant of an object has released it, the tracking partition puts its key in the deletion queue. The existing FileCleaner runs on every broker. On this backend, it only finds rows on brokers that lead a tracking partition. It waits the existing one-minute grace period, so readers that cached coordinates can finish, deletes the keys from storage, and appends a files-deleted record. Deleting a key that doesn't exist counts as success, which covers numbers that were leased but never used. The queue is in SQLite on every replica, so if leadership moves halfway through, the new leader deletes the key again, which is harmless.

Takeaway

Each broker has one bookkeeper. It leases the broker's numbers, records each object's participants, collects their releases, and queues the object once all of them let go.

What this leaves open

A participant whose part never arrived will never send a release. The tracking partition has to fence it instead. But when is it safe to fence a participant that hasn't said anything yet?

23Finish reports: when is it safe to fence?

Why this exists

A fence makes every part at or below its range impossible. Sent too early, it rejects a part that's still on its way, and a healthy produce fails. Only the broker knows when it has stopped sending a file's parts, so the broker must tell the tracking partition. A review of an earlier version found that the obvious rule, "fence the participants you haven't heard from," turns every routine leader change into failed produces.

Review finding: an empty tracking part fences parts in flightData-loss bar

Here's the obvious rule: once the tracking partition and every participant it has heard from are released, fence each participant it hasn't heard from. It sounds safe. The demo shows how it breaks when the tracking part holds no batches: the tracking partition's own entry is released the moment the part is recorded, so the rule fires while the other parts are still in flight.

The file uses sequence (7, 41). Cp2 tracks it but holds no batches, so its part is empty. Compare the obvious rule, which fences participants it hasn't heard from, with the design's two outcomes: cp1 recovers within the deadline, or cp1 stays unavailable past it.

So the tracking partition fences a participant only after the broker has finished the file, and the broker says which files are finished in a finish report:

  • finishedThrough: every file of this broker epoch with a sequence at or below this number is finished. A file is finished when every part, the tracking part included, has committed, got an error that retrying won't fix, or passed the commit deadline. Files finish out of order, so this number trails the slowest unfinished file. It covers the whole epoch, because a participant keeps one floor per broker, not one per tracking partition.
  • Exception ranges: the participants that didn't answer. A participant answered when its reply came from a recorded commit. Each reply carries a Recorded flag that says so, because an error code alone can't tell a commit whose batches all failed from a rejection. Everything else is an exception: a rejection before the producer checks, NOT_COORDINATOR until the deadline, an unknown outcome at the deadline, or a part the broker never sent. A report holds at most one exception range per participant.

The report rides on messages the broker sends anyway: every tracking part, lease request, keepalive, and lease release. A report with an exception is urgent, because a part with an unknown outcome could still commit late. A busy broker's next tracking part carries it. A quiet broker sends an early keepalive within one commit interval to carry it.

The rule that comes out of this is short: the tracking partition never fences a participant that answered. It waits for that participant's release instead. Why not trust a broker that says "this part was rejected, call it released"? Because then a bug in the broker could delete data. A rejected part stays an exception, and its fence costs nothing at the participant, because the sequence is already below the floor there.

Takeaway

The broker reports which files are finished and which participants didn't answer. The tracking partition fences only those participants, and only after the file is finished, so no fence ever races a live part.

What this leaves open

Exceptions are one reason to fence. What are the others, and what stops a burst of failures from flooding a recovering partition with fences?

24Three reasons to fence, and keeping fences in check

Why this exists

Finish reports cover a broker that's alive and talking. A tracking part can also fail on its own, and a broker can die. Each case needs a fence with a different reach. A partition that recovers from an outage can then face thousands of fence ranges at once, so a review asked for a bound on that work.

Orphan casesReview finding: fence storms

The tracking partition sends fences in exactly three cases. Each one waits until the broker has finished the files it covers, or can never send them again:

  • Exceptions. One range fence per exception range in a recorded finish report, to that participant. A report triggers at most N - 1 fences.
  • Missed sequences. A sequence in a leased range is missed once a recorded finishedThrough reaches it while the tracking partition has no record of it. Its tracking part failed, but its other parts may have committed. The tracking partition doesn't know its participants, so it fences the sequence at all N partitions and builds the participant set from the "I hold it" answers. The broker never supplies the set, because a broker bug that left a participant out would delete an object that the participant still references.
  • Lease ends. One range fence per partition, from the sequence after the recorded finishedThrough to the end of the ended range. It covers used sequences without a report, missed sequences, and numbers never used. Keys that nobody holds go straight to the deletion queue.

When one record does both, for example a lease release whose finish report reaches a sequence the tracking partition never recorded, the missed-sequence rule goes first. Otherwise the lease-end range would start above that sequence, and nothing would fence its key.

Batching

Each tracking partition keeps at most one fence request in flight per participant. Fence ranges that pile up meanwhile go into the next request, so batching needs no timer. Within one broker epoch, ranges merge into their hull, from the lowest start to the highest end. That's safe for fences, because a fence's effect depends only on its upper end, and every sequence in the hull is one the broker finished or can never send. A request is capped at 512 KiB, and fences aren't rate-limited. A fence whose entries are all held or released is skipped, because those sequences can't commit there again.

What this leaves open

Answers now arrive from three directions: finish reports, fence answers, and release reports. They can arrive in any order. How does the tracking partition keep its entries straight?

25Tracking entries that only move forward

Why this exists

The network reorders messages. A release report can arrive before the tracking part that names the participant, and a late "referenced" fence answer can arrive after a release. A naive tracker drops the early report or lets the late answer overwrite the release, and in both cases the object waits forever: a leak. A review of an earlier version found both.

Review finding: release orderingLeaks

For each object, the tracking partition keeps one entry per participant. An entry moves through four states and never goes back:

StateMeaningHow it gets there
PendingThe participant set is recorded. Nothing has covered this participant yet.The tracking part records.
FencingA range fence that covers the entry is out, with no answer yet.A finish report lists the participant as an exception, or the lease ends.
HeldThe participant holds batches and owes a release report.A finish report says it answered, or a fence answers "referenced."
ReleasedDone. Nothing can change it again.The participant's release report arrives, or a fence answers "released."

Released is terminal because of an invariant: once a participant releases a sequence, it can't come to reference that sequence again. Either the part committed and a retry gets the stored answer, or the sequence is below the participant's floor. A "referenced" answer that arrives after a release only means the network reordered two messages that the participant's log already put in order.

An early release report gets stored, not dropped. A participant whose batches all failed releases the object in the same apply that records its part, so its report often beats the tracking part. If no entry exists yet, the tracking partition compares the sequence with a bound. Above the bound, it stores the entry as released and merges the participant set into it later. At or below the bound, the object is already resolved, and the report is a harmless repeat.

A retention pass can release thousands of objects at once. 28The leaks left, and why the broker no longer deletes

Why this exists

A design that only deletes what its books name can still leak, and a broker that deletes on its own can still bypass the books. The design checks both. It accepts two small leaks and turns off the broker's own delete for this backend.

Data-loss barPartial sends

The accepted leaks

Object storage can finish a write after the tracking partition deleted that key. For example, an upload request is stuck in the network, the broker gives up, the lease ends, the key is fenced and deleted, and then storage completes the old write. Nothing will ever delete that object again, because no batch row points to it, and a bucket lifecycle rule can't help, because topics can keep data forever.

The leak is bounded and costs storage, not data. One upload attempt leaks at most one object. A broker cut off from the cluster can upload at most the rest of its lease, at most K files. The one-minute grace period also covers uploads that land within a minute. PostgreSQL today leaks more: when a commit fails, the broker deletes the object only if isSafeToDeleteFile allows it, and nothing collects the rest.

The second leak needs a bug: a held entry whose participant no longer holds batches and never reports, because a broker wrongly claimed "answered" or a participant skipped its emptiness check. Note the direction: a wrong claim leaks, it never deletes. A future scanner that only reports suspected orphans would make both leaks visible.

The broker's direct delete

Today, if a commit fails because the control plane is unavailable, FileCommitJob deletes the object itself. With split commits, that's dangerous. Picture part 1 sent with an unknown outcome, then part 2 failing because the control plane became unavailable. No part confirmed, so the broker would delete the object, while part 1 can still commit into it.

The new backend declares a capability that turns off the broker's direct delete, and FileCommitJob checks it first. Every upload already has a leased sequence that the tracking partition resolves, so the backend never needs the direct delete. PostgreSQL and the in-memory backend keep their current behavior.

Takeaway

Only the tracking partition's queue deletes objects. What's left are two bounded leaks that cost storage, never data.

Part 4

Gateway routing: fewer parts per file

Splitting the coordinator into N partitions spread the work, but it also made every file talk to almost every partition. This part shows the cost of that, and how routing clients to the right brokers cuts it to about one part per file in a large cluster, without changing any public protocol.

29The cost of talking to every partition

Why this exists

Chapter 10 showed that each commit part costs a replicated, fsynced append on the leader and on every follower. Without routing, a broker's file holds batches for almost every coordinator partition, so each file costs up to N parts and up to N × R flushes. That's the main cost the coordinator adds over PostgreSQL. KIP-1164 sketches an answer: gateways, a few brokers per rack that collect the traffic for one coordinator.

KIP-1164: GatewaysPerformance bar

Today, Inkless's metadata transformer tells each client to produce to a broker chosen by a hash of the user partition. Every broker gets a slice of every topic. With 64 partitions per broker and N = 8, a 250 ms file holds about 256 batches and hits all 8 coordinator partitions. So each file sends 8 parts, and each coordinator leader receives one part from every broker on every round.

The fix doesn't touch the coordinator at all. It changes which broker a client talks to. If every client that writes to cp3's user partitions in rack a talks to the same broker, that broker's files hold mostly cp3 batches, and each file sends about one part. That broker is a gateway for cp3 in rack a.

  • A gateway accepts produce, uploads the WAL file, and sends the commit part. It holds no coordinator state.
  • A coordinator leader assigns offsets and replicates the commit. Being a gateway and being a leader are independent.
  • Routing is only a hint. A produce that reaches any broker still commits, at the cost of extra parts. Routing never decides correctness, and it doesn't change the number of files or PUTs: each broker still uploads one file per commit tick. It only decides what each file holds.
  • No public protocol changes. The transformer rewrites LeaderId in metadata responses, as it already does.

30Choosing gateways without asking anyone

Why this exists

Any broker can answer a metadata request, so every broker must give the same answer. A controller-written assignment would need a new metadata record and controller code for every fence and registration. Instead, every broker computes the gateways from its metadata image alone, with a rule that gives the same answer everywhere and moves as few gateways as possible when a broker joins or leaves.

KIP-1164: max(1, n_brokers / n_dcs / n_racks) gatewaysRendezvous hashing

The rule works per rack, and no rack reads another rack's brokers:

  • Candidates are the registered, unfenced brokers in the image, minus the ones an operator excluded with diskless.gateway.candidate.enable=false. Brokers without a rack form their own group.
  • How many gateways. Each coordinator partition gets g = max(1, ⌊b_r / N⌋) gateways in a rack with b_r candidates. KIP-1164 proposed counting across the whole cluster. Counting per rack fits racks of different sizes.
  • Scores. Each pair of a coordinator partition and a broker gets a score: toPositive(murmur2(bytes(cp) ++ bytes(brokerId))), with both as 4-byte big-endian integers. This is rendezvous hashing: everyone computes the same scores, and a broker's scores don't depend on anyone else.
  • A cap. Plain rendezvous leaves balance to chance: at 3 brokers and N = 8, about 1 cluster in 4 puts 5 or more coordinator partitions on one broker. So the rule walks the pairs from the highest score down and assigns a pair only if the coordinator partition still needs a gateway and the broker holds fewer than ⌈N × g / b_r⌉. Equal scores go to the lower broker ID.
  • Spares. From N brokers per rack up, each gateway serves exactly one coordinator partition. That's saturation. Leftover brokers are spares and get no gateway traffic.
  • Leadership isn't an input. An election moves no client traffic.

31Routing a client, and correcting stale ones

Why this exists

Diskless topics exist to avoid cross-AZ traffic, so routing must never move a client's bytes to another AZ when a broker in its own AZ can take them. And clients cache metadata for up to 5 minutes, so after a gateway moves they keep producing to the old broker. Without a correction, a rolling restart of 24 brokers costs up to about 139,000 extra parts.

Cross-AZ costStale metadata after a move

For a client in rack r and a user partition of coordinator partition p, the transformer answers with the first match:

  1. A gateway of p in r.
  2. Another broker in r, in the order of p's scores.
  3. A gateway of p in another rack.
  4. Any broker.

The order keeps traffic in the client's AZ whenever a broker there can take it, at the cost of an extra part. When it can't, it crosses AZs only to a gateway that already sends a part for p. Each choice among several brokers takes the highest hash(logKey, brokerId), so the producer and consumers of one user partition reach the same broker.

A client whose AZ is unknown, because its client ID has no diskless_az, counts as a client of the rack-less group. When every broker has a rack, step 3 picks a gateway in some rack. About 2 picks in 3 cross an AZ with 3 racks under any rule, so the rule only makes sure the pick already sends a part for p.

The misroute rejection

A batch is misrouted when the receiving broker isn't a gateway of its coordinator partition in its own rack. On the gateway path, the broker rejects a misrouted batch with NOT_LEADER_OR_FOLLOWER, before writing it. Producers treat that error as stale metadata: they refresh at once and retry, and idempotent sequences stay intact. The broker rejects at most once per connection and partition per metadata.max.age.ms, and accepts and commits the batch otherwise. That guard matters. Two brokers whose images differ for a moment could otherwise bounce a client back and forth until its delivery timeout. With the guard, a false positive costs one retry, and then the batch commits.

32Picking the tracking partition

Why this exists

A tracking partition fixed by a hash of the broker ID matches a gateway's own coordinator partition only 1 time in N. At saturation, files then send about 1.88 parts instead of 1, every leader receives 5.6 parts per round instead of 3, and every object needs a release report across partitions. If the tracking partition is one of the broker's own gateway partitions, a routed file sends no extra part for tracking, and its releases are local.

Review finding: the fixed hash doubles partsPerformance bar

A broker's gateway set is the coordinator partitions it's a gateway for in its own rack. A spare's set is empty. The broker picks its preferred tracking partition from that set with the sticky rule:

  • While the current tracking partition stays in the set, keep it.
  • When it leaves the set, or at the start of an epoch, take the member with the highest score, the same score the gateway rule uses. At saturation the set has one member, so this only chooses below N brokers per rack.
  • With an empty set, keep the current one. At the start of an epoch with an empty set, take the highest score over all N.

Why sticky, and not always the highest score? Because a broker that only gains coordinator partitions, such as a stand-in during a fence, never switches, so a rolling restart doesn't bounce tracking partitions back and forth. Always taking the highest score switches about twice as often below saturation.

The rule produces the ordered list that lease renewals walk, as chapter 20 described: the preferred tracking partition, then the rest of the gateway set by score, then every other coordinator partition by score.

When to switch

When the preferred partition changes, the broker switches once it closes the first file with no batch for its current tracking partition. Until then, clients with cached metadata still send it that partition's traffic, so its tracking part isn't empty and a switch would save nothing. Each switch costs one lease request at the new partition, one lease release at the old one, and N lease-end range fences merged into pending batches: about 18 records at N = 8.

33Where routing stops helping, and the operator's levers

Why this exists

Routing has costs. Some partitions can't use gateways, a gateway carries whole coordinator partitions and can get hot, and brokers must agree on when routing is on. The design names each limit with a signal and a lever, so nobody discovers them in production.

Accepted limitsOperability

Partitions that need a broker-local log

Some diskless partitions keep data in a broker-local log: consolidating partitions, tiered partitions, and switched partitions whose classic prefix is still on local disks. Their fetches need a replica, so they keep the transformer's replica routing. Their traffic spreads over all N coordinator partitions and adds parts even to a gateway's files. With consolidation on, every new diskless topic also gets remote storage, so every file sends about 8 parts, and gateways save nothing.

A narrower rule is future work: route every diskless partition to gateways, and send only the reads that need a replica to one. On two production services with consolidation on, such reads are 0.035% and 0.00014% of bytes out.

A hot gateway

The assignment counts brokers, not traffic, because every broker must compute the same answer and each one only sees its own traffic. A gateway carries whole coordinator partitions, so at some rack sizes the busiest broker carries more than it does today.

When routing is on

Routing is on only when three inputs in the image hold: the coordinator feature is finalized, __diskless_metadata exists, which gives N, and diskless.gateway.routing.enable is on. Every input comes from the image, so brokers flip at the same offset.

  • diskless.gateway.routing.enable: the cluster-wide switch, default true. It can only be set at the cluster default. Turn it off for a hot gateway that hurts produce latency or for a suspected routing defect, not for rolling restarts or upgrades.
  • diskless.gateway.candidate.enable: per broker only, default true. false excludes a degraded broker or one about to be decommissioned. A cluster default of false is rejected, because it would remove every candidate.

A change to the rule itself needs no version gate. During a rolling upgrade, old and new brokers compute different gateways, which adds parts until the upgrade ends and never affects correctness.

Fenced and cut-off brokers

Diskless produce has no fencing check: each broker's own image decides. A broker that applies its own fence isn't in its own candidate set, so it rejects its first misrouted batch per connection and partition, and sends clients to the stand-in. A broker cut off from the controller never sees its fence. It keeps acting as the gateway while it reaches the coordinator leaders, and its clients drift to the stand-in as they refresh from other brokers. The cost is up to one extra part per file and uneven load. Nothing acknowledged is lost.

Takeaway

Routing saves the most in large, evenly sized racks, and nothing for partitions that need a local log. A hot gateway can carry up to 1.7 times today's busiest broker. One cluster-wide switch and one per-broker exclusion are the levers.

Part 5

Protecting the coordinator

The coordinator lives inside an ordinary Kafka topic, so everything that can happen to a Kafka topic can happen to it: a leader that doesn't know it was replaced, an admin who deletes the topic, a disk that gets wiped, a broker running an older binary. This part closes each of those doors.

34Reads, and the leader that doesn't know it was replaced

Why this exists

A KRaft broker that loses contact with the controller doesn't step down. It keeps answering from its own state until it learns about the new leader. For most reads, an older answer only makes a consumer re-read. One answer is different: "that offset doesn't exist yet." A consumer that believes it resets its position and can skip records. KIP-1164 lets followers serve findBatches, which widens this problem to every replica. This design serves reads from the leader only, and adds a barrier for the one dangerous answer.

KIP-1164: DisklessFindBatches on followersKafka parity

Only the leader answers

findBatches, listOffsets, and every other call go to the leader of the user partition's coordinator partition. Brokers absorb most lookups in the existing batch coordinate cache, so only cache misses reach the leader.

  • Reads don't block commits. The leader answers reads from a read pool with 4 threads, each with a read-only SQLite connection. Only commits, leases, releases, and fences use the single coordinator thread. Without the pool, a cache storm would put about 8B scans in front of every commit part.
  • Reads don't block the caller. findBatches becomes asynchronous on every backend, so a slow coordinator partition holds no shared thread.
  • Reads are bounded. Each broker allows at most 8 read parts in flight per coordinator partition. A part that fails or passes its 1000 ms deadline gives its user partitions KAFKA_STORAGE_ERROR, and the rest of the fetch returns normally. The consumer fetches again, so the delegate doesn't retry reads.

The deposed window

Unclean election is off, so a deposed leader's state is a committed prefix of the new leader's log. Every answer it gives is lower than or equal to the current answer, or unknown. A lower answer makes a consumer re-read, and an unknown answer makes it retry. The exception is findBatches for an offset above the deposed leader's high watermark: it says OFFSET_OUT_OF_RANGE, which can be false. Classic topics avoid this with KIP-320's leader epochs, but a coordinator leader change doesn't bump the user partition's epoch.

The barrier fixes it. When a request asks above the high watermark, the leader appends a barrier record and waits for it to commit. A deposed leader's barrier never commits, because the new leader stopped fetching from it, so after 500 ms the request gets the retriable OFFSET_NOT_AVAILABLE and the consumer refreshes. A current leader commits the barrier in one replication round trip, then answers truthfully. A consumer that keeps up never reaches the barrier, because an offset equal to the high watermark is in range.

37Electing a safe leader after a power loss

Why this exists

When every replica restarts uncleanly, Kafka elects the last known leader. If that broker came back with a wiped or replaced disk, it leads with an empty log, and the surviving replicas truncate to match it. On a classic topic that loses one partition's tail. Here, every follower truncates to offset 0, and the coordinator partition loses its whole batch index, leases, and deletion queues, while object storage doesn't roll back.

Data-loss barKIP-966: eligible leader replicas

The rule: storage identity, not shutdown cleanliness, decides whether a replica may lead.

  • Storage change guard. When a broker registers, the controller removes it from the eligible leader replicas (ELR) and the last-known-leader list of every coordinator partition whose log directory isn't in the new registration. Formatting always creates a new directory ID, so this catches a wiped, replaced, or reformatted disk. Registration comes before unfencing, so the guard runs before the broker can be elected.
  • ELR across an unclean shutdown. With flush.messages=1, every replica holds every acknowledged record on disk, so an unclean shutdown keeps it eligible, as a clean one does. The first returning replica wins a clean election.
  • No cluster-wide ELR clear. A cluster-level min.insync.replicas change normally clears every ELR. It skips this topic, whose own setting is fixed.

What this leaves open

Brokers in a cluster run different versions during an upgrade. What happens when a replica reads a record type it doesn't know?

38Mixed versions and upgrades

Why this exists

Every replica replays the same log into SQLite. A replica that skips a record it doesn't understand ends up with different state from the leader, silently. Upgrades and downgrades therefore need a rule for which records a leader may write and which binaries may read them.

Rolling upgradesReplicas must agree

A replica that meets an unknown record type stops, it never skips. Two features keep that from happening in a healthy cluster:

  • An upstream feature, for example diskless.coordinator.version, selects the backend. Level 0 means off. Each later level names the record types and versions a leader may write.
  • An Inkless-owned feature gates Inkless's own extension fields, with each level declaring the upstream level it needs.

The controller raises a level only when every registered broker supports it, and registration rejects a broker that lacks a finalized level. So the upgrade order is: roll every broker to the new binary, then raise the level. Raising the level is the point of no return. The controller refuses every downgrade of both features, because a downgrade would leave newer records in the log and snapshots, and brokers rolled back to an older binary would stop on them. There's no rollback onto PostgreSQL.

Takeaway

Features gate which records a leader writes. A binary that can't read them can't register, and a replica that meets one anyway stops instead of drifting.

What this leaves open

The coordinator acts on the metadata image: topics created and deleted, brokers registered and gone. Images lag. How does a leader avoid acting on an old one?

39Acting on a metadata image that lags

Why this exists

In the PostgreSQL design, the controller calls the control plane when a topic is created or deleted, and waits up to ten seconds on the request thread. The coordinator removes that call: each leader reconciles its state against its own metadata image. But images lag, and a leader that reads "absent" as "gone" could purge a live topic or reject a live broker forever. Absence only proves something when the image is past the point where the thing was created.

KIP-1164: Topic creation and deletionLeader changes

Topics

  • For each mapped diskless partition in the image that the leader doesn't hold, it appends a partition-created record with metadataOffset, the image offset it acted on.
  • For each topic it holds that the image no longer has, it appends topic-deleted only when the image is at or past the highest metadataOffset for that topic. Topic IDs are never reused, so absence past the creation offset proves the deletion.
  • A call that names a partition the leader hasn't created yet, an unreconciled partition, gets a retriable error and appends nothing. The caller retries until the leader's image catches up.

Broker epochs

KRaft sets a broker's epoch to the offset of its registration record. So an image at offset X shows every registration at or below X. When the image shows a newer epoch E for a broker, the leader retires through E - 1. When it shows no registration, the leader retires through X. And the leader appends nothing when retiredThrough would be below the newest epoch its own rows already hold, which covers an image that lags a new registration.

What this leaves open

One question is left about load: what stops one busy or slow coordinator partition from overwhelming its leader, or a recovering leader from being flooded?

40Bounding the load on a leader

Why this exists

A coordinator leader shares a broker with that broker's own partitions. If the work arriving at it had no bound, a cache storm, a retry loop, or a recovery burst could stall every commit behind that leader. A review asked for every source of load to have a limit with its own test.

Review finding: unbounded queuesCo-tenancy

The design bounds load at the sender, not with an admission cap at the leader. Each limit is per commit queue or per coordinator partition, so work stuck on one coordinator partition never blocks another:

  • Commit parts: one in flight per commit queue. Producer retries land in later files, so they add batches, not parts.
  • Lease requests: one renewal at a time per broker.
  • Release reports: one in flight per participant and tracking partition.
  • Fences: one batched request in flight per tracking partition and participant.
  • Read parts: at most 8 in flight per coordinator partition on each calling broker.
  • Retries wait with Kafka's exponential backoff: 100 ms, doubling to at most 1000 ms, with 0.2 jitter. A slow leader causes no retries. Only fast errors do.

The only thing that sheds load is the overlay cap of 4 × B entries from chapter 9, which only trips on a bug or a stalled high watermark. Why no admission cap? It would duplicate the in-flight limits, and shedding commit parts turns slowness into failed produce requests sooner.

41A produce and a fetch, end to end

The cluster has 3 racks of 8 brokers and N = 8, so racks are at saturation. Broker 3 is in rack a, in zone A. It's the rack-a gateway for cp0, so its gateway set is {cp0} and its tracking partition is cp0. Its epoch is 7, and it holds the lease [0, 1023] at cp0. A producer in zone A writes to orders-0, which maps to cp0.

  1. Route. The producer asks any broker for metadata. Every broker computes the same gateways from its image, so each one names broker 3 as the leader of orders-0 for a zone-A client (chapters 30 and 31).
  2. Buffer. Broker 3 adds the batch to its current file. Its other zone-A clients for cp0's user partitions write there too, so the file holds cp0 batches only (chapter 2).
  3. Close. After 250 ms, FileCommitter closes the file and gives it the pair (7, 41) from the lease. No request is sent (chapters 18 and 20).
  4. Name and upload. The object key is <clusterId>.3.7.41. Retries reuse the same key (chapter 19).
  5. Split. All of the file's batches map to cp0, which is also the tracking partition. So the file sends exactly one part: it carries the batches, the participant set {cp0}, and the finish report for earlier files (chapters 22, 23, and 32).
  6. Check. cp0's leader checks the mapping, the broker epoch, the lease, the broker row, and the producer's own idempotence rules. It reserves offsets against SQLite plus its overlay (chapters 9, 18, and 20).
  7. Append. The leader adds a file-committed record to the current batch and appends with acks=-1. The leader and each follower fsync it (chapter 10).
  8. Apply and reply. When the high watermark passes the record, the leader applies it to SQLite in a group with other records, moves broker 3's row to (7, 41), and replies with the offsets and the Recorded flag (chapters 11 and 23).
  9. Answer the producer. The producer's request waits only for the parts that hold its batches, here one. Broker 3 responds and fills its batch coordinate cache (chapter 15).
  10. Fetch. A consumer in zone A reads orders-0. Routing sends it to broker 3 too, so the read is usually a cache hit. On a miss, broker 3 asks cp0's leader, whose read pool answers from SQLite without touching the commit thread (chapter 34).
  11. Release. Days later, retention removes the batches on cp0. In the same transaction, the emptiness check finds nothing pointing into 3.7.41. cp0 is the tracking partition, so the release is local, and the key goes straight into cp0's deletion queue (chapter 22).
  12. Delete. After one minute, FileCleaner on cp0's leader deletes the key and appends a files-deleted record.

Compare this with the same produce on a cluster without routing: the file would hold batches for all 8 coordinator partitions and send 8 parts, plus 7 release reports later, one from each participant other than the tracking partition. If the producer's metadata had been stale, broker 3 would have rejected its first misrouted batch once, and the retry would have reached the right gateway.

42How the design is checked

Why this exists

Both reviews of the earlier version asked for proof, not prose: a model check of the fence, floor, and release protocol, and benchmarks with pass rules decided before anyone runs them. A benchmark without a pass rule invites arguing about the result after the fact.

Council review: model-check the protocolCouncil review: benchmark pass criteria

The model check

A TLA+ model covers leases, the switch and fallback, commits, late attempts, finish reports, fences, floors, releases, lease ends, retention, and the deletion queue. It has four modules: FencesFloors, FFScenarios, TrackingEntries, and EpochRetirement. It checks four invariants:

  • NoDeleteReferenced: no object is deleted or queued while a batch references it.
  • NoCutLive: no fence raises a floor past a part the broker still sends, or past a sequence it still plans to use.
  • NoLeak: once an epoch ended and the coordinator is quiet, every uploaded key that no partition holds is queued.
  • EndedKnown: once the lease covering a finished file ends, its tracking partition knows the key.

Within its bounds of 3 partitions, ranges of 2 sequences, up to 4 files, 1 late attempt, 1 pause, and 1 or 2 epochs, no invariant fails. Each rule the model guards has a flag, and turning it off reproduces the race that rule closes within seconds. The model leaves out the overlay, a tracking leader change, and more than one broker. Shared tests, cluster tests, and seam tests cover those.

Benchmarks with pass rules

The baseline is the PostgreSQL backend as Inkless runs it in production. A latency comparison passes when the coordinator's P50 and P99 produce latency are each at most 1.1 times PostgreSQL's at the same throughput. Each side runs 3 times for 30 minutes after a 10-minute warmup, and the comparison uses the median. Accepted limits

Performance limits aren't risks to data. Each one has a signal and a lever:

  • Outgrowing N. Each coordinator partition has one writer, so N caps commit throughput, and N can't change after creation. Choose N for the cluster's expected peak size, and reassign coordinator leaders to less loaded brokers. Splitting partitions is future work.
  • A hot gateway. The busiest gateway can carry up to 1.7 times today's busiest broker at some rack sizes. Watch BytesInPerSec against the rack mean. The levers are racks of up to 4 brokers or a multiple of N, or the routing switch off.

44Rejected alternatives and earlier versions

Why this exists

Knowing what a design rejected, and why, is often the fastest way to understand it. This design went through two earlier versions, each reviewed against the same bars. This chapter collects what they did and what replaced it, plus the larger alternatives the design turned down.

Design historyReviews

Version 1: an owner and an intent for every object

The first version kept KIP-1164's idea of an owner, but one owner collected everything instead of handing the object along. Before every upload, the broker sent an intent to an owner chosen among the participants: the random object key, the participants, and the owner. The owner appended and fsynced it before the upload could start. Each commit part carried the broker's clock reading. After a maximum commit age of 5 minutes, the owner fenced participants it hadn't heard from. Participants kept a tombstone per released key so a late retry couldn't add the batches back, and tombstones expired after twice the maximum commit age.

It failed both bars:

  • Performance. The intent is a replicated, fsynced append on the produce path, which PostgreSQL doesn't have.
  • Data loss. Safety depended on broker clocks. If two clocks differed by more than the maximum commit age, a late part could pass the age check after its tombstone expired, and commit batches into a deleted object.
  • Machinery. Intent records, owner hashing and fallback, predecessor fences, per-key tombstones, and expiry records, each a source of bugs.

Other rejected alternatives

  • An external database, a cluster KRaft quorum, or a separate KRaft quorum. KIP-1164 itself rejected these (chapter 4).
  • Coordinator-less designs, where partition leaders act as coordinators. KIP-1163 rejected them for separating stateful coordinators from stateless replicas.
  • A deleting scanner. It fails toward data loss (chapter 17).
  • Committing at the tracking partition first. It adds a second serial round trip to every commit (chapter 15).
  • A live-batch count per object. A count can drift toward zero while batches remain (chapter 22).
  • Follower reads and a leader lease. Followers widen the stale-read problem, and a lease adds a wait to every failover (chapter 34).
  • A controller-written gateway assignment, plain rendezvous, and round-robin. The first costs a new record type and controller code, the second leaves balance to chance, and the third moves too many slots (chapter 30).
  • Co-location mirroring, where gateways follow coordinator leadership. The coordinator still sends one part per coordinator partition, so it saves nothing and ties gateways to elections.
  • A monotonic grace period. It delays every delete by one grace period after each failover (chapter 27).

45Where this is heading

The north-star RFC's goal is one metadata component that indexes every form diskless data takes, instead of splitting the truth between the coordinator, tiered storage metadata, and KRaft. None of the following is part of this design, but each depends on a decision this design keeps intact:

  • Grow the coordinator by splitting partitions. With slot % N and a power-of-two N, doubling N moves exactly half of each partition's slots. It still needs a handoff of a slot's state.
  • Merge WAL objects into extents. A merged object replaces many batch rows with one extent row, and old objects release through the normal path. Merged objects in the WAL format also remove local-log partitions, so every partition can use gateways.
  • Tiered metadata in the coordinator. Remote segment metadata for a diskless partition would live in the same coordinator partition as its batches, which answers concerns Jun Rao raised in the KIP-1163 discussion.
  • Partitionless key ranges. Every record names its log with a Log structure, so a later encoding can describe a key range.
  • A report-only orphan scanner. It lists keys nobody holds without deleting them, the only detector for the two accepted leaks.
  • Object footers and recovery. A footer naming each object's partition runs would let an operator rebuild a coordinator partition after losing every replica, removing clause 2's exception.
  • Deletion bounds. Soft delete or bucket versioning for 7 days, checked by a probe, plus a deletion-rate cap. A wrongly deleted object could then be restored by name.
  • An empty restart. A coordinator partition that lost every replica could come back empty instead of staying offline.
  • Extra gateways for a hot coordinator partition, and the per-read rule, which routes every diskless partition to gateways and sends only reads that need a replica to one.

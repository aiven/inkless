How the diskless metadata coordinator works

Inkless diskless topics need a service that orders their data and remembers where it is. This page walks through a proposed design that keeps that state inside Kafka itself, in an internal topic, instead of in an external Postgres database. You follow one topic from creation to deletion, and you can poke at each mechanism along the way.

How to read this page Terms with a dotted underline, like [[hw]], show a definition when you hover or focus them; click one to jump to the glossary. Each lifecycle chapter has a stepped diagram: use Next and Back, or focus the diagram and press the arrow keys. The labs let you change things and watch what the system does. No background in the design is assumed, but some familiarity with Kafka helps; if you don't have it, read Kafka in five minutes first.

Why this exists

A [[diskless-topic]] stores its records in object storage, such as S3, instead of on broker disks. Any broker accepts produce requests for any partition. Each broker collects the [[batch|batches]] it receives, from many partitions and often from many topics, into one file, and every 250 ms (or once 8 MiB accumulates) uploads that file as one [[wal-object]].

That raises two questions that a classic Kafka partition answers with its local log:

  • Which offsets does each batch get? Many brokers write to the same partition at the same time, so something must put their batches in one order.
  • Where is each batch? A consumer asking for orders-0 at offset 42 needs the object and the byte range that hold it.

The [[batch-coordinator]] answers both. Brokers talk to it through the [[control-plane]] interface. Today's production implementation stores the state in Postgres, a separate database that every cluster has to run and scale.

The design on this page adds a third implementation, DisklessMetadataControlPlane. It stores the coordinator's state in an internal Kafka topic, [[dmt]], split into several [[cp|coordinator partitions]]. Every replica of a coordinator partition rebuilds that state into a local [[sqlite]] database, so lookups are local queries. It's a scoped-down version of KIP-1164: Diskless Coordinator.

ScopeThe design targets new clusters only: there's no migration from Postgres and no rollback onto it. It adds no public Kafka protocol; the new inter-broker requests use private API keys numbered 504 and up. Transactions, follower reads, and changing the coordinator partition count after creation are out of scope.

Five ideas carry the design

If you remember nothing else, remember these. Every chapter that follows is one of them in action.

1Split by user partition

Each [[user-partition]] belongs to exactly one coordinator partition, chosen by a hash. That coordinator partition's [[leader]] is its single writer, so offsets for a user partition always come from one place.

2The log is the truth

Every state change is a [[record]] in the coordinator partition's log. Replicas [[apply]] records to SQLite in log order, only up to the [[hw|high watermark]]. The same log produces the same database on every replica.

3Commits split into parts

A WAL object holds batches for several coordinator partitions, so the broker sends one commit [[part]] to each. Each part succeeds or fails on its own; there's no [[two-pc|two-phase commit]].

4Every object has one owner

No single coordinator partition sees all of an object's batches, so one of them, the [[owner]], records the object before upload and decides when it can be deleted. The others report to it.

5Snapshots bound the log

The coordinator log has no time-based retention. Each replica takes [[snapshot|snapshots]] of its database, and the leader trims the log only behind snapshots that enough replicas hold.

Kafka in five minutes

The design reuses ordinary Kafka machinery for the coordinator topic. If these terms are familiar, skip ahead to the example cluster.

  • A topic has partitions. Each partition is an append-only log, and every record in it has an increasing offset.
  • Each partition has [[replica|replicas]] on several brokers. One replica is the [[leader]] and takes all writes. The others are [[follower|followers]] that copy the leader's log by fetching from it.
  • The [[isr|in-sync replica set (ISR)]] is the set of replicas that are caught up. The leader counts itself.
  • Each replica's [[leo|log end offset]] is the offset its next record will get. The [[hw|high watermark]] is the point below which every ISR member holds the record. A record below it is committed: it survives losing any one replica.
  • With [[acks|acks=-1]] and [[min-isr|min.insync.replicas=2]], a write succeeds only once the whole ISR has it, and the leader refuses writes while fewer than two replicas are in sync.
  • When a leader fails, the controller picks a new one from the ISR, and the [[leader-epoch]] goes up. With unclean leader election off, a replica outside the ISR never becomes leader, so committed records never disappear.
  • [[kraft|KRaft]] is Kafka's metadata quorum. It decides which topics and partitions exist and who leads them. Each broker keeps a [[metadata-image]] of that state.

You can watch the high watermark move, and see a leader failure truncate uncommitted records, in the overlay lab.

Who owns a partition: the mapping

Every broker must agree, without asking anyone, which coordinator partition owns a user partition. If two brokers disagreed, one user partition would get two writers and duplicate offsets. So the mapping is a fixed function, part of the protocol, pinned by a test with fixed expected values:

  1. Build the [[log-key]]: the 16 bytes of the topic ID, then the partition index as 4 big-endian bytes.
  2. Hash it with Kafka's [[murmur2]] and make it positive: slot = toPositive(murmur2(logKey)) % 4096.
  3. Map the [[slot]] to a coordinator partition: slot % N, where [[N]] is the partition count of __diskless_metadata.

Because N must be a power of two, slot % N equals toPositive(murmur2(logKey)) % N. The slot layer costs nothing at runtime and stores nothing. It exists for a future change: if N doubles, coordinator partition p keeps half of its slots and hands the other half to the new partition p + N, instead of every user partition moving. Growing N still needs a state handoff, so for now the controller rejects CreatePartitions on the topic.

The partition index is part of the key, so one busy topic spreads across coordinator partitions instead of loading one leader. Each leader also re-checks the mapping on every request and rejects a user partition that isn't its own with INVALID_REQUEST.

1. Create a topic

Creating a diskless topic is mostly ordinary Kafka. What changes is who tells the coordinator. Today the controller calls the control plane while handling the request. In this design the controller never calls the coordinator: each coordinator leader notices the new topic in its metadata image and records it in its own log. That pattern, called [[reconciliation]], also handles deletion and outages.

2. Produce

Producing is where most of the design lives. A broker closes a WAL file holding batches for several coordinator partitions. It has to get offsets from each one, make sure the object can never be forgotten, and survive crashes and retries at every step. The order of operations is the key:

  1. Close the file, find its [[participant|participants]], and generate the object key.
  2. Store an [[intent]] at the object's owner. Nothing is uploaded until this succeeds.
  3. Upload the object.
  4. Send one commit part to each participant, in parallel. Each leader assigns offsets and appends a record.
  5. Reply to the producer once every part has an answer.

Start with the happy path, then try the scenarios where something goes wrong.

What a leader checks before it commits a part

Each coordinator leader runs every part through the same checks, in this order, on its single writer thread:

  1. Age and identity. Reject the part if its [[first-send|first-send time]] is older than the [[max-age|maximum commit age]] (5 minutes by default), or if the metadata image holds a newer [[broker-epoch]] for the uploader, which means the uploader has restarted since. A newer epoch than the image's is fine, because the image can lag.
  2. Predecessor fences. [[fence|Fence]] any earlier keys the part lists as unconfirmed, unless they did commit. See the "one coordinator partition is down" scenario.
  3. Is this a retry? Look up the object key in the overlay and SQLite. If a commit for it is pending or applied, append nothing and return the stored result of every batch. If the key is fenced or has a [[tombstone]], reject the part.
  4. Producer rules. Check [[idempotent|idempotent producer]] epochs and sequence numbers against SQLite plus the overlay, as the Postgres functions do against committed state.
  5. Reserve and append. Assign offsets in the overlay and add one file-committed record to the current batch. The record stores the committed batches and the outcome of every batch that didn't commit, so a retry gets identical answers.
  6. Apply and reply. When the high watermark passes the record, apply it to SQLite together with the applied offset, drop the overlay entry, and send the reply.

Why each coordinator partition gets its own commit queue

Today FileCommitter commits a broker's files on one thread, which keeps them in order. Ordering only matters within a user partition, which on this backend means within a coordinator partition. With one thread, a part stuck on one slow coordinator partition holds back every later file of the broker. Most files touch most coordinator partitions, so one sick coordinator partition would stall all diskless produce on every broker.

The design gives FileCommitter one ordered [[commit-queue]] per coordinator partition. A part runs once its file is uploaded and the previous file's part on the same queue has finished. Every part of a file shares the file's [[commit-deadline]], measured from when the file closed. Postgres and in-memory map everything to one queue, so their behavior doesn't change.

The overlay and the high watermark

A leader can't apply a record to SQLite until the record is committed, because a leader change could still truncate it. But it can't wait for each commit to replicate before starting the next, or throughput would collapse, and the next commit needs to know which offsets the previous one took. The answer is the [[overlay]]: an in-memory list of records the leader has reserved or appended but not yet applied. A new commit reads SQLite plus the overlay, so two commits never get the same offsets.

The leader runs this loop on Kafka's [[coordinator-runtime]], the framework behind the group and share coordinators, with one shard per coordinator partition. The runtime supplies the single writer thread, the [[linger|append linger]], [[parked-reply|parked replies]], and revert after a failed append. It writes through an Inkless PartitionWriter with acks=-1, so an append fails at once when the ISR is too small, instead of hanging until a timeout.

3. Consume

Reading is simpler than writing. A consumer fetches from any broker. The broker needs [[batch-coordinates]] (which object, which bytes) for the offsets the consumer asked for. Most of the time its [[cache|batch coordinate cache]] has them. On a miss, it asks the coordinator leaders, then reads the bytes from object storage.

4. Clean up data

Data leaves a diskless partition in four ways: retention, DeleteRecords, [[consolidation]] pruning, and topic purge. Each one removes batch rows from one coordinator partition. The hard part is the object: it holds batches for several coordinator partitions, and none of them knows when the others are done with it.

The design solves this with ownership. Each participant tells the owner when it holds no batch of the object anymore; that's a [[release]]. The owner deletes the object once everyone has released it. Participants that never speak up get a [[fence]], which forces a final answer.

Owner lab: when is it safe to delete?

The owner deletes an object only when two things are true: every participant is released, and the intent is older than the [[max-age|maximum commit age]], T. The age matters because a delayed commit part can arrive until T has passed; after that, every leader rejects it.

A participant the owner hasn't heard from is [[silent]]. It either still holds batches, or its part never committed, and only a fence can tell which. The owner fences only when a fence can unblock deletion: once T has passed and the owner itself, plus every participant it has heard from, are released. A fenced participant answers [[referenced]] if it holds a commit; otherwise it records the fence, rejects any later commit for the key, and counts as [[released]].

Two details keep the deletion state small and correct:

  • Tombstones. If a participant releases an object less than T after the part was first sent, it keeps a [[tombstone]] for the key. Otherwise a delayed retry of the commit could put back batches that retention had removed. Tombstones and fences expire after 2T through a [[keys-expired]], so SQLite only holds keys for objects released in the last 10 minutes.
  • Stale owners. If an intent is stored but its reply is lost, the broker falls back to another owner. The first partition now holds a [[stale-owner|stale]] intent. When it eventually fences, an answer names the real owner, so it drops its entry and never deletes the object.
Why not scan the bucket instead?A scanner that deletes objects no coordinator partition knows about is simpler, but it fails toward data loss: a stale snapshot, a restore, or a shared bucket prefix makes live objects look unknown. Owner-based deletion fails toward a leak. See Roads not taken.

Trim the coordinator's own log

The coordinator topic has retention.ms=-1 and retention.bytes=-1, so Kafka never deletes its segments by time or size. That's on purpose: the log is the source of truth, and a replica that loses its database rebuilds by replaying it. Without trimming, though, the log grows forever.

So every replica takes its own [[snapshot|snapshots]] of SQLite, every hour or every 1 GiB of applied log, whichever comes first, and keeps exactly two. The leader moves the [[log-start|log start offset]] forward only to a point that at least min.insync.replicas in-sync replicas, the leader included, hold a [[covering-snapshot|covering snapshot]] for. It uses its older snapshot, so the one it keeps after the next rotation still covers the log start.

Snapshot lab: how far can the leader trim?
B1 leads. Append records, take snapshots on each replica, and watch the log start. Then take B3 out of the ISR, or replace its disk.

A replica that needs records below the log start, because it's new or its database is gone, fetches a covering snapshot from an in-sync follower if one has it, and from the leader only as a last resort. The leader is already busy with every commit. Transfers are resumable, 8 MiB chunks are sent zero-copy from the file, and each broker serves one transfer at a time by default. Before the log start first moves, nothing needs a snapshot: a rebuild replays from offset 0.

5. Delete a topic

Deletion runs the creation flow in reverse, and then hands off to cleanup. KRaft decides the topic is gone, each coordinator leader notices on its own, purges the partition's batches, and the purge releases objects through the same owner path as retention.

Other calls in a partition's life

  • Classic-to-diskless switch. After the controller commits the seal, the partition leader calls initDisklessLog from InitDisklessLogManager, and the coordinator appends a diskless-log-initialized record. repairDisklessLog follows the same pattern from ReplicaManager.
  • Consolidation and cross-tier offsets. The broker that hosts a partition's local log decides the safe prune offset, from highestOffsetInRemoteStorage and the seal. It sends pruneDisklessLogs or advanceCrossTierLogStartOffset to the leader, which records the outcome. The leader never needs a local copy of the user partition's log.
  • Ordering. A user partition's creation, deletion, initialization, repair, and commits all go to the same coordinator partition, so they're ordered in one log. Nothing depends on ordering across user partitions.

When things fail

A design like this is mostly defined by its failure behavior. Pick a failure to see what the system does and which mechanism keeps it safe. The produce scenarios and the labs already show several of these in motion.

Roads not taken

Each of these alternatives was considered and rejected. The reasons explain a lot about the shape of the design.

Limits and open risks

The design is a draft, and it's explicit about what isn't settled:

  • Capacity is the open risk. Each coordinator leader handles every commit part, intent, release report, and cache-miss lookup for its user partitions, on top of its broker's own partitions. Splitting into N partitions reduces the work per batch, not the number of calls: an object usually touches most coordinator partitions, so each leader still gets about one part per broker per commit interval. A produce waits for its intent and then its slowest part, so tail latency grows with N. SQLite also shares the broker's heap, page cache, disk, and garbage collector. Benchmarks against Postgres, at N=1 and N=8, decide how serious this is.
  • Clocks. Deletion safety depends on broker clocks differing by less than one maximum commit age (5 minutes). With larger skew, a late part can pass the age check after its fence expired and point into a deleted object. The broker epoch check covers restarted brokers, not a live broker with a wrong clock. A metric for age-check rejections shows skew before it gets that large.
  • Durability cost. flush.messages=1 fsyncs every batch on every replica, because a correlated power loss would otherwise lose acknowledged commits. Benchmarks measure the cost; the fallback is Kafka's default flush with that exposure accepted.
  • Losing every covering snapshot. If the leader's database is gone and no replica holds a covering snapshot, that coordinator partition can't serve. How the leader gives up leadership of one partition is an open item.
  • Provisional defaults. N=8, the 5-minute maximum commit age, and the 1-hour and 1 GiB snapshot triggers all wait on benchmarks.
